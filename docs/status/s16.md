# S16 status — Search and skills

Updated 2026-10-19. Branch `ws/s16-search-skills`. Owner paths: `packages/search/**`, `packages/skills/**`, the `skills` migration and its drizzle mirror, this file. Plan: `docs/plans/s16.md`.

## What works (M1)

- **Unified search (S1)** — `@psyche/search`: FTS5 index (unstemmed tokens, diacritics folded, prefix matching with a plural fold) in `state/search.sqlite`; query language (`in:`, `type:`, `from:`, `before:`/`after:`/`on:` with relative dates, `has:approval|receipt|attachment`, `is:<provenance>`, `thread:`, phrases, `OR`, `-x`, prefix on the last word) that can never emit FTS5 syntax; BM25 × 30-day recency boost; grouped results in UI order with counts, collapsing messages onto threads and actions onto tasks; plain snippets with highlight ranges; memory fused live from `MemoryStore` by reciprocal rank fusion; adapters for threads, messages, tasks, actions, Library, feed, ideas, goals, connector caches; `SearchIndexer` for `thread.updated|deleted`, `chat.message`, `task.updated`, `task.action`, `approval.created`, `receipt.created`, `feed.post|updated`, `idea.updated`, `goal.updated`; `search.query` handler with deep-link routes. Passes the `SearchIndex` conformance suite.
- **Permissions in search**: incognito content is never stored (and removed when a thread turns incognito); designated-person threads are scoped to their session key and a delegated viewer sees only that scope and never memory; provenance on every hit.
- **Performance**: 100 000 documents, worst query ~260 ms (three common prefixes), a term in 70 % of the corpus ~130 ms, filtered and rare queries < 40 ms.
- **Skills loader (T1)** — `@psyche/skills`: discovery workspace → `$PSYCHE_HOME/skills` → bundled with precedence and "overrides"; frontmatter validation (Agent Skills fields, OpenClaw metadata, S20's `requires.tools` / `anyTools` globs); gating on bins / env / OS / tools; statuses (`active, disabled, ineligible, blocked, draft, unlocked, hash_mismatch, invalid, shadowed`); `<available_skills>` index under a character budget with an explicit omission marker; `skills_search` / `skills_read` tools; `$skill` references (max 8); slash commands; hot reload. S20's twelve bundled skills load, list and fit in ~3 800 characters.
- **Install and trust (T2)**: local folder, `.zip` / `.skill`, git at a ref pinned to a commit (no checkout); limits, symlink and traversal refusal; static scanner (pipe-to-shell, prerequisites that fetch or install, Gatekeeper bypass, persistence, credential access, exfiltration endpoints, secrets, encoded payloads, invisible characters, agent-directed instructions); optional VirusTotal by hash; `skill_install` approval (device-only, once) bound to name + scope + source + whole-tree hash; install writes exactly the scanned tree, lock file with pins, receipt; high findings install disabled and cannot be enabled; whole-tree hash re-verified on every load; update with per-file diff and re-approval; disable / remove; `skills.*` handlers.
- **`skills` table** (data model §10): migration `202610191300_skills_init.sql`, mirror `schema-s16.ts`, `SqliteSkillStateStore`.
- Tests: search 50 (parser, ranking, filters, scoping, grouping, events, handler, conformance, 100k performance); skills 89 (frontmatter, gating, scanner incl. bundled skills clean, prompt budget, references, diff, precedence, drafts, hash mismatch, state, tools, install via path / zip / git, approvals, lock, update diff, VirusTotal, handlers, hot reload).

## Decisions and doc deviations

- **Search index in its own file** (`state/search.sqlite`) instead of `psyche.sqlite` (ADR-004 says one file): it is derived and rebuildable, and its write volume should not contend with the transcript writer. `docs/02` §12 and `docs/04` §10 updated. S01 may ask to move it into the main DB; the package accepts any connection (`db` option).
- **Workspace skills need the owner's approval** (review design-02, Critical): architecture §13 says workspace skills are discovered; they still are, but load only with an owner approval in the lock file. `requireWorkspaceApproval: false` disables this.
- **Third-party skill text is `untrusted`** when read through `skills_read` (review design-24); bundled and owner-approved local skills are trusted.
- **`skill_install` cards use side-effect class `destructive`** so they are `once`-only and device-only, although installing is reversible. Binding fields: `{name, scope, source, treeHash}`; grant key `skill_install|<name>`. Docs 04 §4.2 / 05 §3.5 have no row for `skill_install`; proposed text is in `packages/skills/README.md`.
- `acceptance.md` files are hashed and scanned (they ship in the folder) but never given to the model. S20's acceptance fixtures contain injected-instruction text on purpose, so a scan of the whole bundled folder has `agent-directed-instruction` findings in `acceptance.md`; bundled skills are not scanned at load.

Git fetch size is bounded only by the 60 s timeout. The scanner is advisory; the approval, the lock, untrusted provenance of third-party text and "never widens tool policy" are the controls.

## T3 agent-proposed skills (M3, 2026-10-20)

Branch `ws/m3-skills-proposed`; protocol half in #479.

- **Protocol (#479)**: `SkillDraft` (+ status, step, replay), `skills.drafts.list|update|accept|dismiss`, event `skills.draft.updated`.
- **agent-core (hook signature, additive)**: `AgentEndContext` gains `ownerText`, `mode`, `taint`, `subagent`. New `routines.ts` (`attachRoutineDetector(hooks, {onRoutine, isIncognito, minSteps 3, minOccurrences 2, window 20})`) is the detection evaluator. It runs in-process on the existing `after_tool_call` / `agent_end` hooks and never changes a call or a result. It skips failed calls and meta tools, and counts only the owner's attended, non-subagent, non-incognito turns that end `final`. A routine is the same collapsed tool sequence ending such a turn again in the same thread. T4 plugins (#440) are not given these fields: plugins still see only outcome and steps.
- **`@psyche/skills` (`drafts.ts`)**: `SkillDrafts` turns a routine into a `SKILL.md`. The draft keeps tool names, input names only (never values), side-effect words, and `permissions` inferred for side-effecting steps. The owner's words pass through the Gateway's vault + audit redactors, then emails, links and long numbers are generalized; nothing tools returned is used. The draft must parse and pass the manifest check.
  - Rate limits: one proposal per thread per day, at most five open drafts. A routine already proposed, installed or dismissed is never proposed again. Open drafts expire after 14 days.
  - The owner can edit a draft (it is re-validated).
  - Accepting runs the replay check: the draft may not declare tools or approval kinds the routine never used, and every tool must still exist. It is then written to `$PSYCHE_HOME/skills/.drafts/<id>/<name>/`, a quarantine folder the loader never reads, and goes through `proposeInstall`: scan, policy, trust card, device-only `skill_install` card marked `proposedBy: agent`, lock.
  - Every proposal, edit, accept, dismissal, expiry and install is sent to the audit hook. The Gateway appends these to the hash-chained audit log.
- **Gateway**: `compose/skills.ts` attaches the detector in `start()` (when the Gateway's agent is a `PsycheAgentLoop`); `compose/index.ts` is not touched. `proposeSkills: false` turns it off. Drafts are handled by the same `createSkillsHandlers`, and installs mark the accepted draft `installed`.
- **UI**: `SkillDraftCard` / `SkillSuggestions` ("Suggested by <persona>" in Settings → Skills). Each card shows steps, occurrences, the redaction count and a tainted marker, plus a replay failure when there is one. Edit puts `SKILL.md` in a textarea; Review and install opens the same trust card and approval; Dismiss says the routine won't come back. MockGateway implements `skills.drafts.*`.
- **Tests (`--maxWorkers=1`)**:
  - `packages/agent-core/test/routines.test.ts` (3)
  - `packages/skills/test/drafts.test.ts` (7)
  - `packages/ui/test/screens-settings-skills.test.tsx` (3 new), stories `SkillsWithSuggestion`, `SkillSuggestionDoesNotReplay`
  - `tests/integration/skills/t3-skill-drafts.test.ts` (9): the scenario against the real Gateway (`tests/scenarios/t3-skill-drafts/`)
- **Deviation from docs/03 T3**: "from Ideas, verified by replay". The drafts are their own records (`SkillDraft`), not S15 Ideas, so they can carry the redacted text, manifest and quarantine state. "Replay" is a dry run against today's tools and the recorded needs: no tool is executed again, because re-running a routine would repeat its side effects. A real sandboxed replay can come with T4's sandboxed plugins.
