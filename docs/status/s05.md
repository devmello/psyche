## What works (M1)

- **Policy engine** in the security §3.3 order with a deciding rule and a trace per call, every decision audited as `tool_call.decided` (feature F1). Modes per the §3.2 table, connector matrices (F5), app tiers with fixed caps (F6), site rules and Task origin sets (F7), folder grants that fail closed (F8), taint escalation (F9), rules and model classifiers with fail-closed timeouts and circuit breakers (F10), hard prohibitions with one test each (F11).
- **Binding hashes and grant keys** for every kind, over strict canonical JSON; property tests and pinned vectors.
- **Approvals**: hashed single-use tokens per surface, 30-minute expiry, 400 ms arming, first authorized answer wins, late / replayed answers rejected and audited, approver checks, chat limited to `once`, rate limit, typed confirmation for permanent deletion, optional presence verification, delivery through `Notifier` (header only), `reissue()` from persisted call and context.
- **Grants**: `task | site | session | always` with TTLs and use counters; ledger queries, revoke, revoke-all, by device, MCP `tools/list` revocation, export (F4).
- **Audit**: hash-chained monthly JSONL with signed anchors, `verify` / `verifyDetailed`, query, export, redaction before hashing; receipts store with reconciliation (U3).
- **API handlers** `approvals.*`, `grants.*`, `audit.*`; caller identity from the connection.
- Tests: contract conformance on memory and SQLite (broker) and memory and files (audit); decision matrix; prohibitions; lifecycle; S23 cases. `pnpm -r test`, `pnpm -w typecheck`, `pnpm -w lint` pass locally.

## Decisions where the docs disagree

Following the doc that is stricter, or the architecture where it says "resolved". The doc owners should settle these (S23 README, S18 status list):

1. **Chat approval of `destructive`**: device-only (architecture §4.6 "resolved", the contract and its fake). Security §3.7, §9, §3.11 `chatSurfacesMaySee` and §16.6 still allow chat; they should be changed to match.
2. **Binding fields**: security §3.5 is treated as normative, with the extra fields from data model §4.2 and S23 added (see the permissions README). Data model §4.2 now says so.
3. **`send_email` grant key**: account + exact recipient set (security §3.5, design-11), not the recipient domain of data model §4.1 / architecture §4.6.
4. **`session` scope**: its own scope with the Gateway boot id and thread, 12 h idle, 24 h absolute, ended by `reissue()` and `endSession` (design-28), not "`always` with an app-session expiry" (architecture §4.6).
5. **`task` grants for `destructive`**: 8 h, not 24 h (design-28; `grants.destructiveTaskHours`).
6. **Task taint inheritance** (§16.7): the broker trusts the `taint` and `taintSources` the caller passes; it never clears them. Callers (S02, S04) decide inheritance; design-08 asks for "until owner re-approval".
7. **`exec_host` scopes**: `once | always` per security §5.4, although it is `destructive` (which otherwise means `once | task`).
8. **Untrusted writes to protected memory** in a tainted turn: denied (`prohibition:untrusted_memory_promotion`), as the S18 corpus chose; untainted ones ask.
9. **Credential-fill origin vs taint origins** (S18 item 4): the S06 Credential Broker refuses a target outside the item's bindings; the S05 taint rule asks when the fill origin is not among the tainting origins, even with a `site` grant.

## Reviews

- Generated decision matrix (mode × side effect × taint × grant) found two deviations from §3.2, now fixed: sensitive-category reads ignored standing grants' silence rule, and manual first reads offered only `once`.
- Binding property tests found non-plain records, `__proto__` keys and case-colliding headers binding nothing; fixed.
- An independent adversarial review found 15 issues (3 High: request floors lost from a bounded cache, `exec_host` grants not covering stdin / network, loopback and Gateway bypasses via `0.0.0.0`, `[::]`, mapped and wildcard-DNS forms). All fixed with regression tests in `packages/permissions/test/review-fixes.test.ts` and `packages/audit/test/review-fixes.test.ts`. Known limit: truncating the audit tail together with the anchors past the cut looks like a shorter log unless the signer keeps the last anchored seq (S14).

## M3 hardening: fuzzing (2026-10-20)

Property and fuzz tests in `packages/permissions/test/fuzz/` use fast-check with a fixed seed and a small run count by default, so the CI cost stays under a second. Longer runs:

```
PSYCHE_FUZZ_LONG=1 pnpm --filter @psyche/permissions test fuzz        # 20,000 runs per property
PSYCHE_FUZZ_SEED=7 PSYCHE_FUZZ_RUNS=5000 pnpm --filter @psyche/permissions test fuzz
```

- **`canonical.fuzz`:** canonical JSON never splits one value (any key order gives the same bytes) and never merges two (same bytes iff structurally equal). Covers Unicode NFC/NFD pairs, astral characters, controls, number spellings and nested arrays. A one-place edit always changes the hash. Exec argv is bound exactly while env order is not; email recipient order, case and duplicates never split a hash; purchase amounts must be safe integers.
- **`decide.fuzz`:** random modes, taint, `newTarget`, requesters, policies, tools (including forbidden ones), targets (loopback, Gateway, userinfo, opaque schemes) and pre-existing grants of every scope. The broker never allows:
  - a forbidden tool;
  - `financial`;
  - `destructive` without a `grant:*` rule;
  - anything above `none` in plan mode;
  - write+ on a new target in a tainted turn;
  - write+ for an allowlisted sender;
  - persona-denied tools for a designated person;
  - a loopback, Gateway or malformed target.

  Every result is explained (rule plus trace), and offered scopes stay within the side-effect class.
- **`grants-urls.fuzz`:** random use and renewal sequences never carry a grant past its scope's bound (task 24 h / destructive 8 h, site 30 d, session 24 h, always 90 d), and restart / end of Task end session / task grants. `canonicalUrl` returns a canonical, idempotent http(s) origin or throws `TargetError`. A navigation to any loopback spelling (decimal, octal and hex IPv4, `0.0.0.0`, `[::]`, mapped IPv6, wildcard DNS) or malformed URL is never allowed.
- **`approvals.fuzz`:** random sequences of answers (every surface × device / sender), forged tokens, clock jumps, binding checks, restarts and cancellations. At most one answer is ever accepted, and only from an approver on its own surface, armed and unexpired, never chat for destructive, chat scopes `once` only. A `once` approval verifies at most once and only for its own binding.

Found and fixed, each with a regression test in `test/review-fixes.test.ts`:

1. **Unused once approvals survived a restart.** An approved `once` that was not dispatched before a Gateway restart still verified afterwards, though the call it was for is gone (S23 design-09). `reissue()` now revokes it (`approval.invalidated`, reason `gateway_restart_unconsumed`).
2. **Hosts with empty labels were accepted.** `canonicalUrl` accepted them (`http://..` became the origin `http://.`, and `a..b` passed). They now throw `TargetError`; a single trailing dot is still removed.

The other counterexamples were bugs in the tests' own generators or expectations. Examples: a doubled float overflowing to Infinity; `exec_host` legitimately allowed by an `always` grant when enabled (§5.4); a credential-shaped URL denied as `visible_secret` before `invalid_target`.

## Threat model (docs/05 §2) against main after wave 2 (2026-10-20)

Done in code and tests: approval replay controls; the hard prohibitions in §3.9, including the typed-confirmation word for permanent deletes and always-ask for third-party account creation; taint escalation and persistence through restarts, subagents and Tasks (S02 #98, #107); memory write gating (S07); channel pairing, owner identity and group rules (S10); WebSocket Origin checks and no `gatewayUrl` (S01, S11); pairing and challenge rate limits; device revocation revoking its grants (gateway `grant-revocation.test.ts`); chat cards rendered from `renderForSurface` (S10, S12); the `fetch` SSRF policy (S09).

Gaps, most important first (owner in parentheses):

1. **MCP is not mounted in the Gateway.** `revokeMcpGrants` is wired in `compose/mcp-grants.ts`, but no MCP host part mounts it. Grant keys still include the `tools/list` hash, so stale grants stop matching once MCP is mounted, but there is no revocation event or diff yet (S09, S01).
2. **The vault is not in the default composition.** Origin-bound fills, post-fill `redact` and page-echo checks only run when `setup.credentials` is passed (S06, S01).
3. **No host egress proxy (§5.2).** `network: proxy` has nothing behind it (S21).
4. **Presence is not enforced everywhere.** Security settings need `operator.admin`, but there's no fresh-presence check (`handlers/settings.ts`). Passkeys fall back to `NO_PRESENCE` (fail closed), so authentication-required approvals cannot be answered from the web (S01). The helper Touch ID verifier is wired (S14).
5. **Backup restore can resurrect revoked devices and grants** (design-26) (S22, S01).
6. **Audit anchors are never signed.** `createAuditLog` is composed without a signer, and the helper has no signing capability, so tail truncation is detectable only after anchors exist (S14, S05).
7. **Task origin sets are never populated.** The engine honors `ctx.originSet`, but no producer fills it (S04, S08).
8. **Sandbox and srt profiles are not composed** for host helpers outside the MCP launcher (S21, S17).
9. **No signed update manifest check** (S22, S11).
10. **Missing rate limits:** inbound chat 30/min/sender and `fetch` 60/min/Task. Also missing: Cloudflare Access JWKS verification and mobile TLS pinning (S10, S09, S01, S19).

Smaller gaps:
- The `schedule` builtin does not record the tainting sources on the automation (S02, S04).
- The §3.10 "test values only" check needs the vault's test-item flag (S06, S08).
- `psyche security audit` lacks token age, chat surfaces for device-only kinds, unknown-tier MCP servers with network, TLS pins, version, VM shares and computer-use overrides (S22).
- VM share policy has no code yet (S14).
