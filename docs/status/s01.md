## What works (M1)

- **Server**: WS + HTTP on `127.0.0.1:7979`, `req/res/event` frames, `seq` + persisted `stateVersion` on every event, async dispatch, graceful shutdown, metadata-only JSON logs, `config.json` (validated, fail fast) with env overrides.
- **Auth and pairing**: signed Ed25519 challenge; loopback auto-pairing for the desktop (read/write/approvals, never admin) and the helper (`node`); node socket accepts only nodes; pairing requests with key fingerprint, transport and address; `devices.list|pairing.list|approve|deny|revoke` (approve checks the fingerprint and optional code; revoke closes connections and takes node authority); first-admin bootstrap with `psyched devices approve <code>`; rate limits (failed challenges 10/min/IP, pairing 5/hour/IP, 20 pending); pending connections close at expiry; Origin allowlist; proxy identity headers ignored; `trustedProxy` is a config flag only.
- **Idempotency**: results of side-effecting methods persisted in `gateway_idempotency` in the mutation's transaction; concurrent duplicates share one in-flight call.
- **Session controller**: per-thread serialization on the writer guard, `followUp` (durable, visible, removable queue) / `steer` / `interrupt`, cancellation revokes authority via `AgentLoop.cancel` and `PermissionBroker.revokeRunAuthority`.
- **Threads and chat**: every `threads.*` method (one main thread, side, incognito with 24 h expiry, title search, activity counts, cursor paging, fork with lineage copying blocks and provider-native turns verbatim), `chat.send` (Library attachments as `file` blocks), `chat.steer`, `chat.followUp`, `chat.cancel`, `chat.history`, `chat.queue.list|remove`, `chat.export` (Markdown, JSON), `events.subscribe` filters.
- **Agent wiring**: `AgentEvent` → `chat.delta`, `chat.block`, `chat.message`, `run.updated`, `tool_call.updated` (persisted rows), `approval.created`, `question.created`.
- **Nodes**: registry over the node protocol, `nodes.list|capabilities|invoke` through `PermissionBroker.decide` with approval requests, `approvalId` passthrough re-verified with `verifyBinding`, receipts via `recordReceipt` + `receipt.created`; `vault.*`, `keychain.*` and security namespaces unreachable.
- **Restart recovery** and **retention** as described in the README.

## Independent review of this diff

A read-only reviewer reported 10 findings (3 reproduced); all are fixed with regression tests in `test/review-regressions.test.ts`: an interrupt now detaches the superseded turn before the new one starts and finished runs cannot be reopened; `threads.delete` stops the thread's queue before cancelling; a reconnecting node stays online; recovery leaves tool calls of suspended runs alone; retention keeps expired incognito threads that still have suspended runs; the capability denylist matches whole names (`vault`, `vault_fill`, `keychain/read`); every persisted run and tool-call update bumps `stateVersion`; scopes are re-read from the device row on each request (a downgrade or revocation applies to live connections); an unverified `approvalId` is not passed to the node on `allow`; agent errors are logged by code only.

## M3: VM mode, Gateway side (L1–L5)

Protocol #247 (`TaskWorkspace`, `SandboxBackendKind` `vm`, `VM_SETTING_KEYS`), then `ws/s01-vm-mode`.

- **Task mode selection:** `Task.workspace` (`sandbox | vm`) is persisted (`202610231000_tasks_workspace.sql`) and set by `task.start {workspace}`. Absent means `vm.defaultWorkspace`, else `sandbox`. `exec` routes per call (`runnerFor`). A Task that asked for the guest never falls back to the host's container, and the reverse holds too.
- **`compose/vm.ts`:**
  - `VmRunner` (a `SandboxRunner`, backend `vm`) sends commands to the guest psyche-node's `exec`, with the Task's scope.
  - It is refused (`unavailable`, with a reason) while VM mode is off (`vm_disabled`), the guest is not `running` (`vm_not_running`), or the node set in `vm.guestNodeId` is offline (`vm_guest_offline`).
  - Guest results are always `untrusted`, and the guest's own receipt is re-recorded as `vm.exec`.
  - It polls the helper's `vm.status` (30 s, or 3 s while a guest is busy) and publishes `vm.updated` for every changed guest, plus a `vm.lifecycle` receipt (audited) for each phase change.
- **Settings:** `vm.enabled`, `vm.guestNodeId`, `vm.defaultWorkspace`, `vm.clipboard`, `vm.credentials`, all admin-only and read on every decision. S11 draws the screen. Without a container backend, `exec` is registered only while `vm.enabled` is true.
- **Found on the way:** approval cards from background Task runs were never published as `approval.created`, because only the session controller announces cards, for chat turns. The loop's broker handle now announces cards whose `requestedBy.taskId` is set.
- **Guest side:** psyche-node `GuestRunner` (`exec.guest` in the guest's `node.json`) runs `exec` on the guest itself. S14's guest bootstrap should write that file.
- **Tests:**
  - `apps/gateway/test/vm-mode.test.ts` is the scripted scenario, run against a fake helper and a fake guest node on the real node socket. The chat starts a `vm` Task; its `exec` runs in the guest with the Task's scope; the evaluator closes it; `vm.updated` and receipts are checked.
  - The same file covers no host fallback while stopped or disabled, and `exec` following `vm.enabled`.
  - `apps/node/test/guest-runner.test.ts`.
- **Not done:**
  - auto-detecting the guest node (node kind `vm-guest`) without `vm.guestNodeId`
  - `filesChanged` in the guest
  - the display pane and clipboard enforcement (L4, S11/S14)
  - shares in Task context (L5 is enforced by the helper)

## L6 VM snapshots and resets: Gateway contract (with S14)

- **The helper (S14, protocol #452)** offers `vm.snapshot`, `vm.restore`, `vm.reset` and `vm.snapshot_delete` with the `VmSnapshot*` shapes. The Gateway calls them only from:
  - **owner methods** `vm.snapshots.list | create | restore | reset | delete` (protocol, S01). They are admin-only and side-effecting; each is a `vm.snapshot` receipt (audited) and is followed by a `vm.updated` refresh;
  - **per-Task reset:** with `vm.resetPerTask` on, a `vm` Task's first command runs after `vm.reset` (once per Task), audited as `vm.lifecycle` / `vm.snapshot`. A failed reset fails the Task's command; it never runs on an unreset guest.
- The agent gets no snapshot or reset tool: changing the guest is the owner's (docs/05 §13).
- **Asks to S14:** `vm.reset` / `vm.restore` refuse while the guest is `running`. The Gateway stops it first with `vm.stop` and starts it again after the reset, so please keep `vm.stop` / `vm.start` idempotent.

- **Follow-up spotted:** messages from non-owner channel requesters are stored with provenance `owner` in the transcript (the requester itself is passed to the turn); they should be `untrusted`.

- **Compose owns what it opens:** `composeGateway().stop()` closes the database compose opened itself; a caller-supplied `db` stays open (tests in `apps/gateway/test/compose-restart.test.ts`). `PsycheDb.close()` is idempotent, so an extra close in a test is harmless.
- **Fresh presence for security settings (S05 #178) and the helper's key:** #178 counts the helper verifier as ready when `HelperSetup.presenceKeys` is configured. It should count it only once a presence key is registered for at least one paired helper device, because a verifier with no key can never verify and would lock security settings. Today nothing registers one: the helper exposes `presence.public_key` (#102), and registering it is an owner action in the Gateway (mac-helper README). Next S01 step: an admin method that reads the key from a paired helper through `nodes.invoke presence.public_key`, shows the key id for confirmation, stores it (device-bound, revoked with the device), and makes `ready()` true only while one is stored. Until then the gate stays off, and security settings need `operator.admin` only.

- **Speech mounted (S17 #135):** `composeSpeech` (always on) mounts `voice.*`, `voice.memo.save`, `speech.readAloud`, `speech.voices` over the helper engine; `EventBus.publishToDevice` and `GatewayContext.deviceDisconnected` are new for it.
