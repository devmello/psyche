### Gateway bundle (build-psyched.mjs)

- `node deploy/scripts/build-psyched.mjs [--smoke] [--skip-web-build]` builds the layout above for the host arch. It exports the tracked tree, installs the Gateway's and CLI's production dependencies, builds the web client, prunes prebuilt addons for other platforms (14 on arm64) and fails on any `.node` file for the wrong arch. It adds Node from nodejs.org (SHA-256 checked, cached in `~/Library/Caches/psyche-build`), the launchers, the plist template and `build-info.json`.
- Proven on darwin-arm64: the built `psyched` starts with only `PSYCHE_HOME` set (no PATH, Node or checkout), answers `/healthz`, serves the web client and creates its database (`apps/gateway/test/dist-bin.test.ts`, which runs when a bundle exists).
- **Size: about 935 MB** (Node 128 MB, `node_modules` 809 MB). Most of it is UI code the Gateway never runs: `@psyche/gateway` depends on `@psyche/viewers`, which depends on Univer and `@psyche/ui` (React, lucide-react, base-ui, Sandpack), plus build tools as production dependencies (rolldown, happy-dom). **Request to S13:** give `@psyche/viewers` a server-only entry, or make the UI packages peer or optional dependencies, so the Gateway's production graph drops them. The Docker image carries the same weight.
- x64: build on an Intel host (the release workflow's DMG job, next PR).

### Installer DMG (make-dmg.sh)

- `deploy/macos/make-dmg.sh <Psyche.app> <version> <arm64|x64> <out>` stages the app with an `Applications` link and lays out a Finder window over `deploy/macos/dmg-background.png` (drag arrow, plus the unsigned-build hint; regenerate it with `node deploy/macos/make-background.mjs`). The layout uses a read-write image, then compresses to ULFO. It scripts Finder, which raises a one-time Automation prompt on a desktop Mac, so it is **opt-in** with `PSYCHE_DMG_LAYOUT=1`: on by default only when `CI=true`, and set explicitly in `release.yml`. Without it, or where Finder scripting fails, the DMG is plain (the app and the `Applications` link). It writes `Psyche-<v>-<arch>.dmg.sha256` next to the image.
- Without `PSYCHE_SIGN_IDENTITY`, the app keeps the package step's ad-hoc, inside-out signature (#390). An app that arrives unsigned or invalid is signed ad-hoc in the DMG copy instead: `codesign --force --deep --sign - --entitlements`, no hardened runtime. Gatekeeper and first-open steps: `apps/desktop/docs/signing.md`, "Without a Developer ID".
- Tested: `apps/cli/test/deploy.test.ts` (macOS, only with `PSYCHE_DMG_TEST=1`, because it mounts a disk image) builds a stub app both unsigned and presigned, mounts the DMG, and checks the `Applications` link, the ad-hoc signature (kept when presigned) and the checksum.
- Real run, once, on darwin-arm64: `electron-forge package` from main, plus this machine's `psyched` copied into `Contents/Resources` as #390 lays it out. It produced a 403 MB DMG in 83 s. The app arrived unsigned, so the `--deep` ad-hoc fallback ran. Finder layout applied (`.background`, `.DS_Store`, `Applications` link). `shasum -c` OK, `codesign --verify --deep --strict` OK, `Signature=adhoc`. `psyched` started from the mounted image with only `PSYCHE_HOME`: `/healthz` `{ok:true}`, the web client served, `psyche.sqlite` created. `--deep` leaves loose Mach-O files under `Resources/psyched` alone: `runtime/node` keeps the nodejs.org signature (hardened runtime) and still loads the addons. The window layout was not inspected visually. `hdiutil create/attach/convert` print deprecation warnings on macOS 27 (use `diskutil image`); they still work.
- `release.yml` dmg job: runs `build-psyched.mjs --smoke` and `deploy/macos/build-helper.sh` (#388) before `package`, x64 on `macos-15-intel`, and uploads the `.dmg.sha256` too. The agreed helper path is `apps/mac-helper/dist/PsycheHelper.app` (#388); the job passes it as `PSYCHE_HELPER_APP` while the desktop default moves to it.
## Packaging layout (Psyche.app from a DMG, no Node or checkout on the Mac)

S22 builds the Gateway bundle; the desktop-bundle session copies it into the app with Forge (`forge.config.ts`) and signs it with the rest of the app. Paths are relative to `Psyche.app/Contents/`.

```
MacOS/Psyche                                   Electron (desktop)
Resources/
  app.asar                                     desktop (desktop session)
  psyched/                                     ← copy apps/gateway/dist-bin/darwin-<arch>/psyched/ verbatim (S22)
    psyched                                    launcher, /bin/sh: exec runtime/node app/apps/gateway/src/main.ts "$@"
    psyche                                     CLI launcher, same runtime: app/apps/cli/src/main.ts
    runtime/node                               official Node 24.x darwin-<arch> binary (version = deploy/scripts/node-pins.mjs pins), SHA-256 checked against nodejs.org SHASUMS256
    app/                                       workspace subset run by Node's type stripping (same as the Docker image):
      apps/gateway/src/…, apps/cli/src/…, apps/web/dist/… (built web client), packages/*/…, templates/…,
      node_modules/… (production dependencies only; native addons as plain .node/.dylib files, never in an asar)
    com.psyche.gateway.plist.template          LaunchAgent with two placeholders: {{PSYCHED}} and {{PSYCHE_HOME}}
    build-info.json                            {version, commit, node, arch, builtAt}
  launchd/com.psyche.gateway.plist             desktop's `bundledPlist`: render it from the template at install time
                                               (replace {{PSYCHED}} with Resources/psyched/psyched and {{PSYCHE_HOME}}
                                               with the home, XML-escaped), never copy it verbatim
  Psyche Helper.app/                           the Swift helper (S14 build), copied by the desktop session
```

Rules for the desktop session:
- `bundledProgram` = `Resources/psyched/psyched` (already in `apps/desktop/src/main.ts`). It needs only `PSYCHE_HOME` in its environment; it sets nothing global and writes only under `$PSYCHE_HOME`.
- **Signing:** every Mach-O under `Resources/psyched/` (`runtime/node`, each `.node`, `.dylib` and helper binary such as node-pty's `spawn-helper`) must be signed with the app's identity. `@electron/osx-sign` signs nested binaries when they are not in an asar. Under the hardened runtime, `runtime/node` needs `com.apple.security.cs.allow-jit` (already in `apps/desktop/entitlements.plist`). Ad-hoc builds (no Developer ID) are signed without the hardened runtime, so library validation does not block the addons.
- **Do not** put `psyched/` in `app.asar`, and do not prune or rebuild its `node_modules`. They are already built for `darwin-<arch>` with Node 24's ABI.
- **Size:** roughly 110 MB runtime plus the app tree. `du -sh` is in `build-info.json` once the first build lands.
- **x64:** the same layout under `darwin-x64`, built on an Intel runner in the release workflow. Universal app: one `psyched/` per arch, selected by the Forge `--arch` build (no lipo).

## M3 release hardening

- **Release preflight**: `deploy/scripts/release-preflight.mjs` runs first in the release workflow and by hand before tagging. It fails on a missing or short dependency cool-down (`minimumReleaseAge` below 1440 minutes, DEP-11), floating or disagreeing Node pins (#295), an unpinned image in the release Compose file (#296), a malformed `deploy/update-policy.json` and a sandbox signer regexp that would not match `release.yml` tag runs; it warns while no update-manifest key is embedded. The cool-down is listed in the docs/05 §10 coverage table as a release-time check: a user's install has no lockfile, so `psyche security audit` cannot check it.
- **Node base-image pins (#295)**: `deploy/scripts/node-pins.mjs` lists every Node pin (`deploy/Dockerfile`, `deploy/sandbox-image/Dockerfile` and `versions.json`, `tests/integration/server-mode/Dockerfile`), checks they are exact `x.y.z` versions pinned by digest and agree (`check`), compares with nodejs.org (`check --latest`, a step of the release deploy smoke, so a tag cannot ship an outdated Node) and re-pins them all from Docker Hub (`update --version`). The Gateway Dockerfile and the server-mode test image moved from the floating `node:24-…` tags to `24.22.0` (same digests). **To do on 2026-10-21 or after**, once the patched images publish: `node deploy/scripts/node-pins.mjs update --version <24.x patched>` then `check --latest`, one PR covering every file (the sandbox image with S21).
- **Security audit completeness** (#331): every check in security §10 and the S05 review has a rule or is listed as "not checked" (TLS pins, VM shares, chat surfaces for device-only kinds: no data source yet); coverage table in docs/05 §10. New rules: `sandbox.egress_off`, `mcp.no_launcher`, `mcp.unknown_with_network`, `computer_use.sensitive_override`, `browser.real_chrome_enabled`, `browser.real_chrome_standing_grant`, `backups.unencrypted`, `backups.stale`, `updates.refused`, `updates.no_release_key`, `devices.old_token`, `version.mismatch`. Gateway pieces they need: `sandbox.status` is now served (it had no handler, so `sandbox.disabled` never fired on live data), new `mcp.status`, and `browser.realChrome.status` reports `enabled` from the setting as well as the env.
- **Sandbox image publishing, reviewed on paper** (`deploy/sandbox-image/publish.sh`, `release.yml` jobs `sandbox-image` and `sandbox-image-pr`; nothing built locally). `publish.sh --dry-run --version 1.2.3 core base full` prints, per variant, a multi-platform `buildx build --push` with provenance and SBOM, then `cosign sign` by digest, and leaves `versions.json` untouched; bad versions and unknown variants exit 2. `apps/cli/test/deploy.test.ts` now runs that dry run. Walking the job: it publishes only when `PUBLISH` and the ref is a `v*` tag (dispatch runs and branches dry-run); before building it checks that `versions.json .repository` is under `ghcr.io/<owner>` and that this run's signer identity (`https://github.com/<repo>/.github/workflows/release.yml@refs/tags/v…`) matches `.signing.certificateIdentityRegexp`; after pushing it `cosign verify`s every variant against that regexp and issuer; `sandbox-image-pr` copies only `version` and `variants` onto the default branch and opens a PR. No defects found. Notes: a full tag run takes up to ~3 h (the `full` variant under QEMU); the digests PR is opened with `GITHUB_TOKEN`, so it starts no workflows (irrelevant under the local merge gate).
- **Signed update manifest** (#252): the release workflow zips each packaged app, builds `update-manifest.json` and signs it with Ed25519 (`RELEASE_SIGNING_KEY` in the `release` environment); the desktop verifies signature, version, pinned host and the zip's SHA-256 before Squirrel sees it (security §11). No key is embedded yet, so updates stay off until the owner runs `node deploy/scripts/update-manifest.mjs keygen` and adds the public key to `apps/desktop/src/main/release-keys.ts`.
- **Upgrade round trip (scripted):** `deploy/scripts/upgrade-roundtrip.mjs` (fresh home → `migrate --check` → psyched + pairing → online backup → `migrate --check` on live data → verify + restore into a second fresh home → `migrate --check` → a Gateway boots from it with the data). Run by `apps/cli/test/upgrade-roundtrip.test.ts`; `PSYCHE=<binary>` tests a release build.

### First release checklist

In order, for v1.0.0 (or any first tag of a fork):

1. **Repository settings**: everything in the table above (Actions may create PRs, the `release` and `release-dry-run` environments, the `v*` tag ruleset).
2. **Update-manifest key** (security §11): on an offline machine, `node deploy/scripts/update-manifest.mjs keygen release-key.pem`. Keep the PEM in a password manager and paste it as the `release` environment secret `RELEASE_SIGNING_KEY`. Put the printed `{keyId, publicKey}` into `apps/desktop/src/main/release-keys.ts` in a PR. Installed apps can verify updates only from the release *after* the one that ships the key, so this belongs in v1.0.0 itself.
3. **Signing secrets (optional)**: the Developer ID certificate as `MACOS_CERTIFICATE_P12_BASE64` + `MACOS_CERTIFICATE_PASSWORD` + `MACOS_SIGNING_IDENTITY`, and an App Store Connect API key as `APPLE_API_KEY_P8_BASE64` / `APPLE_API_KEY_ID` / `APPLE_API_ISSUER`. Without them the release is unsigned and says so.
4. **Homebrew**: create the empty repository `devmello/homebrew-psyche` and a fine-grained token with contents:write on it only, as `HOMEBREW_TAP_TOKEN`.
5. **Pins current**: `node deploy/scripts/node-pins.mjs check --latest` (after a Node security release: `update --version <patched>` first, #295).
6. **Preflight and round trip**: `node deploy/scripts/release-preflight.mjs` (no `fail`; the `release-keys` warning must be gone after step 2) and `node deploy/scripts/upgrade-roundtrip.mjs`.
7. **Dry run**: Actions › release › Run workflow on `main` with `dry_run` ticked. It runs in `release-dry-run`, builds everything and publishes nothing.
8. **Changelog**: Run workflow with `version_pr` ticked, review and merge the "Version Packages" PR.
9. **Tag**: `git tag -s v1.0.0 -m "Psyche 1.0.0"` and `git push origin v1.0.0`, then approve the `release` environment when the release job asks.
10. **After the tag**: make the two GHCR packages public; merge the sandbox digest pin PR the workflow opens; check the signatures with the cosign identity above (`cosign verify ghcr.io/devmello/psyche-gateway@<digest> --certificate-identity-regexp … --certificate-oidc-issuer https://token.actions.githubusercontent.com`); `brew install --cask devmello/psyche/psyche` and `brew install devmello/psyche/psyche-cli` on a clean Mac; check that `update-manifest.json` and its `.sig` are attached to the release.

## Independent review (fixed in this PR)

A read-only review of the diff found: crafted backup manifests could rename files outside `$PSYCHE_HOME` on restore (entries and file paths are now validated against the known top-level names, with rollback on a failed restore); tar failures were unhandled rejections; the Compose backup scripts `cd`'d into a directory owned by uid 10001 and copied identities next to the backup (now absolute paths and the identity on stdin); signed Bun binaries lacked JIT entitlements; Compose env vars silently overrode `config.json`; `launchctl bootstrap` raced `bootout`; node-shim `psyched` paths would crash-loop under launchd's PATH; `config set gateway.host 0.0.0.0` was accepted; `backup verify` extracted plaintext next to the archive (now under `$PSYCHE_HOME`); Ctrl-C at a secret prompt hung. Left as is: `security import -P` takes the P12 password in argv on the ephemeral macOS runner (no alternative in `security`); the Playwright sidecar fetches its pinned npm package on start (documented in the Compose file).

## Objections to the docs (proceeding with the doc's intent)

- **Security §10 "Docker defaults"** says the image binds the container interface with `PSYCHE_BIND=container` and requires `PSYCHE_GATEWAY_TOKEN_FILE`. The Gateway implements neither and refuses non-loopback binds. Compose therefore uses host networking: the Gateway listens on the host's loopback, nothing is published, and the proxies (Tailscale, cloudflared) run on the host network. This meets the goal (no exposed bind) but needs Linux or Docker Desktop host networking. When S01 adds a container bind with token auth, switch Compose to a bridge network with the proxy on an internal network.
- **Architecture §14 / security §14** say backups are age-encrypted; the doc does not say how the snapshot stays consistent. The CLI never opens the database, so backups stop the Gateway (`--stop`). An online snapshot needs a Gateway method (request below).
