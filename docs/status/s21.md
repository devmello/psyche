# S21 sandbox: status

Updated 2026-10-20. Branch `ws/s21-sandbox` (M1), `ws/taint-handoffs` (design-07 follow-up). Plan: [docs/plans/s21.md](../plans/s21.md).

## What works

- **Image** (`deploy/sandbox-image/`): multi-stage `core` / `base` / `full` on digest-pinned `node:24.22.0-trixie-slim` and `uv` 0.13.1. It runs as UID/GID 1000, is compatible with a read-only rootfs, has no setuid/setgid binaries and gives root no shell or password. Built with Docker (OrbStack) and Apple `container build`.
- **`ContainerSandboxRunner`** (`packages/sandbox`), implementing `SandboxRunner` on Apple `container`, Docker and Podman:
  - per-scope containers with the full contract and network none by default;
  - a persistent named `/workspace` volume per scope;
  - bounded commands with receipts, process-group interrupts recorded as `uncertain`, and a 128 KB cap per stream;
  - `filesChanged`;
  - a per-scope concurrency limit, warm reuse with an idle stop, a cap on running sandboxes, and adoption of containers left by an earlier process;
  - an in-container PTY;
  - the workspace file API (symlink and special-file rejection, atomic writes, 256 KB / 10 MB caps).
- **Detection** order: Apple `container` (macOS 26+, arm64), then Docker, then Podman; with an override (option or `PSYCHE_SANDBOX_BACKEND`). No backend means `unavailable`, never the host shell.
- **Tests**: 52 unit tests (no runtime needed); the 15-check smoke test on every detected backend; the `@psyche/testing` `SandboxRunner` conformance suite against the real runner. 88/88 green on this Mac with Docker and Apple `container`. `pnpm sandbox:smoke` prints the same checks as a table.
- **Independent review** (a subagent over the full diff) found 10 issues, all fixed before the PR:
  - Agent-written programs in `/workspace/.local/bin` (first on PATH) could replace the helpers and read per-exec secrets. Every helper and tool now starts by absolute path, and a smoke check plants fake binaries.
  - Env names could overwrite wrapper variables (`secs` lifted the timeout). Env now applies only to the command, via `env --`.
  - Races: idle stop vs restart, the running-sandbox cap under concurrent starts, and orphaned containers after `dispose`/`destroy`.
  - A CLI-error heuristic misfired on ordinary `Error:` output and emptied `filesChanged`.
  - The PTY relay could deadlock on a large paste.
  - PTY sizes were not clamped.
  - A missed `filesChanged` entry within one clock tick (the marker is now back-dated).
  - Host-side validation of helper output was missing.

## M2 follow-up: file provenance (S23 design-07, issue #97)

Branch `ws/taint-handoffs` (shared with S04's #96), `packages/sandbox` README "File provenance".

- A host-side provenance index per scope (`src/provenance.ts`: `WorkspaceProvenance`, `MemoryProvenanceStore` default, `FileProvenanceStore(dir)` for persistence; option `provenanceStore`). It never lives in the volume, because everything under `/workspace` is writable by the agent as UID 1000.
- File API: `writeText` / `edit` / `importFile` take `{ provenance, sources }` (absent = `untrusted`; imports are untrusted at birth) and record the write with the content hash; `readText` / `exportFile` / `stat` return `{ provenance, sources }`; `list` marks each file and returns the listing's provenance. A file with no record, or whose bytes differ from the recorded write, is `untrusted` (`{ sourceKind: "workspace", origin: "/workspace/<path>" }`).
- `exec`: `ExecRequest.provenance` / `taintSources` (additive `protocol:` change, `CHANGES.md`) say what the command's writes carry; `filesChanged` is recorded with it. `ExecResult.provenance` is `untrusted` when the request was, or while the workspace holds any untrusted file, and files such a command changes inherit the untrusted files' sources. A capped or failed change listing after an untrusted command keeps the workspace untrusted until `deleteWorkspace`.
- `FakeSandboxRunner` mirrors the exec rule; `FakeDriver` (sandbox tests) now answers the in-container file helper from an in-memory workspace. Tests: the issue's two cases as written plus eight more (`test/provenance.test.ts`); the smoke test asserts the provenance of its own writes.
- Not run here: the smoke test on a real backend (Docker was not running on this machine during the change); CI's Ubuntu job runs it.
- Follow-ups: the `exec` and workspace file tools (S01, `apps/gateway/src/compose/file-tools.ts`) must pass `ctx.taint` / `ctx.taintSources` as `provenance` / `sources` and report `result.provenance` as the `ToolResult` provenance; wire `new FileProvenanceStore(join(PSYCHE_HOME, "sandbox", "provenance"))` so a restart does not forget. No owner "mark trusted" path yet (S11 files pane). PTY writes are unobserved and read back as untrusted. No xattr on the files themselves.

## M2 follow-up: dev servers for the browser's dev preview (feature I12)

Branch `ws/sandbox-devservers`, README "Dev servers". Requested by the integrator for S08's dev preview (#128 / #138).

- Security finding, fixed by design: a sandbox port is not a host port (network `none`), so announcing the container's port number to the dev-preview registry would let the preview open any host process on that number (security §3.10). The runner binds its own `127.0.0.1:<ephemeral>` forward per listener and announces that port.
- `onDevServer` on the runner (opt-in): a session-scoped listener probe after each exec, background re-probes for late binds, a relay per connection over `exec -i`, a 5 s liveness poll, `stopped` on container stop / remove / dispose, idle stop held while a server is forwarded.
- Gateway: `apps/gateway/src/compose/sandbox.ts` (`composeSandbox`, `devServerBridge`, structural `DevServerSink`); `packages/sandbox` does not import `packages/browser`. Hooking `browser.devServers` into `partsFromEnv` needs #128 (`ComposedBrowser.devServers`); that commit is written and passes against the real `DevServerRegistry`, and lands once #128 is on main.
- Tests: 7 in `packages/sandbox/test/devservers.test.ts` (fake driver; real host sockets through the forward); 3 in `apps/gateway/test/compose-sandbox.test.ts`, plus 2 more with the wiring commit. The Python probe's `/proc` decoding was checked on sample lines; it has not run in a real container (no backend was running on this machine).
- Request to S08: `DevServerRegistry.started` drops the `pid` this passes; add `pid?: number` to `DevServer` if the card or the gate should show it.

## M3 follow-up: `openStdio` for stdio MCP servers (issue #143)

Branch `ws/sandbox-stdio`. `ContainerSandboxRunner.openStdio(sandboxId, { argv, cwd, env })` returns `SandboxStdio` (raw `stdin` / `stdout` / `stderr`, `exited`, `kill`, `receipt`, `provenance: "untrusted"`).

- In-container relay `STDIO_RELAY` (Python, `-I -S`, absolute path): reads a length-prefixed env header from stdin exactly, then forks the command as a session leader that inherits the pipes directly (no copying, no PTY), records the session in a pid file for `KILL_GROUP`, and exits with the command's code (128 + signal when killed). Proven on the host with plain Python (env only in the child, byte-exact pipes, exit code, group kill of a server and its child); not run in a container locally (machine load rule), CI's M3 acceptance test does that.
- Busy like a PTY (no idle stop), `maxStdioProcesses` per scope, TERM of every group on `destroy` / `deleteWorkspace` / `dispose` before the container goes. The workspace is marked untrusted (design-07): the server is third-party code and its writes are not observed.
- `tests/integration/mcp-sandbox/vault-isolation.test.ts` now uses the runner without casts (a compile-time check that it satisfies mcp-host's `SandboxStdioHost`) and no longer skips for a missing `openStdio`.
- Not done: composing `containerLauncher({ sandbox: runner })` in the Gateway (S01 / INT, per S09's status).

## M2: egress proxy (feature K4)

Branch `ws/s21-egress-proxy`; sandbox README "Egress proxy".

- `EgressProxy` (`packages/sandbox/src/egress/`): per-scope allowlists, deny by default, CONNECT with TLS whose SNI must equal the CONNECT host, absolute-form `http://`, DNS resolved and pinned by the proxy, loopback / link-local / metadata / reserved always refused and private ranges only with `private` entries, one broker `new_origin` decision per origin per scope (cards in tainted tasks, `approval-pending` after 20 s, no duplicate cards), a receipt per first decision, a log line per connection with byte counts, `403` + `X-Proxy-Error`.
- Transport: proxy-mode sandboxes keep network `none`; `EGRESS_SHIM` on the container's `127.0.0.1:3128` multiplexes connections over `exec -i` stdio to the host. This removes the Apple `container` gap (proxy mode works on all three backends) and needs no sidecar or internal network.
- Hook: `createSandboxEgress({ broker, context, logger })` returns `egressTunnel` (runner option) and `egressAllowlist(scope, domains)` (mcp-host's `containerLauncher` option). Registering it in `apps/gateway/src/compose` is S01's (issue filed).
- Tests: 17 without containers. Policy, proxy over real local sockets with injected DNS, the real Python shim on the host carrying a CONNECT tunnel, and runner proxy mode with the fake driver. A real-container proof (pip through the proxy) is not written yet; it belongs in the CI sandbox suite.

## M3 hardening: secrets in exec (#289, #290) and reaping (#286)

Branch `ws/s21-exec-secrets`.

- #289: `EXEC_WRAPPER` no longer passes env as `env -- NAME=value` arguments, which left `setsid` and `timeout` holding every secret in `/proc/<pid>/cmdline`, and on Linux Docker hosts in the host's `ps`. Pairs go through a pipe on fd 3 to `ENV_TRAMPOLINE`, which `execvpe`s the command. The trampoline was proven on the host with plain Python: the value reaches the command and no process's argv holds it, checked by scanning `ps`. It has not run in a container here.
- #290 (runner side; the lease is S06's): after an exec with a `PSYCHE_SECRET_*` value, `REAP` kills the exec's session and every process whose environment carries its `PSYCHE_EXEC_MARK`. A failed reap stops the container.
- #286 (runner side): `reapBackground: "always"` reaps every exec of a runner. **Request to S13 / S01:** the conversion runner in `apps/gateway/src/compose/convert.ts` (`defaultRunner`, `namePrefix: "psyche-convert"`) should pass `reapBackground: "always"`, so a LibreOffice payload cannot keep a process alive between documents. Two other measures are S13's call and are not done: a fresh container per conversion (`deleteWorkspace` after each), and LibreOffice macro lockdown in `deploy/sandbox-image`.

## Measured start times (this machine)

Apple M5, 16 GB, macOS 27.0.1; Apple `container` 1.5.0; Docker 29.4.0 on OrbStack; image target `core`. Each row is one `pnpm sandbox:smoke` run. Other Psyche sessions shared the machine. Run A was taken at a high load average (about 20–40) and run B at a load average of about 7, so treat run B as the representative one.

| metric | Docker A | Docker B | Apple A | Apple B |
|---|---|---|---|---|
| cold: new volume + container + first `exec` | 1966 ms | **251 ms** | 7239 ms | **1523 ms** |
| warm: `exec true` on a running sandbox (wrapper + `filesChanged` pass) | 243 ms | **64 ms** | 377 ms | **91 ms** |
| restart: start a stopped container + `exec` | 613 ms | **142 ms** | 2041 ms | **827 ms** |
| recreate: new container on an existing volume + `exec` | 1708 ms | **218 ms** | 1892 ms | **723 ms** |

The Apple cold start includes creating the 8G ext4 volume and the one-shot root `chown` container (a second VM boot); recreating the container on an existing volume avoids both. A warm `exec` is two CLI round trips: the command, then the `filesChanged` listing. One-time costs: the first `container build` took 117 s (BuildKit VM). The uncached Docker build of `base` took about 3 minutes.

## Doc and prompt conflicts (the doc was followed)

1. **Output cap:** the prompt says 64 KB per stream; architecture §9, security §5.1 and the contract say 128 KB. I used 128 KB (`EXEC_OUTPUT_CAP_BYTES`).
2. **`outcome: "timeout"`:** the prompt lists it, but the contract has `ok | failed | uncertain` plus `timedOut`. A timeout is `timedOut: true, outcome: "uncertain", exitCode: null`, as in the fake.
3. **Objection to architecture §12 (storage layout):** it lists `sandbox/<thread-or-project>/workspace/` under `$PSYCHE_HOME`, which suggests a host bind mount. I used backend **named volumes** instead, for four reasons:
   - Security §5.1 and ADR-008 cite host-mount escapes (Cowork SharedRoot).
   - Named volumes need no host-side path or symlink validation.
   - They avoid UID mismatches on Linux hosts.
   - Apple volumes come with a size cap.

   The file API reads through the container. Proposal: drop that §12 line or describe it as "backend volume `psyche-ws-<hash>`". This is a security-motivated change, so I proceeded with it.
4. **Spike 02's suggested detection** ("`container system status` running → Docker → error") would fall through to Docker after every reboot, because the apiserver is not running at login. Instead I treat the installed CLI on macOS 26+ as available and start the service on first use (about 250 ms). That keeps ADR-008's Apple-first order.
