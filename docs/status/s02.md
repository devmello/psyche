## #509 learning about the owner into USER.md (protocol `ws/s02-user-profile-protocol` #519, implementation `ws/s02-user-profile`)

Shapes for S11:

- **Setting** `memory.userProfile`: `{enabled: boolean (default true), review: "auto" | "ask" (default "auto")}`.
- **Block** `learned` (in a `system` message after the turn): `items: LearnedFact[]`, where `LearnedFact = {factId: "lf_…", text, kind: name | preference | routine | person | project | other, date: YYYY-MM-DD, threadId}`. Render as "Learned: <text>" with an Undo button per item.
- **Undo:** `memory.forgetLearned {factId}` → `{removed}` (write).
- **`review: "ask"`:** a `memory_protected_write` card per turn's facts instead of the note; approving writes them and then posts the note.

What works:

- **agent-core:** `onOwnerTurn({threadId, runId, taskId, ownerText, taint})` fires after an attended, non-subagent turn ends (`final`, `awaiting_approval` or `awaiting_input`) and the owner typed text. It is fire-and-forget, so it never delays the turn.
- **memory (`learned.ts`, `store.learnUserFacts` / `forgetLearned`):** the one writer of the `## Learned (dated; from your chats)` section. Line format: `- YYYY-MM-DD [lf_… thread:<id> <kind>] <text>`.
  - Refuses: empty, too long, sensitive (`blockingKinds`), instruction-like, and duplicates of USER.md lines or live claims.
  - Writes through the job actor with owner provenance.
  - The health filter now also catches "insulin".
- **Gateway (`compose/user-profile.ts`):**
  - Runs only when a utility model is configured (the router always has one). The switch and incognito check come first, then the redactor, then the utility model with `LEARN_SYSTEM` (JSON, at most 5 facts).
  - `auto` writes; `ask` opens a `memory_protected_write` card first.
  - Writes are audited as `memory.user_profile.learned` (factIds and refusal reasons only). A `learned` system message is published.
  - `memory.forgetLearned` is audited as `memory.user_profile.forgotten`.
- **Scenario (`apps/gateway/test/user-profile.test.ts`):**
  - Two facts land with the thread id, and a health fact is refused.
  - The note is posted, the audit entry has no text, and Undo removes one fact.
  - With `{enabled: false}`, the learn model is not called and nothing is written.

Left for S11: the Settings switch and the "Learned: …" note with Undo, both built from the shapes above.

## Context usage, limits and auto-compaction (protocol `ws/s02-context-protocol`, implementation `ws/s02-context-usage`)

Owner priority. Protocol shapes for S11's context meter, settings and compaction markers:

- `threads.contextUsage {threadId}` → `{usage: ContextUsage | null, limits: EffectiveContextLimits, threadLimits: ContextLimits}` (read).
  - `ContextUsage`: `threadId`, `runId`, `model`, `at`, `promptTokens`, `estimated`, `breakdown {system, tools, context, history, current}`, `peakTokens`, `limits`, `compactions`. `promptTokens` is the turn's last model call: the provider's input + cache-read + cache-write tokens when reported (`estimated: false`), else the router's estimate. The breakdown is estimated per part and scaled to that total.
- `threads.setContextLimits {threadId, limits: ContextLimits | null}` (write; null clears the override).
  - `ContextLimits`: `maxTokens ≥ 1000`, `compactAt` 0.2–0.95, `keepRecentTurns` 1–20; all optional.
  - Resolution: thread → settings `context.maxTokens` / `context.compactAt` / `context.keepRecentTurns` → model. Defaults: maxTokens = the model's context window from the router, compactAt 0.8, keepRecentTurns 4. `EffectiveContextLimits` adds `contextWindow` and `maxTokensFrom` (`thread | settings | model`).
- `threads.compact {threadId}` (write, side-effecting) → `{compaction: CompactionResult | null}` (`compactionId`, `messageId`, `tokensBefore`, `tokensAfter`, `replacedTurns`). `conflict` while the thread runs or waits on an approval.
- Event `thread.context.updated {usage}` after every turn.
- Block `compaction` in a `system` message where the compaction happened: `compactionId`, `trigger: auto | manual`, `summary {facts, decisions, openTasks, pinnedInstructions}`, `replaced {turns, fromMessageId, toMessageId}`, `tokensBefore`, `tokensAfter`. The replaced turns stay in the transcript.

What works:

- **Accounting (agent-core):** each model call records the provider's input + cache-read + cache-write tokens (exact), else the estimate (`estimated: true`). The breakdown is estimated from the assembled sections (base → system, tools section + schemas → tools, persona / skills / notes / providers / plugins → context, summary → history) and the messages split at the turn's start (history / current), scaled to the total. `onContextUsage` fires after every turn that called the model.
- **Limits:** `AgentLoopOptions.contextLimits(threadId)`; `maxTokens` is capped at the model's window, `compactAt` defaults to 0.8 and `keepRecentTurns` to 4. Before a call, the loop compacts past `maxTokens × compactAt`; if the turn would still pass `maxTokens`, it ends with `context_limit` and a visible marker. Nothing is ever sent over the limit.
- **Structured compaction:** the utility model returns `{facts, decisions, openTasks, pinnedInstructions}` as JSON, merged with the previous summary. Anything else fails closed: no compaction, and the limit check decides. Turns are folded at owner-turn boundaries, never past a tool call without its result. `ThreadState.summary.structured` and `compactions` are kept; `onCompaction` reports what was replaced. `loop.compactThread(threadId)` (manual) refuses with `conflict` while a run holds the thread.
- **Gateway (`compose/context.ts`):**
  - limits from `context.thread.<id>`, then the `context.*` settings;
  - the last usage kept as `context.usage.<id>`, with `thread.context.updated` published;
  - each compaction appended as a `system` message with the `compaction` block (range of replaced message ids; those messages stay) and audited as `thread.compacted`;
  - `threads.contextUsage`, `threads.setContextLimits` (over the window → `invalid_params`) and `threads.compact` (`conflict` while running or with a pending approval in the thread).
- **Tests:**
  - agent-core `context-usage.test.ts` (7), including the scenario: 40 turns under a 4,000-token limit, at least three compactions, every call ≤ the limit, and the plan and standing instruction intact;
  - gateway `context.test.ts`: the meter, limits refused over the window, seven long turns under a thread limit with compaction markers and audit entries, and `threads.compact`;
  - the two B7 tests updated to the structured summary.
- **Not done:** S11's UI (meter, settings, markers); token counts per section are estimates scaled to the exact total (no per-section count from providers).

## #414 tool input schemas (branch `ws/s02-code-git-schema`)

Providers take a tool's input schema only as one top-level `type: "object"`; `code.git` (a `Type.Union` of operations) went out as `{anyOf: [...]}`, and Anthropic refused every request that offered it. `memory` (a union of commands) had the same shape. Fix in `defineTool` / `toJsonSchema` (`toObjectSchema`): a union of object variants is advertised as one object. The discriminator (`op`, `command`) becomes an enum whose description names each value's required fields, the other fields are optional, and a field the variants type differently keeps an `anyOf` inside the property. Any other non-object schema gets `type: "object"`. Validation still checks the exact variant, and `firstSchemaError` now reports the chosen variant's own error. Regression tests: `packages/agent-core/test/tool-schemas.test.ts` (every built-in and coding tool), `apps/gateway/test/tool-schemas.test.ts` (every tool of a composed Gateway with the coding part). MCP schemas from servers do not pass through `defineTool`; normalizing those is the model router's second line of defense.

## #307 notify to the owner (branch `ws/s02-notify-owner`)

The broker allows `notify` to the owner without a card (`owner_inbox`, S05 #329). Agent-core's part:

- The built-in's summary reads "Notify the owner: <title>" (it was "Notified: …" before anything ran).
- A per-Task notify budget (`AgentLoopOptions.notifyBudget`, default 3; per run outside a Task, so each automation fire has its own): a silent `notify` is no longer bounded by a card, so a run looping on it would flood the owner's inbox. Past the budget the loop turns the broker's allow into an ask (`notify:budget`, `once` only, the card says how many were sent). In an unattended run the card is deferred with one "Approval needed" notice, and every later call is blocked without a new card while it waits; the model is told to put the rest in its final answer. Counts live in the loop (a restart resets them).
- Tests: `packages/agent-core/test/notify-budget.test.ts` (4) and `tests/acceptance/offline/notify-budget.test.ts` (V9's automation looping six times on the real stack: three delivered via `owner_inbox`, one card for call 4, calls 5 and 6 blocked, one notice).

## V10 coding helper (M3; branches `ws/m3-v10-protocol`, `ws/m3-v10-coding`)

Plan: [docs/plans/v10.md](../plans/v10.md). Code: `packages/agent-core/src/coding/`.

**What works**

- **Workspace.** `code.open {path}` binds a repository root to the call's task (or thread). The root must be a real path (no symlink) inside a folder the owner granted (`permissions.policy.folders`); the broker's folder policy now covers `code.*` path targets, and every executor re-checks the live grant. Every other tool names the root and is refused (`forbidden`) for one its scope has not opened.
- **`code.search`** (read, untrusted): ripgrep-style regex or literal search with `-g`-style globs over the root, `path:line:text` hits; skips `.git`, `node_modules`, build output, symlinks and binaries. Nested quantifiers and backreferences are refused (a tainted pattern runs in the Gateway process).
- **`code.read`** (read, untrusted): root-relative path, numbered lines, through the P9 `read_file` executor.
- **`code.edit`** (write, `file_write`): unified diffs (git-style headers, `/dev/null` creates). Every hunk must match exactly (moved hunks are found) or nothing is written; deletes, renames, binary patches and anything under `.git` are refused; invalid patches never reach the broker. Writes go through the P9 `write_file` executor (atomic, provenance recorded) after a hash re-check. The card and the receipt carry the whole patch.
- **`code.run`** (write, `exec`): argv in the sandbox scope `project:<workspace>` with the repository bind-mounted at `/workspace/repo` and its `.git` read-only on top, so a command cannot plant hooks or config the owner's own git would run. Network `none`; `network: "proxy"` uses a separate sandbox and the K4 egress proxy, whose new origins are decided with the turn's context (`ComposedSandbox.track`). A cwd outside the root is refused: by the broker (`folder:not_granted`) when it leaves the grant, by the executor otherwise. Binding: argv, container cwd, network, repository.
- **`code.git`**: `status` / `diff` / `log` read; `commit` (stages the given paths, default all) and `branch` (`switch`, `create`) are `git_write`; `push` is `git_push`, bound to repository, remote, remote URL, branch and commit, offered `once` only and asked even under an allow rule (`git:push` floor). Before pushing, the executor checks the remote's URL and the branch tip still equal the approved ones (`binding_mismatch` otherwise); it pushes `<commit>:refs/heads/<branch>`, never forced. Git runs on the host with a fixed argv, `core.hooksPath=/dev/null`, `--no-verify`, no external diff or textconv, prompts off (a test proves a working-tree hooks path does not run).
- **Receipts**: the tools record their own (`file_write` with the diff, `exec` with exit code and files changed, `git_write` with the commit and its diff, `git_push` with commit and branch).
- **Gateway**: `apps/gateway/src/compose/coding.ts` (`composeCoding`, `hostGit`), mounted by `partsFromEnv` after the sandbox part; `code.run` only when a container backend exists; `PSYCHE_CODING=off` skips it.
- **Sandbox**: `ensureSandbox(scope, {mounts})` on the container runner: sources must be their own real path and never `/`, the home folder or an ancestor, `~/Library` or a protected root; targets under `/workspace/`; mounts are in the config label (adopted containers with other mounts are recreated) and a different mount set is a `conflict`.
- **UI**: `DiffBlock` (the kit's Markdown code block with Shiki's `diff` grammar) on `file_write` cards and under tool rows whose receipt carries a diff; `git_write` / `git_push` cards with their own rows (the commit is a row, not hidden in Details).
- **Acceptance**: `tests/acceptance/scenarios-m3/v10-coding-helper` (21/21 hard, 1/1 soft): fix a failing test in a fixture repo, `npm test` in the fake runner fails then passes, commit, the push stops at its card and lands in a bare remote after approval; a hijacked command outside the workspace is denied before any sandbox. Scorecard row V10.
- **Tests**: agent-core `test/coding.test.ts` (11), permissions `test/coding.test.ts` (4), sandbox `test/mounts.test.ts` (4), gateway `test/compose-coding.test.ts` (3), ui `test/coding-diffs.test.tsx` (5), the scenario (3).

**Decisions**

- In balanced mode, writes inside a folder the owner granted read-write are allowed without a card (`folder:rw`), so a test run, a patch and a commit in the named repository run with receipts and no card; only the push asks. A networked `code.run` in a tainted turn asks (`taint:exec_egress`).
- Repository files are untrusted (security §3.6), so opening or reading a workspace taints the turn.
- Git runs on the host, not in the sandbox: the history and the owner's push credentials live there. It is not `exec_host`: the argv is built by the tool from typed operations, never taken from the model.
- `code.*` are not loop built-ins: the Gateway registers them with its runner, file tools and git (`codingTools(deps)`).

**Not done / not verified**

- The mount flags never ran against a real container (heat rule): Docker's nested read-only bind over a read-write bind is standard; Apple `container`'s `--mount type=bind` is unverified.
- No resumability sweep for V10 yet (kill points are written in the scenario; the sweep's harness has no real-tool registrations).
- The sandbox's own file API does not see the bind mount (it reads the volume); `code.read` reads the host file instead.

## M2 follow-up (branch `ws/s02-loop-grants`)

Three slices in one PR, each tested on the real loop with the fake broker (`packages/agent-core/test/grants.test.ts`) and on the real loop + real `@psyche/permissions` broker + real connector registry (`tests/integration/compose/loop-grants.test.ts`, `requester.test.ts`).

1. **Standing grants on connector writes** (PR #86 note). The loop puts what authorized a dispatch on `ToolRunContext.authority` (protocol `ToolCallAuthority`: `rule`, `bindingHash`, `grantKey`, `approvalId`, `grantId`, `scope`). After an answered card it names the approval and the grant it created; after an `allow` by a standing grant it names the grant, which the loop re-reads from the ledger right before dispatch and fails closed on (`grant check failed`). The loop stays the single verifier and consumer of `once` approvals. `@psyche/connectors` takes `authorityFor(callId)` next to `approvalFor` and confirms a grant the way it confirms an approval: live in the ledger, keyed by the call's own `namespacedGrantKey(tool, describeCall().grantKey)`, `task`-scoped for `destructive`; a tool without a grant key can only be covered by an approval. The Gateway's `CallContexts.authorityFor` wires it. "Allow for this task" now covers the task's later sends without a card and with receipts.
2. **Requester identity** (S05 PR #89, S10 `RouteContext`). Protocol `Requester` and `StartTurnInput.requester`; `DecisionContext.requester` / `taintSources`; `ApprovalRequestInput.context`. The loop passes the requester to `decide` and on the card's context; a non-owner's text taints the turn (`channel_message`, with the sender) and never names targets. `requesterFromRoute(route)` maps S10's route; the Gateway's `SessionController.send` takes `requester` and the channels part passes it for the owner's chats (non-owner chats are still refused there until S01 carries memory injection, persona overlay and tool allowlist into a turn). `FakePermissionBroker` got `policy.designated[identityId].byTool`, per-requester grants, `requestedFor` and the requester's chats stripped from surfaces, so the matrix test runs against the fake; against the real broker the context arrives, and the matrix applies once #89 merges.
3. **Taint persistence** (S23 design-07/08). Every call's final `tool_call` event carries `details` (decision, rule, approval, `taintIn`, `taintOut`, provenance, receipt), so the Gateway's `tool_calls` rows keep taint (INT-2 noted `taintOut` was always false). `ThreadState.taint.sources` keeps the turn's sources while untrusted content stays in the transcript or summary; a new loop over the same store starts the next turn tainted with them, and cards name the original origins. `task.start` passes `taintSources`; a task run starts tainted with the task's sources (plus `task`); subagents start with the parent's sources. Protocol: `TaintSource` schema, `TaskCreateInput.taintSources`, `Task.taintSources` (fake persists them).

Handed off with failing tests in the issues: S04 must persist `Task.taintSources` in SQLite; S21 must give workspace files and `exec` results a provenance (design-07). S01 still owes a durable `ThreadStateStore` (until then a Gateway restart loses the model transcript and the thread's saved sources; the `tool_calls` rows keep per-call taint) and the rest of `RouteContext` in channel turns.

## What works (M1)

- **Loop (C1)**: `PsycheAgentLoop` implements `AgentLoop`. Steer skips the rest of the tool batch and injects guidance; follow-ups run in order when the model would stop; `finishTurn → end | continue`; all seven hooks in architecture §13 order; step and token budgets with visible markers; cancellation revokes run authority and closes dangling tool calls.
- **Tool registry (C3)**: `AgentToolRegistry` implements `ToolRegistry`; `defineTool` with TypeBox schemas (validated before the broker); `mcp__<server>__<tool>` helpers; per-tool toggles; active set by permission mode and run mode.
- **Context assembly (C2)**: base prompt → persona files (20k / 4k `USER.md` / 60k total, missing and truncated markers) → skills index → tools → yesterday's and today's daily notes → compaction summary; untrusted sections fenced and labelled. Golden file in `packages/agent-core/test/fixtures/prompt.golden.txt`.
- **Compaction (B7)**: estimate against the model's context window → `MemoryStore.flush` on a private copy (skipped for incognito threads) → `before_compaction` → utility-model summary; summaries of untrusted content stay marked untrusted.
- **Permission path and taint**: hooks → `decide` with taint and `newTarget` → approval with binding verification → receipt for write+ actions. Provenance never goes below the spec's `provenanceOut`; untrusted results, provider-executed tool results and `[untrusted]` daily-note lines taint the turn; tasks created from tainted turns pass their taint on.
- **Questions (C4)**: `ask_user` (1–4 questions, 2–4 options, header ≤12, recommended first, no explicit "Other", safe previews); attended runs park in-turn, task runs park through `TaskEngine.requestInput`.
- **Plan mode and checklist (C5)**: read-only tool set, `exit_plan_mode` → `plan_exit` approval → mode change; `update_plan` and `wrap_up` blocks.
- **Unattended contract (C8)**: `NO_REPLY` silent, empty final fails, approvals queued with a notification, `ask_user` withheld.
- **Composer commands (C9)**: `parseComposerInput` → `ComposerIntent` for all twelve commands.
- **Prompt viewer (C11)**: `explainContext(runId)`.
- Tests: 71 in `packages/agent-core/test` (scripted `FakeModelProvider` for every case in the prompt's definition of done, golden prompt, unit tests, and `security.test.ts` for the fixes from the independent security review).

## Decisions and doc notes

- The prompt says "zod → JSON Schema"; the protocol uses TypeBox, whose schemas are JSON Schema, so tools use TypeBox (no zod dependency).
- Attended approvals and questions park inside the turn; a run with a `taskId` hands its question to the task engine and ends `awaiting_input`.
- `ask_user` answers are keyed by question `header`, matching `questions.answer` in S12's protocol PR (#7).
- Hooks run before `decide` (security §3.3 puts hard prohibitions and deny rules first). Hooks can only block or suspend, and the broker still decides afterwards, so the outcome is the same; the audit order differs.
- Taint is turn-scoped in security §3.6, but a turn starts tainted while untrusted tool results or an untrusted compaction summary are still in its context: the model still reads that content. This is stricter than the doc's wording; S05 may want the doc to say so.
- Follow-ups and steers are treated as the owner's words (target matching, `user` role). The Gateway must only route owner messages through them.
- With `kind` set, `bindingHash` = `bindingHash(kind, {tool, paramsHash, fields: bindingFields})`, a superset of data model §4.2, so it always covers every argument.
- `exit_plan_mode` is the model-facing name of the `ExitPlanMode` tool in the docs (snake_case like the other built-ins).
