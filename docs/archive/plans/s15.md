# S15 plan: proactive surfaces and notifications

Owner: S15. Packages: `packages/notifications` (M1), `packages/proactive` (M2). Feature ids O5–O10.

## Goal

M1: a durable, typed notification inbox (`Notifier`) with delivery routing to the desktop/web
clients (Gateway events), the OS (mac helper `notify.show` through a `NodeClient`) and chat
channels (`ChannelAdapter`), with de-duplication, quiet hours, restart reconciliation and the
`notifications.*` handlers. M2: the interest ledger, Feed, Ideas and Goals pipelines that feed
the inbox, bounded and confirmable (architecture §2 principle 10, ADR-012).

## Steps (one PR each, stacked, each under ~800 changed lines where possible)

1. `protocol:` additive PR: `notification.updated` / `notification.resolved` events, optional
   `Notification.staleAt`, `feed.*` / `ideas.*` / `goals.*` methods and their events.
2. Notifications (M1): store interface + in-memory and SQLite stores (DDL shipped in the package
   until S01 registers the migration), routing policy, quiet hours, surface adapters, dedupe,
   reconciliation, handlers. Notifier conformance suite + routing matrix tests.
3. Interest ledger + Goals: `interests.md` parse/serialize round-trip, feedback rules with an audit
   line, derived embeddings via `ModelProvider.embed`; goals CRUD, milestones, links, check-ins
   via `Scheduler`, confirm-first inferred candidates.
4. Feed: source fetchers behind an injected `fetch`, candidate pool, URL + embedding clustering,
   recall × recency, seeded-shuffle LLM rerank, exploration slots, citation-enforced post writer,
   bounded brief, briefings via `Scheduler`.
5. Ideas: tool-sequence mining, memory/goal mining, connector signals, logistic acceptance model,
   batched delivery windows, accept → `TaskEngine` / `Scheduler`, dismissed-pattern suppression.

## Interfaces consumed

`Notifier` (implemented), `NodeClient`, `ChannelAdapter`, `Scheduler`, `MemoryStore`,
`ModelProvider`, `TaskEngine`, `Clock`; all tested against `@psyche/testing` fakes. Web fetch and
search come from S09 as injected functions (`FetchLike`, `SearchLike`), never imported.

## Risks

- `Surface` naming: the protocol says `"notification"` for OS delivery, the S15 prompt says
  `os`. The protocol wins; `os` is accepted as an alias and normalized.
- Migrations: adding `packages/db/migrations/*_notifications_*.sql` breaks `@psyche/db`'s
  schema-parity test unless `schema.ts` (S01) changes in the same PR. The SQL ships in
  `packages/notifications/migrations/` and S01 is asked to register it.
- Model-dependent steps (rerank, post writing, skill drafts) must be deterministic in tests: a
  seeded shuffle, scripted `FakeModelProvider` turns, and strict output parsing with rejection.
- Proactive content is untrusted data: source text never becomes instructions; posts without
  citations are rejected; nothing proactive contacts a third party.

## M2 (2026-10-19, branch `ws/s15-m2`): O2, O3, O5–O9 in `packages/proactive`

Order follows the spec's dependencies: goals and the migration first (ideas and watches link to
goals), then the interest ledger and the Feed, then Ideas (which turn into tasks, automations and
goal candidates), then goal watches and a budget audit.

1. **PR1 goals + budget.** One migration for every S15 table (`feed_posts`, `ideas`, `goals`,
   `goal_milestones`, `goal_links`) with its drizzle mirror (`schema-s15.ts`, S07 pattern).
   `GoalsService`: stated goals (active at once), inferred candidates (confirm-first: no automation,
   task or notification exists before `confirm`), milestones, links, archive, check-ins as system
   `cron` / `interval` automations on the real scheduler, recognised by a prompt marker and run
   in-process by `withProactiveJobs` (S07's `withDreaming` pattern), each raising at most one
   `reminder` notification. `PROACTIVITY_BUDGET` and a heartbeat launcher with a 5k-token task
   budget (O2). `goals.*` handlers; `goal.updated` events; Gateway wiring in
   `apps/gateway/src/compose/proactive.ts`.
2. **PR2 ledger + Feed (O5, O6).** `interests.md` parse / serialize with weight rules, sources
   behind an injected fetch, clustering, recall × recency, seeded-shuffle rerank through the
   utility model, exploration slots, citation-enforced posts, bounded brief and briefings as
   `briefing` automations, `feed.*` handlers, `feed.post` / `feed.updated` events.
3. **PR3 Ideas (O7, O8).** Mining of `tool_calls` sequences, memory claims and goals, connector
   signals through an injected provider; evidence, effort, logistic acceptance model over
   accept / dismiss; batched delivery windows; `ideas.accept` → Task or Automation,
   `ideas.dismiss` suppresses the pattern; `ideas.*` handlers; `idea.updated` events.
4. **PR4 goal watches (O3) + audit.** Watches linked to goals, one alert per transition (the
   scheduler already dedupes), progress on the goal page; a test that walks every proactive
   producer and asserts bounded, attributable, dismissible, and no send or write without an
   approval.

Invariants every PR keeps (architecture §2 principle 10, ADR-012, security §3): bounded batches;
every item cites evidence (`reasons`, `citations`, `evidence`, `plan.evidence`); every item can
be dismissed (`feedback`, `dismiss`, `reject`, `notifications.resolve`); the pipelines never call
a channel adapter, connector write or model tool, so nothing proactive sends or writes without
an approval (an accepted idea becomes a Task that runs under the Permission Broker).
