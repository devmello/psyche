# Plan — S01 Gateway core (2026-10-19)

## Goal

Turn the S00 skeleton into the M1 `psyched`: pairing with owner approval, scoped devices, the session controller, `threads.*` / `chat.*`, agent wiring through the `AgentLoop` contract, the node registry, `events.subscribe`, persisted idempotency, restart recovery and retention. Feature ids A2, A4 (retention), A5 (config subset), E1–E3, N14, D6 (restart part). Done per `prompts/s01-gateway-core.md`.

## Steps

1. **`protocol:` PR** (separate branch `ws/s01-protocol`, cherry-picked here until it merges):
   - `isAdminSettingKey` becomes an allowlist: every key is admin unless its root is on a short list of cosmetic roots (S23 PR-1-C).
   - `PairingRequest` gains optional `publicKeyFingerprint`, `transport`, `remoteAddress`; `devices.approve` gains optional `code` (S23 PR-1-B).
   - `threads.list` gains optional `query` (title search, E1).
   - `AgentEvent` `tool_call` gains optional `details` so the Gateway can persist a full `tool_calls` row and emit `tool_call.updated`.
2. **db**: one migration for S01's tables: pairing columns, `gateway_idempotency`, `chat_queue`, `tool_payloads`; repos for threads (rename, archive, pin, delete, fork, search, paging), messages (history paging, copy for forks), runs (status, usage, recovery), tool calls, nodes, idempotency, queue, retention.
3. **Auth** (S23 PR-1-A/B): `node.sock` accepts only `role: node`; the handshake secret auto-pairs the desktop with `operator.read|write|approvals` only, never `operator.admin`; admin comes from owner approval (`devices.approve`) or the local bootstrap command `psyched devices approve <code>`; a different key for a live pending device id is denied; requests carry the key fingerprint and transport; `devices.approve` re-checks the fingerprint. Rate limits: failed challenges 10/min/IP, pairing 5/hour/IP; a pending connection closes after the pairing TTL.
4. **Dispatch** becomes async; side-effecting results are stored in SQLite (`gateway_idempotency`) in the same transaction as the mutation where possible, and concurrent duplicates share one in-flight promise.
5. **Session controller**: per-thread state (active run + abort controller), durable follow-up queue, modes `steer | followUp | interrupt`, writer guard on every append, cancellation through `AgentLoop.cancel` + `PermissionBroker.revokeRunAuthority`.
6. **Agent wiring**: map `AgentEvent`s to `chat.delta`, `chat.block`, `chat.message`, `run.updated`, `tool_call.updated`, `approval.created`, `question.created`; commit agent messages at message boundaries and at `end`.
7. **Nodes**: registry of connected node connections implementing `NodeClient` over the node protocol; `nodes.list|capabilities|invoke` through `PermissionBroker.decide` with `approvalId` passthrough, receipts via `recordReceipt`, helper-internal capabilities unreachable.
8. **Restart recovery**: on boot, runs left `running` are failed (`gateway_restart`), writers released, tool calls `pending|running` become `uncertain`, queued follow-ups drain.
9. **Retention**: hourly job deleting `tool_payloads` older than `cleanupPeriodDays` (default 30) and expired incognito threads.
10. Tests (contract matrix from the prompt, load test with 10 threads), README, `docs/status/s01.md`, independent review subagent.

## Interfaces

Consumed through fakes: `AgentLoop`, `PermissionBroker`, `MemoryStore` (`alsoForget`), `NodeClient` (exposed by the registry). `TaskEngine`, `Notifier`, `SearchIndex` are accepted as options but have no event stream the Gateway can forward yet (see status). Exposed: the WS API in `packages/protocol`.

## Risks

- `AgentLoop.followUp` vs a Gateway-owned queue: the Gateway owns the durable queue and starts one run per follow-up; it does not call `AgentLoop.followUp` (documented for S02).
- Same-user malware can read the handshake secret and the SQLite file; capping auto-pair scopes is defense in depth, the real fix (peer code signature) needs native code (S11/S14).
- PR #1 is unmerged; everything stacks on `ws/s00-bootstrap`.
