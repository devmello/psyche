# Personal-agent capability layer for a self-hosted assistant: agentic commerce, messaging channels, self-hosted server, Gmail/Calendar, PDF document workflows, cross-device approvals (as of 2026-10-18)

Scope note: all findings below were gathered 2026-10-18 from primary docs where possible (vendor docs, GitHub repos, Apple/Google developer docs, OpenClaw docs). Secondary sources are flagged. Web-search budget ran out near the end of the session, so a handful of items are listed as gaps rather than guessed.

## Key Question 1 — Agentic commerce: protocols (ACP, AP2, UCP, Visa TAP, Mastercard Agent Pay), platforms (Instant Checkout, Amazon Buy for Me, Perplexity, Shopify, PayPal), what a self-hosted agent can do via browser vs protocols, payment-credential handling and confirmation UX, bot detection

### Takeaway
As of October 2026 the "agent pays for the user" problem has split into two layers: (a) merchant-side protocols (OpenAI/Stripe ACP, Google/Shopify UCP, AP2 mandates) that are open-spec but in practice gated to large platforms, and (b) agent-side payment credentials (Stripe Link Agent Wallet spend requests → one-time virtual card / Link Pay Token / Shared Payment Token; network programs Visa Intelligent Commerce / Mastercard Agent Pay) that a self-hosted agent can realistically use, paired with browser automation and identity signing (Web Bot Auth / Visa TAP) to avoid being blocked. ChatGPT's native Instant Checkout was deprioritized in March 2026 (discovery-in-chat, buy-on-merchant-site is the dominant pattern), and the Ninth Circuit's August 2026 Amazon v. Perplexity ruling says a user-directed browser agent is the user "accessing" the site for CFAA purposes, but merchants can still block via ToS and technical controls.

### Cited Findings

**ACP (Agentic Commerce Protocol, OpenAI + Stripe)**
- ACP is "an interaction model and open standard for connecting buyers, their AI agents, and businesses to complete purchases"; status beta; OpenAI and Stripe are Founding Maintainers; Apache-2.0; CLA required; aims for "eventual neutral foundation stewardship" — [ACP GitHub](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol)
- Date-based spec versions: 2025-09-29 initial; 2025-12-12 fulfillment; 2026-01-16 capability negotiation; 2026-01-30 extensions/discounts/payment handlers; 2026-04-17 "Cart, feed, orders, authentication, and MCP (latest stable)". Checkout OpenAPI at `spec/2026-04-17/openapi/openapi.agentic_checkout.yaml`, Delegate Payment at `openapi.delegate_payment.yaml` — [ACP GitHub](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol)
- Merchant-implemented REST endpoints: `POST /checkout_sessions` (201; requires `items`), `POST /checkout_sessions/{id}` (update), `POST /checkout_sessions/{id}/complete` (requires `payment_data` {token, provider ∈ stripe|adyen|braintree}; returns `order` with `permalink_url`), `POST /checkout_sessions/{id}/cancel` (405 if already completed/canceled), `GET /checkout_sessions/{id}`. Statuses: `not_ready_for_payment`, `ready_for_payment`, `completed`, `canceled`. Required headers: `Authorization: Bearer`, `API-Version` (e.g. 2025-09-12), `Idempotency-Key`, `Request-Id`, `Signature` (base64 signature of body), `Timestamp`. Webhooks `order_created`/`order_updated` with status ∈ created|manual_review|confirmed|canceled|shipped|fulfilled and `refunds[]`; HMAC header `Merchant_Name-Signature`. Error codes include `out_of_stock`, `payment_declined`, `requires_sign_in`, `requires_3ds` — [OpenAI ACP checkout spec](https://developers.openai.com/commerce/specs/checkout)
- Roles: Buyer, Agent (ChatGPT shows embedded checkout UI), Business (validates, computes tax, accepts/declines using risk signals), PSP ("Stripe's Shared Payment Token is the first compatible implementation"). Delegated payment: "OpenAI prepares a one-time delegated payment request with a maximum chargeable amount and an expiry"; eligible cards upgraded via network tokenization; "OpenAI is not the merchant of record". Product feed: CSV/JSON, sample then daily snapshots — [OpenAI ACP key concepts](https://developers.openai.com/commerce/guides/key-concepts)
- Stripe launch post (Sept 29, 2025): ACP powers Instant Checkout; business remains merchant of record; "payment provider relays payment credentials to the business as a secure token ... programmatically controlled, permissioned, and logged"; Stripe users can enable with "as little as one line of code"; non-Stripe merchants can still use Stripe for agentic payments — [Stripe blog](https://stripe.com/blog/developing-an-open-standard-for-agentic-commerce)
- Instant Checkout status: on March 24, 2026 OpenAI said it is "deprioritizing" Instant Checkout as a stand-alone feature, prioritizing product discovery and supporting checkout on merchants' own websites; OpenAI's blog said the initial version "did not offer the level of flexibility that we aspire to provide"; merchants can still offer checkout via apps within ChatGPT; discovery still runs on ACP data from participating merchants — [TechCrunch, 2026-03-24](https://techcrunch.com/2026/03/24/openais-plans-to-make-chatgpt-more-like-amazon-arent-going-so-well)
- Secondary analyses claim fewer than 15 Shopify merchants ever went live and that Walmart saw in-chat purchases convert at about one-third the rate of click-outs; treat as unverified — [Presenc.ai analysis](https://presenc.ai/research/chatgpt-instant-checkout-shutdown-analysis-2026); [Digital Commerce 360, 2026-03-06](https://www.digitalcommerce360.com/2026/03/06/openai-shifts-checkout-plans-agentic-commerce-strategy/)

**Stripe building blocks a self-hosted agent can actually use**
- Stripe's agentic-commerce hub lists three "build an agent" paths: Link Agent Wallet ("Let your agent pay online and access your customer's financial data"), embedded commerce, and WebMCP for browser agents; plus Shared Payment Tokens and catalog feed concepts, and UCP support — [Stripe agentic commerce](https://docs.stripe.com/agentic-commerce)
- **Link Agent Wallet**: "Your agent can request a payment credential it can safely use to transact anywhere on the internet"; CLI `npm install -g @stripe/link-cli` (handles auth, token storage, refresh, polling) or `@stripe/link-sdk` (TS) / Go SDK; calls `api.link.com`, authorizes at `login.link.com` (not the Stripe API; "Neither secret keys nor restricted API keys authenticate requests"); agent payments available to US and Canadian customers (business and sellers can be elsewhere); "Agent payments don't require a Stripe account, but registering an OAuth client gives your customers a better approval prompt" — [Stripe Link Agent Wallet](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet.md)
- Link spend-request flow: agent creates a spend request (`--amount`, `--context` ≥100 chars shown to customer, `--merchant-name/--merchant-url` for virtual cards), "The customer approves it on the Link website or in the mobile app", agent polls (`spend-request retrieve <id> --interval 2 --max-attempts 300`), "Customers have 30 minutes from the approval request to respond, after which the status becomes `expired`"; credential types: `card` (one-time virtual card number, default), `shared_payment_token`, `link_pay_token` (valid up to 30 minutes; injected into hidden `.AiAgentPaymentSteering input[name="link_pay_token"]` on Stripe-powered checkouts); statuses created → pending_approval → approved → submitted → succeeded / failed / denied / expired / canceled; `requires_action` resolutions `auto_resume` (3DS) vs create-new-request; amount increases require re-approval; `user-info retrieve` exposes `agent_wallet_spend_limits` (per_transaction/daily/thirty_day) — [Stripe: Enable agents to spend](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet/use-link-wallet-pay-online.md)
- Credential hygiene guidance from Stripe: "For hosted agents, write card details directly to a file rather than returning them to stdout, where they can persist in model transcripts and application logs" (`--include card --output-file /tmp/link-card.json`, file created 0600; stdout then carries only brand/last4/expiry) — [Stripe: Enable agents to spend](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet/use-link-wallet-pay-online.md)
- Stripe's outcome-report tags enumerate real-world blockers agents hit at checkout: `captcha`, `anti_bot_script`, `cdn_block`, `waf_block`, `dns_block`, `rate_limited`, `login_required`, `3ds_challenge`, `page_inaccessible`, `timeout`, `site_error`, `payment_declined` — [Stripe: Enable agents to spend](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet/use-link-wallet-pay-online.md)
- Link OAuth: hosted agents need a confidential OAuth client obtained via an application form; authorization-code flow at `https://login.link.com/auth` with PKCE S256 recommended; scopes `payment_methods.agentic` (required for payments), `userinfo:read`, `financial_insights.{sources,balances,transactions}.read`; access tokens `expires_in` 3600 s; refresh tokens rotate on every refresh; revoke endpoint `login.link.com/auth/revoke` — [Stripe Link OAuth](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet/oauth.md)
- **Shared Payment Tokens (SPT)**: agent collects a PaymentMethod via Payment Element, then `POST /v1/shared_payment/issued_tokens` (Stripe-Version `2026-09-30.preview`) with `seller_details[network_business_profile]`, `usage_limits[currency|max_amount|expires_at]`; seller creates a PaymentIntent with the SPT; states active / requires_action (3DS) / deactivated; revocable; webhooks `shared_payment.issued_token.{requires_action,active,used,deactivated}`; available in US, CA and ~30 European countries; supports cards, Link, Apple Pay, Google Pay, Klarna, Affirm (limited); "Stripe might use tokens issued through network programs such as Mastercard's Agent Pay and Visa's Intelligent Commerce programs on your behalf"; use is subject to Stripe's agentic-commerce preview terms — [Stripe SPT (agent variant)](https://docs.stripe.com/agentic-commerce/concepts/shared-payment-tokens.md?agent-seller=agent)
- **WebMCP**: Stripe Checkout (hosted, embedded, Elements) and hosted invoice pages register structured tools in-page so browser agents can read amount/payment methods, select a method, fill fields and submit "rather than relying on page scraping and simulating clicks"; tools must be discovered at runtime; "Stripe sets the WebMCP `consequentialHint` option for payment submission tools. Before calling a tool with this hint, get the user's confirmation"; marked experimental (proposed web standard) — [Stripe WebMCP](https://docs.stripe.com/agentic-commerce/agents/webmcp.md)

**AP2 (Google Agent Payments Protocol)**
- Announced Sept 16, 2025; open, payment-agnostic; mandates are "tamper-proof, cryptographically signed digital contracts" signed with verifiable credentials; Intent Mandate (user request / pre-authorized rules like price limits) and Cart Mandate ("exact items and price the user approved"); human-present flow: Intent Mandate then user signs Cart Mandate; human-not-present: user signs detailed Intent Mandate upfront, agent auto-generates Cart Mandate when conditions are met; works as extension of A2A and MCP; supports cards, stablecoins (via A2A x402 extension with Coinbase, Ethereum Foundation, MetaMask), real-time bank transfers; "more than 60 organizations" incl. Adyen, Amex, Coinbase, Etsy, Mastercard, PayPal, Revolut, Worldpay; accountability via "non-repudiable audit trail" of intent → cart → payment, but the post does not allocate liability — [Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)
- Repo structure: `docs/` spec, `code/sdk/python/ap2` (Pydantic models, JSON schemas), samples in Python, Go, Android using ADK + Gemini (not required); Apache-2.0; no tagged releases; install via `uv pip install git+https://github.com/google-agentic-commerce/AP2.git@main` — [AP2 GitHub](https://github.com/google-agentic-commerce/AP2)

**UCP (Universal Commerce Protocol, Google/Shopify et al.) and Google checkout**
- UCP co-developers listed: Google, Shopify, Etsy, Wayfair, Target, Walmart, Amazon, Microsoft, Meta, Salesforce, Stripe (plus lodging/food cohorts); businesses remain Merchant of Record; capabilities: catalog search, cart, checkout, identity linking (OAuth 2.0), order management, booking; payments via AP2 payment mandates and modular "payment handlers"; transports REST and JSON-RPC with MCP and A2A built in; Apache 2.0; spec at ucp.dev/latest/specification and github.com/Universal-Commerce-Protocol/ucp — [ucp.dev](https://ucp.dev/)
- Shopify's agent docs: agents authenticate via a hosted profile ("hosted at a well-known URL") referenced on every UCP request; "Higher trust tiers unlock broader access, including direct checkout completion" (others hand off to merchant storefront); Global Catalog (all merchants) vs Storefront Catalog; Cart MCP, Checkout MCP, Order MCP with `get_order` and "UCP-shaped" order webhooks covering fulfillment, refunds, returns, exchanges, cancellations; Universal Cart in early access (waitlist); tooling `@shopify/ucp-cli`, Node 18+ — [shopify.dev/docs/agents](https://shopify.dev/docs/agents); [shopify.dev/docs/ucp](https://shopify.dev/docs/ucp)
- Shopify checkout page (via search snippet): Checkout MCP "requires authentication via JWT tokens"; fallback to cart permalinks, web checkout, Checkout Kit or Embedded Checkout Protocol when buyer actions aren't supported over MCP — [shopify.dev/docs/agents/checkout](https://shopify.dev/docs/agents/checkout)
- Google announced checkout inside AI Mode and Gemini at NRF (Jan 2026) on UCP, initially for eligible US retailers paying with Google Pay (PayPal later), merchant remains merchant of record; merchants onboard via Merchant Center + UCP interest form; early access — [Retail TouchPoints](https://www.retailtouchpoints.com/news/google-launches-direct-checkout-in-search-gemini/156360/); [TechCrunch 2026-01-11](https://www.techcrunch.com/2026/01/11/google-announces-a-new-protocol-to-facilitate-commerce-using-ai-agents/); [BigCommerce guide](https://www.bigcommerce.com/articles/ecommerce/google-agentic-checkout/)

**Card networks and agent identity**
- Visa Trusted Agent Protocol (announced Oct 14, 2025) is "available today in the Visa Developer Center and GitHub"; Visa commits to aligning with IETF, OpenID Foundation, EMVCo — [Visa press release](https://usa.visa.com/about-visa/newsroom/press-releases.releaseId.21716.html)

**Web Bot Auth / merchant bot detection**
- Web Bot Auth: Ed25519 key, JWKS published at `/.well-known/http-message-signatures-directory`, requests carry `Signature-Input`, `Signature`, `Signature-Agent` headers with `keyid`, `created`, `expires`; register via Cloudflare dashboard Bot Submission Form ("Request Signature"); Cloudflare recommends ~1-minute `expires` since it does not validate nonces; test at crawltest.com; sets `cf.bot_management.verified_bot` — [Cloudflare Web Bot Auth](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/web-bot-auth/)
- "Signed agents" (Aug 28, 2025) is a verified-bot category for end-user-directed agents; founding cohort ChatGPT agent, Block's Goose, Browserbase, Anchor Browser; register via the Bot Submission Form; Enterprise customers can act on signed agents as a group — [Cloudflare blog](https://blog.cloudflare.com/signed-agents/)
- Cloudflare AI-traffic controls split traffic into Search, Agent ("automated activity acting in real time on a person's behalf, such as chat fetch bots and browser-use agents") and Training; from September 15, 2026 new domains default to blocking Training and Agent bots on ad-displaying pages; all plans including Free can manage by behavior — [Cloudflare changelog 2026-07-01](https://developers.cloudflare.com/changelog/post/2026-07-01-ai-traffic-options/)

### Inferences
- For a self-hosted personal agent, the practical purchase stack in late 2026 is: Stripe Link Agent Wallet (user approves each spend in the Link app/web within 30 minutes → one-time virtual card or Link Pay Token) + browser automation for the merchant checkout + WebMCP where the merchant uses Stripe + optional Web Bot Auth key so Cloudflare-fronted merchants can classify the agent as a signed agent. ACP/UCP checkout endpoints are merchant-facing and (per Shopify's tiering and OpenAI's merchant-only docs) not something an individual can call without platform trust.
- Confirmation UX pattern used by every leader: show line items + totals + seller, require an explicit user approval step (Link approval URL, Amazon's confirm screen, AP2 Cart Mandate signature, WebMCP `consequentialHint`), and time-box it (Link: 30 min). Record the mandate/approval as a receipt (AP2's intent→cart→payment chain is the reference model).
- Price comparison and order tracking are not solved by the payment protocols; they rely on catalog feeds (UCP/Shopify Global Catalog), merchant order webhooks (Shopify Order MCP), or parsing order emails (schema.org `Order`/`ParcelDelivery`, which many merchants do not emit).
- Bot-detection risk is rising for anonymous browser agents (Cloudflare's Sept 15, 2026 default Agent block on ad pages; Stripe's own failure tags). Running the browser on the user's own device with the user's own session (the architecture the Ninth Circuit relied on) is both the legally safer and practically more reliable path; signing requests with Web Bot Auth adds an identity merchants can allow.

## Key Question 2 — Messaging as a channel and as a tool: iMessage (BlueBubbles/imsg, chat.db, Full Disk Access, macOS 26), WhatsApp (Baileys vs Cloud API), Telegram, Signal, Slack/Discord, SMS, email; OpenClaw channel structure (pairing/allowlists, DM policy, groups, identities); voice notes and audio formats

### Takeaway
OpenClaw's channel model (per-channel `dmPolicy` of pairing/allowlist/open/disabled, pairing codes, owner identity separate from chat access, group allowlists + mention gating, per-sender session isolation) is the most complete reference for "only respond to this person." iMessage must run on a signed-in Mac with Full Disk Access (and SIP disabled for private-API features); on macOS 26 the AppleScript send path broke because chat GUIDs changed from `iMessage;-;` to `any;-;`, and OpenClaw has since replaced BlueBubbles with the `imsg` CLI. WhatsApp via Baileys is unofficial and ban-prone (Meta's Cloud API is the compliant, per-message-priced route); Telegram Bot API is the easiest fully-supported channel (voice via OGG/Opus, MP3 or M4A; inline buttons for approvals). Voice notes: Ogg/Opus mono for WhatsApp, OGG/Opus-MP3-M4A for Telegram, CAF (community reports Opus-in-CAF) for native iMessage voice bubbles.

### Cited Findings

**OpenClaw channel architecture (pairing, allowlists, identities)**
- Four DM policies: `pairing` (default; "Unknown senders get a pairing code, and the bot ignores them until approved. Codes expire after 1 hour. Pending requests are capped at 3"), `allowlist` (blocked, no handshake), `open` (requires `"*"` in allowlist), `disabled`. Group allowlists via `groups`, `groupPolicy: "allowlist"` + `groupAllowFrom` (WhatsApp, Telegram, Signal, iMessage, Teams); "Replying to a bot message does not bypass `groupAllowFrom`"; mention gating via `requireMention` and `agents.entries.*.groupChat.mentionPatterns`; `session.dmScope` ∈ main | per-channel-peer | per-account-channel-peer | per-peer; `session.identityLinks` merges one person's DMs across channels; `contextVisibility` filters quoted/forwarded context from non-allowlisted senders; `commands.allowFrom` for slash-command authorization; `openclaw security audit` — [OpenClaw access control](https://docs.openclaw.ai/gateway/security/access-control)
- Pairing codes: 8 chars, uppercase, no 0/O/1/I; expire 1 hour; max 3 pending per channel account; approve via Control UI (Settings → Channels → DM access requests) or `openclaw pairing approve <channel> <CODE>`; first approval can set `commands.ownerAllowFrom` (owner); "Manually allowlisted senders are not automatically owners"; owners can `/update`, restart, change config, approve commands; "Ownership does not grant chat access"; approvals stored in `~/.openclaw/state/openclaw.sqlite` tables `channel_pairing_requests` / `channel_pairing_allow_entries`; supported channels include discord, imessage, matrix, signal, slack, sms, telegram, whatsapp, etc.; reusable `accessGroups` referenced as `accessGroup:<name>` — [OpenClaw pairing](https://docs.openclaw.ai/channels/pairing)
- Channel catalog (31 channels + voice call): Telegram (bundled), WhatsApp (QR pairing), Signal (signal-cli native daemon or bbernhard container), Slack (Socket Mode, HTTP Request URLs, or relay), SMS (Twilio SMS/MMS webhooks), iMessage (`imsg` JSON-RPC over stdio), Discord (voice supported), Matrix, Teams, Google Chat, LINE, Nostr, WebChat (core), X/Twitter; per-account config under `channels.<channel>.accounts.<accountId>`; voice calls via Plivo/Telnyx/Twilio; email is not listed as a channel — [OpenClaw channels](https://docs.openclaw.ai/channels)

**iMessage: imsg (current OpenClaw path), BlueBubbles (legacy), chat.db, macOS 26**

## Key Question 3 — Server/self-hosted deployment: daemon patterns, web UI, auth (passkeys, OIDC, trusted-proxy), remote access (Tailscale, Cloudflare Tunnel), Docker Compose, backups, secrets; how OpenClaw, Open WebUI, LibreChat, Karakeep, Home Assistant structure self-hosting; Mac-app vs server split

### Takeaway
The dominant self-hosting pattern across OpenClaw, Open WebUI, LibreChat and Karakeep is: one long-running gateway/daemon bound to loopback inside Docker Compose, a web UI on the same port, and remote access through an identity-aware proxy (Tailscale Serve with identity headers, or Cloudflare Tunnel + Access) that the app trusts via "trusted header" auth, or OIDC against a self-hosted IdP (Pocket ID is passkey-only; Authelia offers passkeys + OIDC; LibreChat has native WebAuthn passkeys). OpenClaw formalizes the Mac-vs-server split: the Gateway (channels, agent loop, approvals) runs anywhere, while device-bound capabilities (camera, screen, notifications, computer use, exec on the Mac, iMessage via imsg) run on paired "nodes" such as the macOS menu-bar app.

### Cited Findings

**OpenClaw gateway and nodes**
- Nodes are companion devices (macOS, iOS, watchOS, Android, headless) connecting with the node role over the Gateway WebSocket; they expose `camera.*`, `device.*`, `notifications.*`, `system.*` via `node.invoke`; "Nodes are peripherals. They don't run the gateway service, and channel messages (Telegram, WhatsApp, and so on) arrive at the Gateway, not at nodes"; device capabilities (camera, screen recording, location, SMS, widget panel, computer use) run on the node under a per-platform command policy; the macOS menu bar app runs in node mode and should be the only node on that Mac — [OpenClaw nodes](https://docs.openclaw.ai/nodes)
- macOS app: requires macOS 26.2+; modes Local (Mac runs Gateway under launchd) or Remote (another host runs Gateway; Mac connects over SSH, LAN or Tailnet); provides notifications, Quick Chat, camera/screen capture, location, computer control, exec-approval prompts; supports Tailscale and Cloudflare Access sign-in; optional cookie sync to a remote browser profile (off by default); Sparkle updates — [OpenClaw macOS](https://docs.openclaw.ai/platforms/macos)
- Remote exposure: `gateway.tailscale.mode: "serve"` (tailnet-only HTTPS, Gateway stays on 127.0.0.1) or `"funnel"` (public; requires password auth, refuses to start otherwise; ports 443/8443/10000 only); `bind` ∈ loopback | tailnet | auto; `gateway.auth.mode` ∈ none | token (default) | password | trusted-proxy; Tailscale identity headers can replace the token for Control UI/WebSocket only when `gateway.auth.allowTailscale` is true; plain `ws://` is a "downgraded transport"; "Avoid Funnel for browser control. Treat node pairing like operator access" — [OpenClaw Tailscale](https://docs.openclaw.ai/gateway/tailscale)
- Trusted-proxy auth: `gateway.auth.mode: "trusted-proxy"`, `gateway.trustedProxies` (IPs/CIDRs; others rejected), `trustedProxy.userHeader` required (examples `x-forwarded-user`, `x-pomerium-claim-email`, `x-auth-request-email`), optional `requiredHeaders`, `allowUsers`, `allowLoopback` (default false), `deviceAutoApprove`; cannot coexist with a shared token; flagged "Security-sensitive"; proxy must overwrite client-supplied identity/X-Forwarded headers and the port must be firewalled — [OpenClaw trusted-proxy auth](https://docs.openclaw.ai/gateway/trusted-proxy-auth)
- Cloudflare Access: Gateway on loopback + `cloudflared` outbound tunnel; Access adds `cf-access-authenticated-user-email` and `cf-access-jwt-assertion`; configure trusted-proxy with `allowLoopback: true`, `trustedProxies: ["127.0.0.1","::1"]`, `publicOrigin`; "The Gateway does not verify the JWT signature" (presence check only); nodes use an Access service token (`CF_ACCESS_CLIENT_ID/SECRET`) or exempt `/j/*` routes; CLI/TUI via `cloudflared access login` — [OpenClaw Cloudflare Access](https://docs.openclaw.ai/gateway/cloudflare-access)
- Docker: images `ghcr.io/openclaw/openclaw:latest` (or `openclaw/openclaw`), `-browser` variants with Chromium; Control UI at `http://127.0.0.1:18789/`; health endpoints `/healthz`, `/startupz`, `/readyz` (no auth); Prometheus at `/api/diagnostics/prometheus` (auth); state volume at `/home/node/.openclaw`; secrets in Compose `.env` (`OPENCLAW_GATEWAY_TOKEN`, provider/channel tokens), `--gateway-token-ref-env` and `channels add --use-env` keep credentials out of `openclaw.json`; entrypoint runs `openclaw doctor --fix --non-interactive`, saves state snapshots under `<state-dir>.update-captures/` and SQLite `.pre-startup-migration-<id>.bak` before schema migrations; exit code 78 when state cannot be migrated safely; "For mutually untrusted users, run a separate Gateway for each trust boundary"; sandboxing off by default with docker/podman/SSH backends — [OpenClaw Docker](https://docs.openclaw.ai/install/docker)
- Exec approvals (host-command guardrail): approval requests go to "the Control UI, the macOS, iOS, and Android apps, and API clients that declare the `approvals` or `exec-approvals` capability"; macOS panel shows agent/host/command/cwd with Allow Once (⌘↩), Deny, Always Allow Here; `tools.exec.mode` ∈ deny | allowlist | ask | auto | full; `askFallback` default `deny` when no UI is reachable or prompt times out; approved runs bound to cwd, exact argv, env, executable identity; standing grants ledger with `grantExpiryDays`; CLI `openclaw approvals ...`, `openclaw exec-policy preset yolo|cautious|deny-all` — [OpenClaw exec approvals](https://docs.openclaw.ai/tools/exec-approvals)

**Open WebUI**
- Tailscale Serve sidecar: `tailscale/tailscale` container with `TS_AUTHKEY` (OAuth client with device write), `TS_SERVE_CONFIG` proxying HTTPS to `http://open-webui:8080`; identity headers `Tailscale-User-Login` (email) and `Tailscale-User-Name`; Open WebUI `WEBUI_AUTH_TRUSTED_EMAIL_HEADER=Tailscale-User-Login`, `WEBUI_AUTH_TRUSTED_NAME_HEADER=Tailscale-User-Name`; users auto-registered on first visit; restrict with Tailscale ACLs so Serve cannot be bypassed; Funnel requires auth configured first — [Open WebUI Tailscale](https://docs.openwebui.com/tutorials/auth-sso/tailscale)
- Cloudflare Tunnel: Compose with `cloudflare/cloudflared` running `tunnel --no-autoupdate run --token ...`; `WEBUI_URL` set to the public HTTPS hostname "to keep OAuth callbacks and internal links correct"; no `ports:` mapping for open-webui; tunnel service URL `http://open-webui:8080`; optional Zero Trust Access application as login gate; outbound-only connection — [Open WebUI Cloudflare Tunnel](https://docs.openwebui.com/reference/https/cloudflare-tunnel)

**LibreChat**
- OIDC providers: Auth0, AWS Cognito, Azure Entra/AD, Keycloak (plus Authelia/Authentik pages); OAuth2: Apple, Discord, Facebook, GitHub, Google; `AUTH_USER_CACHE_MODE=on` requires Redis; `DEBUG_OPENID_REQUESTS`, `OPENID_GENERATE_NONCE` — [LibreChat OAuth2/OIDC](https://www.librechat.ai/docs/configuration/authentication/OAuth2-OIDC)

- `JWT_SECRET`/`JWT_REFRESH_SECRET` auto-generated if blank; startup refuses retired published defaults; replicas must share values — [LibreChat dotenv](https://www.librechat.ai/docs/configuration/dotenv)

**Karakeep**
- Required `DATA_DIR`, `NEXTAUTH_URL`, `NEXTAUTH_SECRET` (`openssl rand -base64 36`); OIDC via `OAUTH_WELLKNOWN_URL`, `OAUTH_CLIENT_ID`, optional `OAUTH_CLIENT_SECRET` (public client = PKCE only), redirect `<NEXTAUTH_URL>/api/auth/callback/custom`, `OAUTH_AUTO_REDIRECT`; `DISABLE_SIGNUPS`, `DISABLE_PASSWORD_AUTH`; Meilisearch `MEILI_ADDR`/`MEILI_MASTER_KEY`; headless browser via `BROWSER_WEB_URL`/`BROWSER_WEBSOCKET_URL`; secrets list includes `OPENAI_API_KEY`, `SMTP_PASSWORD`, S3 keys; `PROMETHEUS_AUTH_TOKEN` regenerates each start if unset — [Karakeep configuration](https://docs.karakeep.app/configuration)

**Home Assistant (companion app model)**
- Actionable notifications: `actions` array (`action` id + `title`; optional `uri`, `behavior: textInput`, `authenticationRequired` (device unlocked; Android 12+), iOS-only `destructive`, `activationMode`); Android allows 3 actions, iOS ~10; response arrives as event `mobile_app_notification_action` with `action`, `reply_text`, `action_data`; automations use `wait_for_trigger` and should append `context.id` to action ids; dismissal fires `mobile_app_notification_cleared` on Android — [HA actionable notifications](https://companion.home-assistant.io/docs/notifications/actionable-notifications/)

**Identity providers and secrets**
- Pocket ID: self-hosted OIDC/OAuth 2.0 provider, "OpenID Connect Certified", "has no passwords" (passkeys only, multiple per user, QR cross-device sign-in), group-scoped clients, audit log, SCIM, REST API, can act as OAuth AS for remote MCP servers; single Docker container with SQLite or Postgres; BSD-2-Clause — [pocket-id.org](https://pocket-id.org/)
- Authelia: FIDO2 WebAuthn security keys as second factor, multiple credentials since v4.38.0, passwordless passkey login since v4.39.0 (still prompts for password to satisfy `two_factor` unless experimental option set) — [Authelia security keys](https://www.authelia.com/overview/authentication/security-key/)
- Docker Compose secrets: top-level `secrets` from `file:` or `environment:`, mounted per-service at `/run/secrets/<name>`; env vars "are often visible to all processes, are hard to audit, and can end up in logs"; `_FILE` convention (e.g. `POSTGRES_PASSWORD_FILE`); Linux containers only — [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

### Inferences
- Recommended reference architecture: agent core as a single daemon (Node or Python) exposing one HTTP+WebSocket port on loopback inside Compose; web UI served from the same origin; `/healthz`-style probes; state (SQLite + credentials) on one named volume; remote access via Tailscale Serve (identity headers → trusted-header auth) for personal use, or Cloudflare Tunnel + Access when phones must reach it off-tailnet; OIDC via Pocket ID (passkeys) if more than one app needs SSO. OpenClaw's rule that identity headers never authorize the HTTP API (token still required) is a good default.
- Mac vs server split (OpenClaw pattern): server runs channels, model loop, scheduler, approvals ledger; the Mac app is a paired node that executes Mac-only tools (iMessage via imsg, notifications with actions, screen/camera, local file/Quick Look/share sheet, exec approvals). Pairing should be treated as operator access (setup code with 10-minute bootstrap token, device approval list, scoped roles).
- Backups: snapshot the state volume (SQLite + credentials) before upgrades (OpenClaw's doctor captures are the model), keep channel session files (Baileys creds, signal-cli data) in the backup set because losing them forces re-pairing, and keep secrets in Compose secrets or env-ref indirection rather than in the main config file.

## Key Question 4 — Gmail & Google Calendar adapters: APIs (threads, drafts, attachments, watch/push via Pub/Sub, history sync; Calendar free/busy, events CRUD, webhooks), OAuth desktop vs web, scopes, restricted-scope verification and CASA, testing-mode limits for self-hosted deployments, token storage; alternatives (IMAP/app passwords, JMAP/Fastmail, Microsoft Graph)

### Takeaway
A self-hosted Gmail/Calendar agent can run indefinitely unverified only if the OAuth consent screen is published to "In production" (unverified apps are capped at 100 lifetime users and show the "unverified app" screen, but personal-use apps under 100 users are explicitly exempt from verification); leaving it in "Testing" expires refresh tokens every 7 days. Reading mail requires a restricted scope (`gmail.readonly`/`gmail.modify`), which triggers the annual CASA security assessment only when you seek verification. Use the Desktop client type with loopback redirect + PKCE, poll `history.list` (Google recommends polling for installed apps; Pub/Sub watch requires a GCP topic and 7-day renewals), and for Calendar use `events.watch` channels (no payload; call `events.list` with `syncToken`). Alternatives: Fastmail JMAP with user-created API tokens, Microsoft Graph subscriptions (mail/calendar max ~7 days), and IMAP/SMTP app passwords (still allowed with 2-Step Verification; Google turned off plain-password access for Workspace on March 14, 2025).

### Cited Findings

**Gmail API mechanics**
- Push: `POST https://www.googleapis.com/gmail/v1/users/me/watch` with `topicName` (`projects/{project}/topics/{topic}`), `labelIds`, `labelFilterBehavior: INCLUDE`; grant Pub/Sub publish to `gmail-api-push@system.gserviceaccount.com`; response has `historyId` and `expiration`; notification `message.data` is base64url JSON `{"emailAddress","historyId"}`; "You must call the watch method at least once every 7 days or you'll stop receiving updates" (recommend daily); rate limit one notification/sec/user, excess dropped; notifications can be delayed or dropped so fall back to periodic `history.list`; "For user-owned devices such as installed apps, mobile devices, or browsers, the page recommends polling through the sync guide instead" — [Gmail push notifications](https://developers.google.com/workspace/gmail/api/guides/push)
- Sync: full sync via `messages.list` + batched `messages.get` (`format=full|raw` for new, `minimal` for cached); partial sync via `history.list` with `startHistoryId`; history "usually kept for at least a week, often longer"; out-of-range `startHistoryId` returns HTTP 404 → full sync — [Gmail sync guide](https://developers.google.com/workspace/gmail/api/guides/sync)
- Sending: build RFC 2822 MIME, base64url into `raw`, call `messages.send` (or `drafts.send`); attachments as multipart MIME; threading requires matching `Subject` plus `References`/`In-Reply-To` headers — [Gmail sending guide](https://developers.google.com/workspace/gmail/api/guides/sending)
- Quota: per-user per-project 6,000 quota units/minute; per-project 1,200,000/minute; daily billing threshold 80,000,000 units/project (not increasable); costs: `messages.get` 20 (60 for full/raw/html), `messages.list` 5, `messages.send` 100, `drafts.create` 10, `history.list` 2, `watch` 100, `threads.get` 40 (120 full), `attachments.get` 20; 500 recipients per message — [Gmail API quota](https://developers.google.com/workspace/gmail/api/reference/quota)
- Scope classification: non-sensitive `gmail.labels`, add-on compose/message.action; sensitive `gmail.send`, add-on metadata/readonly; restricted `https://mail.google.com/` (also covers IMAP/SMTP/POP), `gmail.readonly`, `gmail.compose`, `gmail.insert`, `gmail.modify`, `gmail.metadata`, `gmail.settings.basic`, `gmail.settings.sharing` — [Gmail API scopes](https://developers.google.com/workspace/gmail/api/auth/scopes); restricted list confirmed (8 Gmail scopes; Drive 8; Fit, Chat, Data Portability, Photos Ambient, Health) — [Google restricted scopes](https://support.google.com/cloud/answer/13464325)

**Calendar API mechanics**
- Push: `events.watch` with `id` (≤64 chars), `type: web_hook`, `address` (HTTPS with valid cert; self-signed invalid), optional `token` (≤256), `expiration`; headers `X-Goog-Channel-ID`, `X-Goog-Message-Number`, `X-Goog-Resource-ID`, `X-Goog-Resource-State` (`sync` on start, `exists` on change), `X-Goog-Resource-URI`; "Notifications have no message body and don't say what changed"; no automatic renewal—create a new channel before expiry; acknowledge with 200/201/202/204/102; "Notifications aren't fully reliable, so design your app to sync even when messages are missed" — [Calendar push](https://developers.google.com/workspace/calendar/api/guides/push)
- Incremental sync: store `nextSyncToken` from a full `events.list`, pass `syncToken` on later calls; deleted entries included; HTTP 410 → clear store and full sync; sync tokens "not compatible with most filters" (400 otherwise) — [Calendar sync](https://developers.google.com/workspace/calendar/api/guides/sync)
- Free/busy: `POST /calendar/v3/freeBusy` with `timeMin`, `timeMax` (RFC3339), `timeZone`, `items[].id`, `calendarExpansionMax` ≤50, `groupExpansionMax` ≤100; response `calendars{}.busy[]{start,end}`; scopes `calendar.readonly`, `calendar`, `calendar.events.freebusy`, `calendar.freebusy` — [freebusy.query](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query)
- Events: `events.insert(calendarId, event)` requires only `start`/`end` (`dateTime` or all-day `date`); `sendUpdates` `all`/`externalOnly` emails attendees; Meet via `conferenceDataVersion=1` and `conferenceData.createRequest{requestId}` with type `hangoutsMeet`; reminders overrides (`email`/`popup`, minutes); `recurrence: ["RRULE:..."]`; `events.patch` for partial updates; edit scope `https://www.googleapis.com/auth/calendar` — [Calendar create events](https://developers.google.com/workspace/calendar/api/guides/create-events)

**OAuth client types, publishing status, verification**
- Desktop/native apps: loopback redirect `http://127.0.0.1:port` "the recommended mechanism"; custom URI schemes "no longer supported due to the risk of app impersonation"; OOB copy/paste deprecated; "Always use PKCE" (S256); desktop clients "cannot keep secrets confidential" (client_secret optional); refresh tokens "always returned for installed apps" and valid until revoked/expired; issuance limited per client/user; store tokens in durable secure storage (hardware-backed keys if DPoP) — [Google OAuth for native apps](https://developers.google.com/identity/protocols/oauth2/native-app)
- Publishing status: Testing "limited to up to 100 test users"; test users see a warning and "their authorizations expire seven days after consent. Refresh tokens also expire" (exception: apps requesting only email/profile/openid); In production "available to any user with a Google Account"; "Unverified apps that request unapproved sensitive or restricted scopes are capped at 100 new users in total ... over the project's lifetime and can't be reset"; internal (Workspace org) apps bypass — [Google OAuth publishing status](https://support.google.com/cloud/answer/15549945)
- Unverified-app screen appears when the app uses sensitive/restricted scopes without verification, requests scopes different from the consent-screen configuration, or verification is pending; such apps are "limited to 100 new users until it is verified" — [Google unverified apps](https://support.google.com/cloud/answer/7454865)
- Verification not needed: "If the app is for your personal use (fewer than 100 users)" (users click through the warning); apps "in development/testing/staging mode"; service-account-only data; internal Workspace apps; admin-trusted/Marketplace admin-installed apps; the 100-user cap "is removed only after an app has been successfully verified" — [Google: when verification is not needed](https://support.google.com/cloud/answer/13464323)
- Verification overview: sensitive and restricted scopes require OAuth app verification; restricted scopes require annual re-verification; non-sensitive-only apps need only "brand-verification" to show name/logo — [Google verification overview](https://support.google.com/cloud/answer/13463073)
- Security assessment: required annually for restricted scopes as the final step of restricted-scope review; uses App Defense Alliance CASA (OWASP ASVS-based) with assurance levels AL1/AL2 assigned by user count, scopes and signals; passing yields a Letter of Validation; "Every app must be revalidated yearly" — [Google security assessment](https://support.google.com/cloud/answer/13465431)
- Secondary cost/time estimates (vendor sources, treat cautiously): self-serve CASA Tier 2 roughly $540–$1,000 and 4–8 weeks — [Unipile](https://www.unipile.com/integrating-google-oauth-2-0-user-authentication-into-your-app/); Google FAQ cited as ~six weeks with yearly redo — [Agentic Fabriq](https://www.agenticfabriq.com/blog/google-oauth-verification-casa); example approval Sept 13, 2026 after CASA Tier 2 (AL1) by TAC Security — [CellCog](https://cellcog.ai/blog/casa-security-assessment/); Nylas lists the 8 restricted Gmail scopes and annual revalidation — [Nylas guide](https://developer.nylas.com/docs/provider-guides/google/google-verification-security-assessment-guide/)

**Alternatives**
- Google app passwords: 16-digit passcodes usable only with 2-Step Verification on; option hidden for security-key-only 2SV, some org accounts, or Advanced Protection; Google says they "aren't recommended and are unnecessary in most cases" — [Google app passwords](https://support.google.com/accounts/answer/185833)
- Workspace LSA shutdown: from March 14, 2025 "Access to less secure apps will be turned off for all Google Accounts"; CalDAV, CardDAV, IMAP, SMTP, POP no longer work with legacy passwords; OAuth replaces them "with the exception of app passwords" (suggested for SMTP devices) — [Google Workspace LSA transition](https://knowledge.workspace.google.com/admin/sync/transition-from-less-secure-apps-to-oauth)
- Fastmail: JMAP session endpoint `https://api.fastmail.com/jmap/session`; `Authorization: Bearer {token}`; personal API tokens under Settings → Privacy & Security → Manage API tokens; apps for others should use OAuth 2.0 (clients registered manually; authorize `https://api.fastmail.com/oauth/authorize`); scopes `urn:ietf:params:jmap:core`, `:mail`, `:submission`, `:vacationresponse`, `:contacts`, masked email; JMAP calendars "as soon as the specification is finalized" (CalDAV meanwhile); CORS enabled; RFCs 8620/8621/9610 — [Fastmail for developers](https://www.fastmail.com/dev/)
- Microsoft Graph: change notifications for `/me/messages`, `/me/mailFolders('inbox')/messages`, `/me/events`, `/me/contacts` with max subscription lifetime 10,080 minutes (under seven days; 1,440 minutes for rich notifications with resource data); max 1,000 active subscriptions per mailbox; delivery via webhooks, Event Hubs, Event Grid; basic notifications carry only ids; lifecycle notifications warn before expiry; delta query is the polling alternative; mail latency <1 min average — [Microsoft Graph change notifications](https://learn.microsoft.com/en-us/graph/change-notifications-overview)

### Inferences
- For a self-hosted single-user agent the cheapest compliant configuration is: Desktop OAuth client, consent screen set to External + In production (not Testing), request `gmail.modify` (or `gmail.readonly` + `gmail.send`) and `calendar`, accept the unverified-app interstitial once, and rely on the explicit "personal use (fewer than 100 users)" exemption. Do not pursue CASA unless distributing to others.
- Token storage: refresh tokens for In-production apps persist until revoked (or ~6 months unused per Google's general policy); store encrypted at rest (Keychain on the Mac node, or an encrypted file/secret on the server), and expect per-client refresh-token issuance limits when re-consenting repeatedly.
- Sync design: poll `history.list` every 1–5 minutes with the saved `historyId` (2 quota units per call) rather than standing up Pub/Sub; for Calendar use `events.list` with `syncToken` on a timer, optionally with `events.watch` through the public tunnel; always handle 404/410 by resyncing.
- If the user is on Fastmail, JMAP with a personal API token avoids the whole Google verification question; Outlook users get webhook-style subscriptions via Graph but must renew weekly.

### Gaps
- Google's documentation does not state a precise refresh-token lifetime for In-production apps on the fetched pages (the 6-month inactivity expiry is referenced only indirectly in search summaries).
- Exact CASA costs/timelines are not published by Google; all figures are vendor estimates.
- Gmail message size limits (35 MB) and resumable upload details were not on the fetched sending page.
- Microsoft Graph app-registration requirements for personal Microsoft accounts were not captured.

## Key Question 5 — Document workflows: email attachment → PDF, detecting AcroForm vs XFA, filling (pdf-lib, PyMuPDF, pdftk, Apple PDFKit), flattening, OCR (Apple Vision, Tesseract, docTR), reviewed reply + receipt, in-app viewing (PDF.js, PDFKit), sharing/export (share sheet, AirDrop, Quick Look)

### Takeaway
AcroForm filling is well served by pdf-lib (JS, any runtime, `getForm()` + `flatten()`), PyMuPDF (Python; `is_form_pdf`, `Widget.update()`, `Document.bake()` to flatten) and pdftk (`fill_form`/`flatten`/`need_appearances`); XFA forms are the exception—pdftk's `drop_xfa` discards XFA, PDF.js can only render pure-XFA, and none of the fetched libraries fill XFA natively. On the Mac, PDFKit gives native viewing (`PDFView`), widget editing (`PDFAnnotation.widgetStringValue`, `buttonWidgetState`) and flattening/encryption on write (`burnInAnnotationsOption`, password options), while Vision provides on-device OCR (`VNRecognizeTextRequest` since macOS 10.15; structured `RecognizeDocumentsRequest` with tables/lists on macOS 26). Share via `NSSharingServicePicker` (AirDrop/Mail/Messages) and preview via `QLPreviewPanel`.

### Cited Findings
- pdf-lib: reads/fills existing fields via `PDFDocument.getForm()` with `getTextField`, `getCheckBox`, `getRadioGroup`, `getDropdown`, `getButton` and setters `setText`, `check`, `uncheck`, `select`; creates fields (`createTextField`, etc.) and `form.flatten()`; custom fonts require `@pdf-lib/fontkit` registration; pure TypeScript/JS with no native deps, runs in browsers, Node, Deno, React Native; page does not mention XFA, encryption or rendering support — [pdf-lib.js.org](https://pdf-lib.js.org/)
- PyMuPDF widgets: `field_name` (dots create hierarchy), `field_type` 0–6 with constants `PDF_WIDGET_TYPE_TEXT/BUTTON/CHECKBOX/COMBOBOX/LISTBOX/RADIOBUTTON/SIGNATURE` (signature read-only), `field_value`, `field_flags`, `choice_values`, `on_state()`; "After any change, you must call `update()`"; iterate with `Page.first_widget`/`Widget.next`; reload page after changes — [PyMuPDF Widget](https://pymupdf.readthedocs.io/en/latest/widget.html)
- PyMuPDF document: `Document.is_form_pdf` returns "False if this is not a PDF or has no form fields, otherwise the number of root form fields"; `Document.bake(annots=True, widgets=True)` converts annotations/widgets "to become permanent parts of the pages" ("the document will also no longer be a 'Form PDF'"; underlying data lost); `Document.need_appearances(value=None)` gets/sets `/NeedAppearances`; XFA not mentioned — [PyMuPDF Document](https://pymupdf.readthedocs.io/en/latest/document.html)
- pdftk: `fill_form` from FDF/XFDF/stdin; `flatten` merges fields into page content (single input); `need_appearances` makes Reader regenerate appearances (recommended for non-ASCII; incompatible with `flatten`); `drop_xfa` omits XFA data (Acrobat 7/Designer forms filled by pdftk may fail to display without it); `generate_fdf`, `dump_data_fields(_utf8)`; GPL — [pdftk man page](https://www.pdflabs.com/docs/pdftk-man-page/)
- Apple PDFKit `PDFAnnotation` (macOS 10.4+, iOS 11+): widget properties `widgetFieldType` (button/choice/text), `widgetStringValue`, `widgetDefaultStringValue`, `fieldName`, `isReadOnly`, `widgetControlType` (radio/push/checkbox), `buttonWidgetState` (on/off/mixed), `buttonWidgetStateString`, `choices`, `values`, `isListChoice`, text-widget `isMultiline`, `maximumLength`, `hasComb`; markup (`markupType` highlight/strikethrough/underline/redact), ink (`paths`), stamp, free text; subclasses `PDFAnnotationTextWidget`, `PDFAnnotationButtonWidget`, `PDFAnnotationChoiceWidget` — [Apple PDFAnnotation](https://developer.apple.com/documentation/pdfkit/pdfannotation)
- PDFKit write options: `ownerPasswordOption`, `userPasswordOption` (encryption), `accessPermissionsOption`, `burnInAnnotationsOption`, `saveTextFromOCROption`, `saveImagesAsJPEGOption`, `optimizeImagesForScreenOption` — [Apple PDFDocumentWriteOption](https://developer.apple.com/documentation/pdfkit/pdfdocumentwriteoption)
- `PDFView` (macOS 10.4+, iOS 11+) handles display, selection, navigation, zoom, copy, page history; `isInMarkupMode`, `pageOverlayViewProvider`, `findInteraction`; notifications for page/scale/selection/annotation hits — [Apple PDFView](https://developer.apple.com/documentation/pdfkit/pdfview)
- PDF.js: Apache-2.0, "PDF Reader in JavaScript", modern and legacy builds, built into Firefox; prebuilt viewer and `pdfjs-dist` npm — [mozilla/pdf.js](https://github.com/mozilla/pdf.js); API: `annotationStorage` ("Storage for annotation data in forms"), `saveDocument()` returns the saved document bytes, `getFieldObjects()` (AcroForm field data), `hasJSActions()`, `isPureXfa` ("True if only XFA form"), `allXfaHtml` mainly for printing XFA — [PDF.js PDFDocumentProxy](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFDocumentProxy.html); FAQ: supports adding "a subset of the possible annotation types"; Safari 18+/Node 22+ "Mostly" supported on legacy build — [PDF.js FAQ](https://github.com/mozilla/pdf.js/wiki/Frequently-Asked-Questions)
- Apple Vision OCR: `VNRecognizeTextRequest` (macOS 10.15+, iOS 13+) with `recognitionLevel` (fast/accurate), `recognitionLanguages`, `automaticallyDetectsLanguage`, `usesLanguageCorrection`, `customWords`, `minimumTextHeight`, revisions 1–3, results `VNRecognizedTextObservation` — [Apple VNRecognizeTextRequest](https://developer.apple.com/documentation/vision/vnrecognizetextrequest); `RecognizeDocumentsRequest` (macOS/iOS 26.0+) "scans a document and extracts different groups of text and barcodes" for receipts, labels, forms; returns `DocumentObservation` grouped by words/lines/paragraphs plus tables and lists; `textRecognitionOptions`, `barcodeDetectionOptions`, `supportedRecognitionLanguages` — [Apple RecognizeDocumentsRequest](https://developer.apple.com/documentation/vision/recognizedocumentsrequest); the open-source `mac-ocr` CLI exposes macOS 26 document recognition as JSON (paragraphs, tables, lists, geometry) — [privatenumber/mac-ocr](https://github.com/privatenumber/mac-ocr)
- Tesseract: v5 line (since Nov 2021), LSTM engine from v4, "more than 100 languages", outputs text/hOCR/PDF/TSV/ALTO/PAGE, Apache 2.0; image quality strongly affects results — [tesseract-ocr/tesseract](https://github.com/tesseract-ocr/tesseract)

- Gmail attachments arrive as MIME parts fetched via `messages.attachments.get` (20 quota units) — [Gmail API quota](https://developers.google.com/workspace/gmail/api/reference/quota)

### Inferences
- Detection pipeline: open with PyMuPDF; `is_form_pdf` > 0 means AcroForm; additionally inspect the catalog `/AcroForm` dictionary for an `/XFA` key (PyMuPDF `xref_get_key`) or use PDF.js `isPureXfa`; if XFA, either hand to the user (Acrobat) or `pdftk drop_xfa` only when an AcroForm fallback exists in the same file.
- Fill → review → flatten: fill widgets (pdf-lib on the server, PDFKit on the Mac), set `/NeedAppearances` or regenerate appearances for non-Latin text, render a preview (PDF.js in the web UI or `PDFView` natively) for the user's approval, then flatten (`form.flatten()`, `Document.bake()`, pdftk `flatten`, or PDFKit `burnInAnnotationsOption`) and attach to the reply draft via Gmail `drafts.create`.
- OCR choice: Apple Vision on the Mac node for scanned attachments (free, on-device; `RecognizeDocumentsRequest` for tables on macOS 26), docTR/Tesseract on a Linux server; keep OCR text alongside the PDF (`saveTextFromOCROption` on PDFKit) so the agent can quote fields in its receipt.
- A "receipt of actions" can be a small flattened PDF/Markdown summary generated with pdf-lib (fields set, values, source email id, timestamps) and stored with the audit log.

### Gaps
- No primary source captured that explicitly states "XFA unsupported" for pdf-lib or PyMuPDF (the pdf-lib site does not mention XFA; PyMuPDF document page omits it); the XFA limitation is inferred from pdftk's `drop_xfa` semantics and PDF.js's pure-XFA rendering note.
- PDF.js page-render options (`annotationMode`, `renderForms`) and annotation-editor list were not in the fetched API page.
- PDFKit `PDFDocumentWriteOption` availability versions per option were not shown.
- No Apple docs fetched for AirDrop-specific `NSSharingService.Name.sendViaAirDrop` or iOS `UIActivityViewController`.

## Key Question 6 — Approvals and notifications across devices: "needs approval" pushes (desktop notification with actions, phone approval via companion app or Telegram/iMessage), timeouts, audit log/receipts

### Takeaway
Production agents converge on the same approval loop: a pending-approval record with an id, a human-readable summary (what/where/how much), delivery to one or more surfaces (Telegram inline buttons, iMessage poll/tapback, Mac notification actions or an app panel, Home Assistant actionable notifications), an explicit timeout with deny-by-default, and binding of the approval to the exact operation (argv/cwd/env, cart contents, amount) so a late or replayed approval cannot authorize something different. OpenClaw (30-minute chat approvals, `askFallback: deny`, standing grants with expiry, per-run binding) and Stripe Link (30-minute approval window, re-approval on amount increase, idempotency keys) are the clearest reference implementations.

### Cited Findings
- OpenClaw Telegram exec approvals: prompts go to approver DMs by default (`execApprovals.target` dm|channel|both), `enabled: "auto"` when an approver resolves, inline buttons require `capabilities.inlineButtons`, "Exec approvals expire after 30 minutes by default", approvers must be numeric Telegram user IDs (fallback to owner ids), `allowFrom`/`groupAllowFrom` "do not grant approval rights"; callback clicks are timestamped at receipt and pass through normal authorization — [OpenClaw Telegram rich messages](https://docs.openclaw.ai/channels/telegram/rich-messages)
- OpenClaw iMessage approvals: native Messages poll with one option per allowed decision (requires imsg poll support; iOS/macOS 26+ to vote natively), text fallback 👍 = allow-once, 👎 = deny, `/approve <id> <decision>`; tapbacks on the prompt resolve it; only handles in `channels.imessage.allowFrom` can approve; after gateway restart old controls are ignored and a new approval must be requested — [OpenClaw iMessage rich messages](https://docs.openclaw.ai/channels/imessage/rich-messages); Signal supports only 👍/👎 approval reactions — [OpenClaw Signal](https://docs.openclaw.ai/channels/signal)
- OpenClaw core approval semantics: requests go to connected approval clients (Control UI, macOS/iOS/Android apps, API clients declaring `approvals` capability); macOS panel shows agent, host, command, cwd with Allow Once / Deny / Always Allow Here; `askFallback` (default `deny`) decides when no UI is reachable or the prompt times out; "Approved runs are bound to cwd, exact argv, env (when present), and resolved executable identity. Changes during the approval window deny the run"; reused Allow-Once approvals and late approvals after the turn closes are rejected; automation (cron) approvals with no connected surface are denied immediately; standing grants mint scoped grants tied to agent, job config and exact operation, expire via `grantExpiryDays`, and are listed in a ledger with use counts and state; audit artifacts are allowlist metadata (`addedAt`, `lastUsedAt`, `lastUsedCommand`, `lastResolvedPath`), the grant ledger and `Exec finished/denied (gateway id=...)` lifecycle messages correlated by approval id; Matrix uses ✅/♾️/❌ reaction shortcuts — [OpenClaw exec approvals](https://docs.openclaw.ai/tools/exec-approvals)
- Apple actionable notifications: declare `UNNotificationCategory` with `UNNotificationAction` / `UNTextInputNotificationAction` at launch (options such as `destructive`, `authenticationRequired`, `foreground`); set `categoryIdentifier` on `UNMutableNotificationContent` (or `aps.category` for remote); "When the user selects an action, the system launches your app in the background" and calls `userNotificationCenter(_:didReceive:withCompletionHandler:)` with `response.actionIdentifier`; action identifiers must be globally unique; files protected with complete protection may be unavailable if the device is locked — [Apple: Declaring actionable notification types](https://developer.apple.com/documentation/usernotifications/declaring-your-actionable-notification-types)
- Home Assistant companion: `actions` with `authenticationRequired` (unlocked device), `destructive` (iOS), text input; Android max 3 actions, iOS ~10; response event `mobile_app_notification_action` with `action`/`reply_text`; use `wait_for_trigger` plus a timeout, and unique per-run ids (`'APPROVE_' ~ context.id`); Android `mobile_app_notification_cleared` on dismissal — [HA actionable notifications](https://companion.home-assistant.io/docs/notifications/actionable-notifications/)
- Stripe Link spend approval UX: customer approves at `approval_url` in the Link app/web; "Customers have 30 minutes from the approval request to respond"; `--context` (≥100 chars) plus `--line-item`/`--total` define what the customer sees; raising the amount requires re-approval; `--idempotency-key` per purchase intent; statuses `denied`/`expired` require a new request; `agent_wallet_spend_limits` (per_transaction/daily/thirty_day) checkable up front — [Stripe: Enable agents to spend](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet/use-link-wallet-pay-online.md)
- Stripe WebMCP marks payment-submission tools with `consequentialHint` and instructs agents to obtain user confirmation first and never treat the hint as consent — [Stripe WebMCP](https://docs.stripe.com/agentic-commerce/agents/webmcp.md)
- AP2 defines the receipt model: signed Intent Mandate → Cart Mandate ("what you see is what you pay for") → payment, forming a "non-repudiable audit trail" to answer authorization, authenticity and accountability — [Google AP2 blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)
- ACP requires `Idempotency-Key` and `Request-Id` headers on every checkout call and a `Signature` over the body; webhooks carry order status transitions (`manual_review`, `confirmed`, `shipped`, `fulfilled`) and refunds — [OpenAI ACP checkout spec](https://developers.openai.com/commerce/specs/checkout)
- Amazon Buy for Me inserts an explicit confirmation step (address, taxes, shipping, payment) before the agent completes checkout on the brand site; tracking and brand confirmation email serve as the receipt — [About Amazon](https://www.aboutamazon.com/md/news/retail/amazon-shopping-app-buy-for-me-brands)
- LangGraph interrupts: `interrupt()` pauses the graph and persists state via a checkpointer under a `thread_id`; resume with `Command(resume=...)`; patterns approve/reject, edit tool args, review output; "waits indefinitely until you resume execution" (no built-in timeout) — [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Telegram inline keyboards (`InlineKeyboardMarkup` on messages; `disabled` button field added) are the Bot API primitive OpenClaw uses for approval buttons — [Telegram Bot API](https://core.telegram.org/bots/api)
- OpenClaw node/device pairing itself is an approval flow: setup codes are base64 JSON with a single-use bootstrap token expiring after 10 minutes; pending device requests expire after 5 minutes; approvals via Control UI or `openclaw devices approve <requestId>` — [OpenClaw pairing](https://docs.openclaw.ai/channels/pairing)

### Inferences
- Approval object schema worth copying: `{id, kind (exec|purchase|send_email|send_message|fill_form), summary, details (argv/cwd or cart/amount/merchant or recipient/subject), requested_at, expires_at (default 30 min), approvers[], surfaces[], decision, decided_by, decided_at, binding_hash}`; deny on expiry; reject if `binding_hash` changes; one-time approvals cannot be reused.
- Fan-out: send the same approval to the Mac (notification with Approve/Deny actions and `authenticationRequired` for purchases) and the phone (Telegram inline buttons, or iMessage poll/👍) and accept the first authorized answer; always keep a web-UI fallback because chat callbacks can be lost on restarts (OpenClaw explicitly invalidates stale controls).
- Receipts: write an append-only audit log entry per action with the approval id, the exact operation, the external references (Stripe spend request id / order id / Gmail message id), and attach a human-readable receipt (message to the owner, optionally a PDF) — mirroring AP2's mandate chain and OpenClaw's lifecycle messages.

### Gaps
- No primary source captured on ChatGPT agent / Operator confirmation UX (OpenAI pages returned 403); their "ask before consequential actions / watch mode / takeover for payments" patterns are not cited here.
- No documentation found on macOS limits for the number of notification actions displayed or on cross-device "approve on iPhone for Mac action" mechanisms beyond OpenClaw's apps.
- OpenClaw does not document a dedicated audit log file; only ledger/metadata/lifecycle messages were documented.
