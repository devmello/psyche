## Key Question 1 — "opendots": what it is, who makes it, what it imitates, architecture, stack, data model, review flow, receipts, roadmap

### Takeaway
The described project is **CopilotKit/openmuse (OpenMuse)**: an MIT-licensed, alpha, single-owner "personal agent with a browser, terminal, files, and work that keeps going," built by CopilotKit (Tawkit, Inc.) on CopilotKit React Native + AG-UI, with a Hono API + CopilotKit runtime, a durable SQL task engine (PGlite/PostgreSQL) using leases and stored action reviews/receipts, a token-protected Playwright/Chromium worker, an optional nonroot Docker "computer," reviewed Gmail/Calendar adapters, and conversation persistence outsourced to the hosted (non-OSS) CopilotKit Intelligence service. It was created 2026-09-15, one week after Meta launched its "Muse" personal agent; CopilotKit's own docs never name the product it mirrors, so the Meta Muse mapping is an inference. CopilotKit/OpenDots (created 2026-09-29, the day OpenAI announced Dots) is the explicitly named "open-source alternative to OpenAI Dots."

#### 1e. Data model and persistence
- "By default, embedded PGlite, documents and the signing key live in `.openmuse/`; browser profiles live in `.openmuse/browser-profiles/`." — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md)
- Durable work: "Server-owned jobs, plans, checkpoints, leases, retries, cancellation, and action receipts." (ROADMAP "Shipped locally") — [ROADMAP.md](https://github.com/CopilotKit/openmuse/blob/main/ROADMAP.md); tests cover "Real PGlite restart, two-worker lease races, expired-lease recovery, cancellation, pause/resume, missing inputs, approval fairness, and saved outcomes" — [docs/VERIFICATION.md](https://github.com/CopilotKit/openmuse/blob/main/docs/VERIFICATION.md)
- Conversation history is **not** in the app's DB: "Chat threads are stored by CopilotKit Intelligence, so a thread can still load after you sign back in even when the disk was never attached." — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md)
- Rich tool messages reference server records rather than embedding them: "Rich tool messages retain task IDs. The renderer fetches current task status, browser previews, PDF links and structured artifacts from the authenticated task endpoint. Expiring file/preview URLs are generated by the server rather than stored in thread messages." — [docs/RICH-THREADS.md](https://github.com/CopilotKit/openmuse/blob/main/docs/RICH-THREADS.md)
- Idempotency/uncertainty: "No hidden retry occurs after an uncertain external write. Review its provider outcome before creating a replacement. Pausing/cancelling prevents subsequent task steps; an already approved in-flight provider request may finish." — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md)
- Identity boundary: "This deployment uses one owner protected by a shared access key; it is not a multi-tenant authentication system." Google credentials "are encrypted at rest. File URLs and browser consoles use short-lived signatures." Live mode requires `OPENMUSE_ACCESS_KEY` (≥24 chars) and `TOKEN_ENCRYPTION_KEY` (32 random bytes, base64) — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md)

#### 1g. The "receipts" concept
- Receipts are persisted records of what the agent actually did, attached to tasks: "saved command receipts" (terminal), "approvals, and saved receipts" (Activity), "receipt" as the terminal step of the Documents pipeline — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md)
- Command receipts: "Commands have a 30-second limit and saved output/exit receipts." "The server records output, status, and exit codes." "Interrupted work is recorded with an uncertain outcome and is never a[utomatically replayed]" (sentence truncated in fetch) — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md); [SECURITY.md](https://github.com/CopilotKit/openmuse/blob/main/SECURITY.md)
- Desktop action receipts (E2B provider): "Each action is recorded next to the commands, for example `desktop left_click (640, 400)`, and the latest screenshot is kept per owner" — [docs/COMPUTER.md](https://github.com/CopilotKit/openmuse/blob/main/docs/COMPUTER.md)
- The acceptance test for chat shows the pattern end-to-end: the agent can "call server tools including a computer command, persist its receipt, save a plan, prepare an event, wait for approval, and resume from the receipt." — [docs/VERIFICATION.md](https://github.com/CopilotKit/openmuse/blob/main/docs/VERIFICATION.md)

#### 1h. Agent computer / sandbox: what is done and what is not
- Container hardening (verbatim): "The container runs as UID/GID 1000 with a read-only root filesystem, all capabilities dropped, no added privileges, and Docker networking set to `none`. It receives no host directory mounts, Docker socket, model keys, Google tokens, or API access key. Limits are 512 MB RAM with no swap, one CPU, 128 processes, and 64 MB of temporary storage." — [SECURITY.md](https://github.com/CopilotKit/openmuse/blob/main/SECURITY.md)
- Command bounds: "Commands have a 30-second container timeout, a 2-second kill grace, a 35-second Docker-client timeout, and a combined 128 KB output cap." File API: "stays inside `/workspace`, rejects symlink traversal and special files, and uses atomic text replacement. Text reads/writes are limited to 256 KB; PDF import/export is limited to 10 MB" — [SECURITY.md](https://github.com/CopilotKit/openmuse/blob/main/SECURITY.md)
- Host-shell prohibition: "The API launches only the fixed Docker CLI with argument arrays; user commands are passed to bash inside the container. It never falls back to a host shell." — [SECURITY.md](https://github.com/CopilotKit/openmuse/blob/main/SECURITY.md); "If Docker is unavailable, the app reports the connection error. There is no fallback that executes commands on the API host." — [docs/COMPUTER.md](https://github.com/CopilotKit/openmuse/blob/main/docs/COMPUTER.md)
- Not an interactive terminal: "The terminal runs bounded commands and displays their saved results. It is not an interactive PTY: full-screen terminal apps and prompts that require ongoing keyboard input are not supported." — [docs/COMPUTER.md](https://github.com/CopilotKit/openmuse/blob/main/docs/COMPUTER.md)
- Explicit limits: "Docker shares its host kernel and does not provide a full VM or a hostile-tenant guarantee. The persistent volume has no portable per-volume disk quota; provision and monitor Docker storage separately." — [SECURITY.md](https://github.com/CopilotKit/openmuse/blob/main/SECURITY.md); "Graphical desktops and autonomous checkout remain future work." — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md)
- Optional isolation upgrade on macOS: Colima VM profile (`colima start openmuse --cpus 2 --memory 3 --disk 12 ... --vm-type vz`) — [docs/COMPUTER.md](https://github.com/CopilotKit/openmuse/blob/main/docs/COMPUTER.md)
- Optional E2B Desktop provider (`COMPUTER_PROVIDER=e2b-desktop`): a Linux VM with Xfce, Firefox ESR, Chrome, LibreOffice; adds a `use_desktop` tool that "mirrors the shape of Anthropic's computer-use tool" (screenshot, left/double/right click, mouse_move, type ≤1000 chars, key, scroll, wait; 1280x800; every action returns a fresh JPEG screenshot sent as an image part); trade-offs: "Network access is on", "Isolation comes from the VM", "Every listening port is public", "Files live with E2B", template user has passwordless sudo — [docs/COMPUTER.md](https://github.com/CopilotKit/openmuse/blob/main/docs/COMPUTER.md)
- Browser worker: "Sessions have persistent Chromium profiles; the app can open a live screenshot console and import PDF downloads. Agent tools can read public pages and hand interactive work to the person." "Playwright disables Chromium's internal sandbox by default; this is not a full desktop VM or a security boundary for hostile tenants." — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md); [SECURITY.md](https://github.com/CopilotKit/openmuse/blob/main/SECURITY.md)

#### 1i. "Rich Threads" via CopilotKit Intelligence
- "Every deployment requires `CPK_INTELLIGENCE_API_KEY` on the API server for CopilotKit Intelligence conversation persistence and replay... The native menu uses `useThreads`; rich tool results link back to saved tasks, documents, and browser sessions. Intelligence is a separate service and is not included in this repository's MIT license. No project key is shipped." — [OpenMuse README](https://github.com/CopilotKit/openmuse/blob/main/README.md)
- Key handling: "Never put the key in an `EXPO_PUBLIC_`, `NEXT_PUBLIC_`, or `VITE_` variable. The server constructs `CopilotKitIntelligence`, and `identifyUser` resolves the owner from the verified OpenMuse session." "The API fails at startup with a missing-key error when the key is unset." — [docs/RICH-THREADS.md](https://github.com/CopilotKit/openmuse/blob/main/docs/RICH-THREADS.md)
- Thread model: "the conversation menu uses CopilotKit's native `useThreads` hook to list, rename, archive, restore and paginate conversations. The server saves an owner-bound main thread ID and provisions it through Intelligence before the first message... Side chats create a fresh client thread ID and persist on their first run. Selecting a saved conversation mounts a private `useAgent({ agentId, runtimeAgentId, threadId })` instance and calls `copilotkit.connectAgent` to replay the thread." "Automatic thread naming is disabled" — [docs/RICH-THREADS.md](https://github.com/CopilotKit/openmuse/blob/main/docs/RICH-THREADS.md)
- Follow-up queue is client-side: "Follow-ups enter a visible, removable queue and run in order after the current reply and its persistence finish... The queue lives in the open app, not a durable server inbox. Delegated tasks remain separate server work." — [docs/RICH-THREADS.md](https://github.com/CopilotKit/openmuse/blob/main/docs/RICH-THREADS.md)
- What Intelligence is (vendor docs): "CopilotKit Intelligence adds AG-UI Streams, User Memories, Automatic Learning, Channels, and Product Analytics"; "AG-UI Streams: Let users reconnect, catch up, and resume conversations across devices"; "Automatic Learning: Turn real usage into skills you can review and publish"; "Channels: Run the same agent in Slack or Microsoft Teams"; self-hosting "in your own Kubernetes cluster or AWS account" via Helm chart or ECS bundle; "TypeScript also works without Intelligence; the other runtime implementations require it." — [docs.copilotkit.ai/intelligence/overview](https://docs.copilotkit.ai/intelligence/overview)

### Inferences
- The assignment's "opendots" description is a verbatim paraphrase of OpenMuse's README tables; the mix-up is understandable because CopilotKit shipped two near-identical templates two weeks apart (OpenMuse 2026-09-15, OpenDots 2026-09-29) with overlapping stacks (CopilotKit, AG-UI, Intelligence threads, OpenBot computers).
- Timing strongly suggests OpenMuse targets Meta's Muse (launched 2026-09-08; OpenMuse created 2026-09-15) and OpenDots targets OpenAI's Dots (announced 2026-09-29; OpenDots created the same day). Meta Muse's defining traits (user-set name/avatar/communication style, a watchable built-in browser, long-running tasks in a cloud VM, read-vs-write permissions) map one-to-one onto OpenMuse's "Personal context", "Take control" browser, durable tasks, and reviewed write actions. This mapping is not stated by CopilotKit anywhere I could find.
- OpenMuse's most reusable ideas for a personal-agent desktop app are architectural rather than code: (1) the **review → receipt** contract (a proposal bound to account + content hash + provider version; recorded approval before dispatch; uncertain outcomes retained, never silently retried); (2) **evidence ≠ permission** as a prompt-injection stance; (3) a **separate browser worker** with persistent profiles and human takeover; (4) a **network-less nonroot container** for commands plus a browser for egress; (5) **durable server-side tasks with SQL leases** that survive restarts, with the chat follow-up queue deliberately kept client-side.
- OpenMuse's biggest architectural compromise is that conversation persistence depends on a proprietary hosted service (CopilotKit Intelligence) even in local sample mode, and the SDK telemetry defaults to full capture — both at odds with a privacy-first self-hosted personal agent unless the Intelligence self-hosting path (Helm/ECS) is used or threads are reimplemented.
- OpenDots is organizationally "team-shaped" (Spaces, Pages, specialist Dots, Slack, calls) whereas OpenMuse is "person-shaped" (one owner, mail/calendar, documents, goals); Psyche's framing ("personal agent") is closer to OpenMuse.

## Key Question 2 — OpenClaw (formerly Clawdbot/Moltbot)

### Takeaway
OpenClaw is the dominant open-source personal-agent runtime by every metric (392k stars, 82k forks, ~100+ commits/week, 722 published security advisories, monthly date-versioned releases; latest v2026.10.5 on 2026-10-18). Its architecture is a single long-lived **Gateway** process per host (WebSocket control plane on 127.0.0.1:18789) that owns channels, sessions (SQLite per agent), the agent loop, cron/heartbeat, and node/companion pairing; the agent's identity and memory are plain Markdown files in a workspace (SOUL.md, AGENTS.md, USER.md, IDENTITY.md, MEMORY.md, memory/YYYY-MM-DD.md, BOOTSTRAP.md), and tools/skills/channels/model harnesses are plugins. Its 2026 security history (one-click RCE CVE-2026-25253, the ClawHavoc ClawHub poisoning campaign, hundreds of advisories) is the clearest cautionary case study on exposing an agent gateway and an open skills registry; the project responded with pairing-by-default, `openclaw security audit`, ClawHub scanning, an OpenAI-sponsored foundation, and a public maturity scorecard that still rates the project "Alpha (68%)" overall.

#### 2b. Gateway architecture and wire protocol
- "One long-lived Gateway owns all messaging surfaces" (WhatsApp via Baileys, Telegram via grammY, Slack, Discord, Signal, iMessage, WebChat); "One Gateway per host"; default bind `127.0.0.1:18789`; typed WS API with JSON-Schema-validated frames; events `agent`, `chat`, `presence`, `health`, `heartbeat`, `cron`; hosted widget surface at `/__openclaw__/canvas/` and `/__openclaw__/a2ui/` — [docs: Architecture](https://docs.openclaw.ai/concepts/architecture)
- Clients vs nodes: control-plane clients (macOS app, CLI, web UI, automations) send `health`, `status`, `send`, `agent`, `system-presence`; nodes (macOS, iOS, Android, headless) connect with `role: node` and expose capabilities like `camera.*`, `screen.record`, `location.get`; the macOS app also exposes `canvas.*` — [docs: Architecture](https://docs.openclaw.ai/concepts/architecture)
- Protocol: first frame must be `connect`; requests `{type:"req", id, method, params}`, responses `{type:"res", id, ok, payload|error}`, events `{type:"event", event, payload, seq?, stateVersion?}`; side-effecting methods (`send`, `agent`) require idempotency keys; "Events are not replayed. Clients must refresh after a gap."; schemas defined in TypeBox → JSON Schema → generated Swift models — [docs: Architecture](https://docs.openclaw.ai/concepts/architecture)
- Device pairing/trust: "Every WS client sends a device identity on `connect`. New device IDs need pairing approval, after which the Gateway issues a device token." Loopback connects can be auto-approved; tailnet/LAN and all non-local connects require explicit approval; clients sign a `connect.challenge` nonce (payload v3 binds platform and deviceFamily) — [docs: Architecture](https://docs.openclaw.ai/concepts/architecture)
- Remote access: Tailscale/VPN preferred, else SSH tunnel to 18789; TLS with optional pinning; `gateway.auth.mode: "none"` disables shared-secret auth and should stay off public ingress; supervision via launchd/systemd — [docs: Architecture](https://docs.openclaw.ai/concepts/architecture)
- Timed work: kernel-owned `GatewayScheduler` with one host timer; durable stores keep deadlines; "After sleep, each runnable due registration runs once... missed ticks are coalesced." — [docs: Architecture](https://docs.openclaw.ai/concepts/architecture)
- State layout: `openclaw.json` (config), `state/openclaw.sqlite` (shared runtime DB), `agents/<agentId>/agent/openclaw-agent.sqlite` (per-agent auth profiles + runtime state), `credentials/`, `agents/<agentId>/sessions/` (transcripts), `workspace/` — [docs: agent runtime workflow](https://github.com/openclaw/openclaw/blob/main/docs/openclaw-agent-runtime.md)

#### 2c. Agent runtime, loop, hooks, resumption (no built-in plan/todo tool)
- Runtime layout: `src/agents/embedded-agent-runner/` (attempt loop, model selection, compaction, transcript wiring); `packages/agent-core/` = "Reusable agent core (`@openclaw/agent-core`): agent loop, harness types, messages, compaction helpers, prompt templates, skills, and session storage contracts"; `src/agents/harness/` = "Harness registry, selection policy, and lifecycle for the built-in and plugin-registered harnesses." "No external agent framework packages remain." "`@earendil-works/pi-tui` remains a third-party dependency." Built-in runtime id is `openclaw`; "The legacy alias `pi` normalizes to `openclaw`"; plugin harnesses register ids such as `codex`; `auto` picks a plugin harness that supports the provider route, else built-in — [docs: Agent runtime architecture](https://github.com/openclaw/openclaw/blob/main/docs/agent-runtime-architecture.md); dependency `"@earendil-works/pi-tui": "1.1.0"` — [package.json](https://github.com/openclaw/openclaw/blob/main/package.json)
- Run sequence: `agent` RPC resolves session from `sessionKey`/`sessionId`, persists metadata, returns `{ runId, acceptedAt }`; `runEmbeddedAgent` reserves the session-controller turn, builds the session, streams deltas, enforces per-attempt timeout; `agent.wait` returns `{status, startedAt, endedAt, error?}` plus `terminalReply`/`terminalReceipt` — [docs: Agent loop](https://docs.openclaw.ai/concepts/agent-loop)
- Concurrency/writes: "The session controller serializes turns by physical session identity"; messaging channels choose a queue mode (steer, followup, collect, interrupt); "An admitted run records a durable `activeWriterRunId` before streaming. Every transcript write carries `expectedWriterRunId`, so a superseded run cannot commit stale data." — [docs: Agent loop](https://docs.openclaw.ai/concepts/agent-loop)
- System prompt = base prompt + skills prompt + bootstrap context (workspace files) + per-run overrides — [docs: Agent loop](https://docs.openclaw.ai/concepts/agent-loop)
- Hooks: internal `HOOK.md` scripts (`agent:bootstrap`, `command:new`, `command:reset`, `command:stop`); plugin hooks `before_model_resolve`, `before_prompt_build` (can narrow tools via `toolsAllow`), `before_agent_reply`, `before_tool_call`/`after_tool_call`, `tool_result_persist`, `before_compaction`/`after_compaction` (observe only), `agent_end`, `message_received/sending/sent`, `session_start/end`, `gateway_start/stop`, `before_install`; "`before_tool_call` with `block: true` is terminal" — [docs: Agent loop](https://docs.openclaw.ai/concepts/agent-loop)
- Interruption/resumption semantics: "Cancellation revokes the run's tool and approval authority immediately"; "Approval waits pause the unused attempt budget"; "A question from `ask_user` does not pause the execution budget"; `agent.wait` timeout does not stop the run; agent runtime timeout default `172800s (48h)` per model attempt; model idle timeout 120s cloud / 300s self-hosted — [docs: Agent loop](https://docs.openclaw.ai/concepts/agent-loop)
- Reply shaping: a final that is only `NO_REPLY` is treated as silence; "An empty final is recorded as a failure"; a confirmed final send to the source conversation ends the loop — [docs: Agent loop](https://docs.openclaw.ai/concepts/agent-loop)
- Planning: "The page does not describe any planning or todo mechanism." (agent-loop page) — [docs: Agent loop](https://docs.openclaw.ai/concepts/agent-loop); the sandbox page lists core Goal controls (`get_goal`, `create_goal`, `update_goal`) in the default sandbox tool allowlist — [docs: Sandboxing](https://docs.openclaw.ai/gateway/sandboxing)
- Restart recovery (2026.10.5): "interrupted turns, first messages during worktree preparation, subagent work, and deferred tasks resume after a Gateway restart, and user input and committed session data survive restarts, concurrent writes, and failed publications" — [release v2026.10.5](https://github.com/openclaw/openclaw/releases/tag/v2026.10.5); sessions page: Gateway retries continuation with a budget of three failed starts, then users click **Resume** in WebChat — [docs: Session](https://docs.openclaw.ai/concepts/session)
- Subagents: "background agent runs spawned from an existing agent run," session key `agent:<agentId>:subagent:<uuid>`; by default a sub-agent "announces" its result back to the requester; "Sub-agents do not receive session or message tools by default"; `context: "fork"` to inherit the requester's transcript; "A subagent run ends; a session does not."; Control UI **Subagents** panel with Running/Finished and view-only transcripts — [docs: Sub-agents](https://docs.openclaw.ai/tools/subagents)

#### 2d. Sessions
- "All session state is owned by the gateway." Routing by source: DMs → shared session; groups → per group; rooms → per room; cron → fresh session per run; webhooks → per hook — [docs: Session](https://docs.openclaw.ai/concepts/session)
- `session.dmScope`: `main` (default; all DMs share one session), `per-peer`, `per-channel-peer` (recommended for multi-user), `per-account-channel-peer`; `session.identityLinks` merges one person's identities across channels; "If multiple people can message your agent, enable DM isolation." — [docs: Session](https://docs.openclaw.ai/concepts/session)
- Reset modes: none (default; compaction manages growth), daily (`atHour` default 4), idle (`idleMinutes`), manual `/new` or `/reset` — [docs: Session](https://docs.openclaw.ai/concepts/session)
- Storage: per-agent SQLite `~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite`; archived transcripts in `~/.openclaw/agents/<agentId>/sessions/`; maintenance defaults `pruneAfter: 30d`, `maxEntries: 5000` — [docs: Session](https://docs.openclaw.ai/concepts/session)
- Incognito sessions: memory-only, expire after 24h or Gateway restart, skip memory flush; caveat: on the Codex runtime "the app-server still writes submitted messages to its diagnostic log database (`logs_2.sqlite`). OpenClaw cannot prevent this." — [docs: Session](https://docs.openclaw.ai/concepts/session)
- Default single agent: `agentId: main`, main session key `"agent:main:main"`, workspace `<stateDir>/workspace` — [docs: Multi-agent](https://docs.openclaw.ai/concepts/multi-agent)

#### 2e. Workspace, persona and memory files
- Workspace default `~/.openclaw/workspace` (profile variant `~/.openclaw-<profile>/workspace`; `OPENCLAW_WORKSPACE_DIR` override); "Keep it private and treat it as memory."; "not a hard sandbox" — absolute paths reach the host unless sandboxing is on — [docs: Agent workspace](https://docs.openclaw.ai/concepts/agent-workspace)
- File map: **AGENTS.md** (operating instructions and how to use memory; loaded every session); **SOUL.md** (persona, tone, boundaries; every session); **USER.md** (optional; stable preferences, relationships, active-project context as dated active/superseded directives; own 4,000-character budget); **IDENTITY.md** (name, vibe, emoji; created during the bootstrap ritual); **AGENTS.md `## Tools` section** replaces a standalone TOOLS.md ("It does not control tool availability; it is only guidance"); **BOOT.md** (optional startup checklist, only with the boot-md hook); **BOOTSTRAP.md** (one-time first-run ritual, delete when done); **memory/YYYY-MM-DD.md** (daily log; read today's and yesterday's at session start); **MEMORY.md** (optional curated long-term memory; "Loaded only in the main, private session, not in shared or group contexts"); **skills/** (workspace skills take precedence) — [docs: Agent workspace](https://docs.openclaw.ai/concepts/agent-workspace)
- Budgets: missing required files inject a "missing file" marker; `agents.defaults.bootstrapMaxChars` 20,000 per file and `bootstrapTotalMaxChars` 60,000 total; USER.md keeps its 4,000-char cap; editor accepts up to 2 MiB per file — [docs: Agent workspace](https://docs.openclaw.ai/concepts/agent-workspace)
- Memory principle: "The model only remembers what gets saved to disk; there is no hidden state."; **DREAMS.md** (optional "Dream Diary and dreaming sweep summaries"); daily files "are indexed but not injected every turn" — [docs: Memory](https://docs.openclaw.ai/concepts/memory)
- Memory search: `memory_search` combines vector similarity with keyword matching when an embedding provider is configured (OpenAI embeddings default; `provider: none` → keyword only); builtin SQLite engine (PostgreSQL experimental); `memory_get`; `sessions_search`/`sessions_history` for transcript recall; `memory.search.rememberAcrossConversations: true` lets a personal agent recall its other private conversations — [docs: Memory](https://docs.openclaw.ai/concepts/memory); [docs: Session](https://docs.openclaw.ai/concepts/session)
- Memory flush before compaction: "a silent turn prompts the agent to save important context" (on by default; `agents.defaults.compaction.memoryFlush.enabled`); runs on a private copy of the conversation; appends only to the daily note; can use a separate (e.g., local) model — [docs: Memory](https://docs.openclaw.ai/concepts/memory)
- HEARTBEAT.md is gone: "The old `HEARTBEAT.md` file is no longer read at runtime. Instructions live in a per-job 'monitor scratch' stored in the state database" (`openclaw cron scratch <jobId>`, 256 KiB cap; `openclaw doctor --fix` imports an existing HEARTBEAT.md) — [docs: Heartbeat](https://docs.openclaw.ai/gateway/heartbeat)
- Git backup guidance: private repo containing `AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `USER.md`, `memory/`; never commit `~/.openclaw/` contents; `.gitignore` covers `.env`, `*.key`, `*.pem`, `secrets*` — [docs: Agent workspace](https://docs.openclaw.ai/concepts/agent-workspace)
- Vision: "Memory is a special plugin slot where only one memory plugin can be active at a time. Today we ship multiple memory options; over time we plan to converge on one recommended default path." — [VISION.md](https://github.com/openclaw/openclaw/blob/main/VISION.md)

#### 2f. Channels, and how a "designated person/platform" is authorized (pairing, allowlists, DM policies)
- Channel inventory: core = WebChat; bundled plugins = A2A, Reef, Telegram, X/Twitter; official plugins = Buzz, ClickClack, Discord, Feishu, Google Chat, iMessage, IRC, LINE, Matrix, Mattermost, Microsoft Teams, Nextcloud Talk, Nostr, QQ bot, Raft, Signal, Slack, SMS (Twilio), Synology Chat, Tlon, Twitch, WhatsApp, Zalo, Zalo personal; external = WeChat, WeCom, Yuanbao, Zalo ClawBot; Voice Call plugin (Plivo/Telnyx/Twilio); install via `openclaw plugins install @openclaw/<id>` — [docs: Channels](https://docs.openclaw.ai/channels)
- Connection methods: Telegram bot token; WhatsApp QR pairing (Baileys, stores state on disk); Signal via signal-cli; iMessage via `imsg` over JSON-RPC stdio; Slack Socket Mode/HTTP/relay; A2A 1.0 JSON-RPC — [docs: Channels](https://docs.openclaw.ai/channels)
- `dmPolicy` values: **pairing** (default): "Unknown senders get a pairing code, and the bot ignores them until approved."; **allowlist**: unknown senders blocked, no handshake; **open**: anyone can DM, requires `"*"` in the channel allowlist as explicit opt-in; **disabled**: inbound DMs ignored — [docs: Access control](https://docs.openclaw.ai/gateway/security/access-control)
- Pairing mechanics: codes expire after 1 hour; pending requests capped at 3 per channel; `openclaw pairing list <channel>` / `openclaw pairing approve <channel> <code>`; approvals saved to `~/.openclaw/credentials/<channel>-allowFrom.json` and merged with config allowlists — [docs: Access control](https://docs.openclaw.ai/gateway/security/access-control); README: "DM-capable channels pair unknown senders by default; approve a pairing request with `openclaw pairing approve <channel> <code>`." — [OpenClaw README](https://github.com/openclaw/openclaw/blob/main/README.md)
- Two allowlist layers: a DM allowlist (who can DM) and a group allowlist (which groups/channels/guilds the bot accepts); `groupPolicy="allowlist"` + `groupAllowFrom` restricts who can trigger inside a group; per-group `requireMention`; `agents.entries.*.groupChat.mentionPatterns`; evaluation order: group policy/allowlists first, then mention/reply activation; "Replying to a bot message does not bypass `groupAllowFrom`" — [docs: Access control](https://docs.openclaw.ai/gateway/security/access-control)
- Command authorization: slash commands/directives run only for authorized senders via per-provider `commands.allowFrom` or channel allowlists + pairing state; "If a channel allowlist is empty or includes `"*"`, commands are effectively open"; `/exec` is session-only — [docs: Access control](https://docs.openclaw.ai/gateway/security/access-control)
- Owner concept: heartbeat delivery `target: "owner"` resolves to "the first concrete `commands.ownerAllowFrom` entry, then channel `allowFrom`"; the access-control page itself "does not define an owner role" — [docs: Heartbeat](https://docs.openclaw.ai/gateway/heartbeat); [docs: Access control](https://docs.openclaw.ai/gateway/security/access-control)
- Context visibility is separate from trigger authorization: `"all"` (default), `"allowlist"`, `"allowlist_quote"` — [docs: Access control](https://docs.openclaw.ai/gateway/security/access-control)
- Security index defaults: "Most chat channels answer an unknown DM sender with a pairing code instead of processing the message. Group access is allowlisted, usually behind a mention gate. Container images default to an exposed bind, so pair them with auth." — [docs: Security](https://docs.openclaw.ai/gateway/security)
- Per-agent routing: bindings map `(channel, accountId, peer)` (optionally guild/team) to an agent; "DM access control (pairing or allowlist) is global per WhatsApp account, not per agent." — [docs: Multi-agent](https://docs.openclaw.ai/concepts/multi-agent)

#### 2i. Cron/automations and heartbeat
- Automations: "The scheduler persists jobs, wakes the agent at the right time" and can deliver output to a chat channel, a webhook, or nowhere; `openclaw automations` CLI (`openclaw cron` alias); schedule types, pacing, and "Event triggers (condition watchers)"; `POST /hooks/wake` — [docs: Automations](https://docs.openclaw.ai/automation/cron-jobs)
- Session targets: `main` ("Owning agent's main session"), `isolated` ("Dedicated `cron:<jobId>`" session, new per run), `current` ("Detached; commits to the creation-bound conversation"), `session:custom-id` (persistent named session) — [docs: Payloads](https://docs.openclaw.ai/automation/cron-jobs/payloads)
- Unattended run contract: isolated runs are "explicitly unattended: no one is present to clarify or approve."; "The final reply must be the deliverable rather than a plan, acknowledgement, or request for input."; "The agent returns `NO_REPLY` when nothing needs doing."; "A completed model run is not proof that the requested task succeeded." — [docs: Payloads](https://docs.openclaw.ai/automation/cron-jobs/payloads)
- Heartbeat: "A system-owned automation that runs periodic agent turns in the main session"; default interval 30m (1h when Anthropic OAuth/Claude CLI auth is used); `activeHours`; quiet replies via `NO_REPLY` or `heartbeat_respond` with `notify: false` (legacy `HEARTBEAT_OK` still accepted); `isolatedSession: true` cuts a run "roughly 100K tokens down to 2–5K"; `lightContext` skips workspace bootstrap files; visibility knobs `showOk` (default false), `showAlerts` (true), `useIndicator` (true); "Use automations for recurring checks, and heartbeat for an occasional 'anything you need?' check-in." — [docs: Heartbeat](https://docs.openclaw.ai/gateway/heartbeat)
- Cron approvals never reach chat: "The TUI does not render exec approval cards, and chat channels never receive automation approvals." — [docs: Exec approvals](https://docs.openclaw.ai/tools/exec-approvals)

#### 2k. Security model: trust boundary, sandboxing, exec approvals, secrets
- Trust model: "one trusted boundary per gateway: a single operator, or a team whose members trust each other."; "OpenClaw is not a hostile multi-tenant security boundary for mutually adversarial users."; `openclaw security audit` checks drift from defaults; threat model mapped to MITRE ATLAS — [docs: Security](https://docs.openclaw.ai/gateway/security); VISION: "A shared Gateway is for people who trust each other. Mutually untrusted users need separate Gateways, host or container isolation, and access controls." — [VISION.md](https://github.com/openclaw/openclaw/blob/main/VISION.md)
- Sandboxing: "Sandboxing is off by default and controlled by `agents.defaults.sandbox`... The Gateway always runs on the host, and only tool execution moves into the sandbox when enabled." Backends: Docker (default), Podman, SSH, OpenShell, Crabbox; example `mode: "non-main"`, `scope: "session"`, `workspaceAccess: "none"`; `tools.elevated` runs `exec` outside the sandbox; `openclaw sandbox list|explain|recreate` — [docs: Sandboxing](https://docs.openclaw.ai/gateway/sandboxing)
- Exec approvals: security modes `deny` / `allowlist` / `full` (defaults: `full` for gateway/node hosts, `deny` for a sandbox host); ask modes `off` (default) / `on-miss` / `always`; `askFallback` default `deny`; normalized `tools.exec.mode` = `deny|allowlist|ask|auto|full`; `strictInlineEval` for `python -c`/`node -e`; "Generated `allow-always` entries are bound to both the exact argv and the working directory where you approved them."; approvals stored in `~/.openclaw/state/openclaw.sqlite`; delivery via macOS app, chat (Matrix reactions `✅/♾️/❌`, `/approve`), Control UI Settings → Approvals — [docs: Exec approvals](https://docs.openclaw.ai/tools/exec-approvals)
- Tool-approval hardening (2026.10.5): "ordinary hooks can no longer rewrite trusted-inline-approved tool arguments without another approval, and transforming plugins must request separate approval for their final arguments or the call is blocked"; "network results reached through Tool Search and Code Mode now taint the turn the same way direct network tool calls do" — [release v2026.10.5](https://github.com/openclaw/openclaw/releases/tag/v2026.10.5)
- Privacy: "OpenClaw sends no usage analytics, tracking identifiers, or telemetry attribution to the project unless the operator turned that on themselves."; daily update check reports version and platform — [VISION.md](https://github.com/openclaw/openclaw/blob/main/VISION.md)
- Criticism of 2.0 defaults: The Register noted shared sessions lack network and file-system security boundaries, Secret Store values aren't encrypted at rest, and the sandbox isn't enabled by default; VentureBeat said the containerised NanoClaw alternative has a narrower attack surface (as summarized by Wikipedia) — [Wikipedia: OpenClaw](https://en.wikipedia.org/wiki/OpenClaw)

#### 2l. 2026 security incidents and criticism

### Inferences
- OpenClaw's durable design decisions worth copying: one local control-plane process with a typed, schema-validated WS protocol; device pairing + per-channel sender allowlists as the single mechanism for "who may talk to the agent"; plain-Markdown identity/memory files with explicit injection budgets; a memory-flush turn before compaction; `NO_REPLY` as a first-class silent outcome for unattended runs; approvals bound to exact argv + cwd; and "a completed model run is not proof that the task succeeded."
- OpenClaw deliberately has no plan/todo tool in the core loop; long-horizon structure comes from sessions, automations, subagents and (newly) goals/Workboard rather than from a plan artifact — the opposite of the coding-harness pattern in KQ3.
- Its security record shows where a personal-agent desktop app is most exposed: (1) any browser-reachable control UI that holds a bearer token; (2) an open skills registry with no review; (3) approval state that outlives its context (cwd, args, session); (4) exec allowlist parsing; (5) node/companion pairing scope. Several of OpenClaw's fixes (origin checks, pairing before scope grant, approval binding, VirusTotal scanning, `security audit`) are concrete requirements for Psyche.

## Key Question 3 — Plan-and-execute patterns in coding/agent harnesses

### Takeaway
Across Claude Code, Codex, Goose, Cline, Open Interpreter, Manus and Anthropic's harness research, the convergent pattern is: (1) a **read-only planning phase** gated by permission mode (Claude Code plan mode, Codex "Plan Mode" collaboration template, Cline Plan/Act), producing a plan the human approves; (2) a **structured, lightweight task list** kept near the end of context (Claude Code TaskCreate/TaskUpdate, Codex `update_plan`, Manus todo.md recitation) — though Cline just deprecated its Focus Chain todo list as not worth the extra layer; (3) **verification by an evaluator separate from the generator** (Claude Code `/goal` evaluator model, Anthropic's generator/evaluator harness, dynamic-workflow adversarial verifiers, Codex `/goal` + auto-review); (4) **resumption through artifacts, not memory** (git + progress files + feature JSON in Anthropic's harness, JSONL transcripts/checkpoints in Claude Code, shadow-git checkpoints in Cline, session resume in Codex/Goose); and (5) **asking the user** through a dedicated multiple-choice tool (Claude Code `AskUserQuestion`, OpenClaw `ask_user`) or by pausing the goal.

#### 3b. Anthropic engineering guidance (and the Claude Agent SDK)
- "Building effective agents" (Dec 19, 2024): workflows = "systems where LLMs and tools are orchestrated through predefined code paths"; agents = "systems where LLMs dynamically direct their own processes and tool usage"; five workflow patterns (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer); agents "can pause at checkpoints or blockers to ask a human for input" and need stopping conditions; principles: simplicity, transparency ("make the agent's planning steps explicit"), and a carefully designed agent-computer interface — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- "Effective context engineering for AI agents" (Sep 29, 2025): context engineering = "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference"; context rot; just-in-time retrieval via identifiers (Claude Code loads CLAUDE.md up front and uses glob/grep); compaction keeps "architectural decisions, unresolved bugs, and implementation details"; structured note-taking "Claude Code's to-do lists, a custom agent's NOTES.md file"; sub-agents return condensed summaries of ~1,000–2,000 tokens — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Writing effective tools for agents" (Sep 11, 2025): prototype, then evaluate with tasks that "might require multiple tool calls—potentially dozens"; "More tools don't always lead to better outcomes"; namespacing; return high-signal context; pagination/truncation with helpful errors; "Think of how you would describe your tool to a new hire on your team." — [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)
- "Building agents with the Claude Agent SDK" (Sep 29, 2025): loop "gather context -> take action -> verify work -> repeat"; folder structure as "a form of context engineering"; start with agentic search before semantic search; verification via rules ("The best form of feedback is providing clearly defined rules for an output"), visual feedback (Playwright screenshots), and LLM-as-judge ("generally not a very robust method") — [Claude blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- "Effective harnesses for long-running agents" (Nov 2025): an **initializer agent** creates `init.sh`, `claude-progress.txt`, a feature list and an initial git commit; a **coding agent** runs each later session; feature list is JSON with `category`, `description`, verification steps and `passes` (agents may only change `passes`; JSON chosen because "the model is less likely to overwrite it than Markdown"; prompt: "It is unacceptable to remove or edit tests"); one feature per session; session startup = `pwd`, read git log + progress file, pick highest-priority unfinished feature, run `init.sh`, do a basic end-to-end test first; browser automation (Puppeteer MCP) required before marking features passing; failure-mode table (premature victory, buggy state, premature completion marks, time lost figuring out how to run the app) — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- "Harness design for long-running application development" (Mar 24, 2026, Prithvi Rajasekaran): generator + evaluator inspired by GANs, later planner + generator + evaluator; "agents reliably skew positive when grading their own work"; "context anxiety" → full context resets with structured handoffs instead of in-place compaction (needed for Sonnet 4.5, dropped for Opus 4.5); **sprint contracts** where the generator proposes what "done" means and the evaluator agrees before coding; evaluator used Playwright with hard per-criterion thresholds; retro-game example: solo 20 min/$9 (broken) vs harness 6 hr/$200 (working); DAW example on Opus 4.6: ~3h50m, $124.70, planner $0.46; with Opus 4.6 the sprint construct was removed and the evaluator moved to a single final pass; lesson: "Re-examine the harness when a new model arrives, removing pieces that are no longer load-bearing." — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Claude Agent SDK: "the same tools, agent loop, and context management that power Claude Code, programmable in Python and TypeScript"; capabilities: built-in tools, hooks, subagents, MCP, permissions, sessions ("resume or fork later"), skills/commands/memory loaded from `.claude/`, plugins; alternative "Managed Agents" (Anthropic-hosted harness with cloud or self-hosted sandbox); "Use of the Claude Agent SDK is governed by Anthropic's Commercial Terms of Service"; "Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products" — [docs: Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

### Inferences
- The field is converging on **two separate artifacts**: a human-approved *plan* produced in a read-only mode, and a machine-maintained *checklist* (tasks) that is cheap to rewrite; Codex makes the separation explicit ("`update_plan` is a checklist/progress/TODOs tool; it does not enter or exit Plan Mode"). Cline's deprecation of Focus Chain and the Manus "one-third of actions" anecdote both suggest the checklist should be harness-managed and lightweight, not a model-maintained Markdown file.
- Verification is moving out of the working model: Claude Code's `/goal` and Anthropic's evaluator both use a *different* model instance to decide "done," because "agents reliably skew positive when grading their own work." For a personal agent, the analogue is a receipt-checking evaluator (did the email actually send? does the calendar event exist?) rather than a code test.
- Resumption everywhere is artifact-based (transcripts, git, progress files, SQLite rows), never model-memory-based; Anthropic's "fresh agent reads `init.sh`, git log, progress file" routine is the simplest portable recipe and maps directly onto a personal agent's "task file + receipts log."
- Asking the user is best modelled as a first-class, structured tool (`AskUserQuestion`) whose answers stay open until resolved, and which is withheld from subagents; unattended/background runs instead follow OpenClaw's rule that "the final reply must be the deliverable rather than a plan, acknowledgement, or request for input."
- Sandboxing is now table stakes and OS-native (Seatbelt / bubblewrap+seccomp / Windows sandbox in Codex and Open Interpreter; Docker in OpenClaw/OpenMuse), with approvals as the *policy* layer on top of the sandbox *boundary* — Codex's framing ("Approvals determine when Codex pauses... while the sandbox determines which files and network resources commands can access") is a clean model to adopt.

## Key Question 4 — What Psyche could reuse as a library vs must build

### Takeaway
Reusable today under permissive licenses: **pi-agent-core** (MIT, TS, the loop OpenClaw started from, with steering/follow-up queues and tool hooks) and the sibling experimental **pi-durable** (crash-resumable conversations/tasks on SQLite); **Vercel AI SDK** (Apache-2.0) for the loop (`ToolLoopAgent` with `stopWhen`/`prepareStep`) and, notably, **HarnessAgent** to drive Claude Code, Codex or Pi as embedded harnesses; **OpenAI Agents SDK** (MIT) for serializable human-in-the-loop run state; **Mastra** (Apache-2.0) for durable suspend/resume workflows and typed memory; **LangGraph** (MIT, Python-first) for checkpointed graphs with `interrupt()`; **AG-UI + CopilotKit** (MIT) for the UI/event protocol (what OpenMuse/OpenDots use), and **Goose's Rust crates** (Apache-2.0) if Psyche is Rust-side. The **Claude Agent SDK** gives the entire Claude Code harness but under Anthropic's Commercial Terms and API-key-only auth. What no library provides and Psyche must build: the persona/memory file layer, channel pairing/allowlists, the review→receipt ledger and reconciliation, the sandboxed "computer" policy, and the evaluator that checks receipts rather than tests.
