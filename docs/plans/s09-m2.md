# S09 plan, Milestone 2: M7 IMAP/JMAP, M10 shopping helpers, M3 MCP sandboxing

Owner: S09. Branch `ws/s09-m2` (from `main` at #103). Paths: `packages/connectors/**`, `packages/mcp-host/**`, plus the mail fakes in `packages/testing/src/fakes/mail/` and the V3 scenario fixtures in `tests/scenarios/v3-shopping/` that the integrator asked for. M1 plan: [s09.md](s09.md).

## Goal

Non-Google mail works with the same tools as Gmail (M7); the agent can compare prices, build a cart and stop at the payment hand-off with a receipt (M10); local MCP servers run inside the sandbox container through `packages/sandbox` (M3).

## Steps (small PRs, in order)

1. **M7a: mail layer + JMAP.** `src/mail/`: one `MailConnector` over a `MailBackend` interface (mailboxes, search, read, attachment, flags / move, draft, send, sync); the Gmail send binding (`send_email`: account, recipients, subject, body hash) and `connector_action` bindings shared with Google; an RFC 5322 / MIME parser (bounded like the Gmail part-tree parser, reusing `parsePayload`); the JMAP backend (RFC 8620 / 8621 / 8617 subset: session, `Mailbox/get`, `Email/query`, `Email/get`, `Email/set`, blob upload + `Email/import`, `Identity/get` + `EmailSubmission/set`, `Email/changes`). Credentials are `{{cred:slug}}` placeholders in config, resolved per call through `CredentialBroker.resolve` with the item bound to `{ connector: <id> }`; the resolved token lives only in the request. Fakes: `FakeMailStore` + `FakeJmapServer` in `@psyche/testing`.
2. **M7b: IMAP + SMTP.** A minimal IMAP4rev1 client (LOGIN, LIST with SPECIAL-USE, SELECT, UID SEARCH / FETCH / STORE / MOVE, APPEND, LOGOUT) and SMTP client (EHLO, AUTH PLAIN, MAIL / RCPT / DATA) over a `MailSocket` seam; production uses implicit TLS only (`tls.connect`, TLS 1.2+), no STARTTLS and no plaintext. Fakes: `FakeImapServer`, `FakeSmtpServer` speaking the same subset over in-memory streams.
3. **M10: shopping helpers.** `src/shopping/`: a connector over the `BrowserDriver` contract with an owner allowlist of merchants (`config.merchants[]`: name, origin, search path). Tools: `shop_search` (read, one merchant), `shop_compare` (read, all merchants, sorted offers), `shop_add_to_cart` (write, `connector_action` bound to merchant + offer), `shop_view_cart` (read), `shop_checkout_handoff` (`financial`, `purchase` binding: merchant, amount in minor units, currency, line-item hash; never submits; returns the confirm-card payload and records a receipt; payment itself is G12 / Stripe Link, later), `shop_parse_order_email` (schema.org `Order` from HTML/JSON-LD, pure). Scenario V3 fixtures (two fixture storefronts, steps up to the hand-off) in `tests/scenarios/v3-shopping/` with the tool rows in `shared/tools.json`; the scripted runner needs `shop.*` executors (S18) so V3 is validated by `validate.mjs` and listed in `known-failures.json` until the runner has them.
4. **M3: container launcher.** `containerLauncher({ sandbox })` in `@psyche/mcp-host`: `ensureSandbox({ kind: "task", id: "mcp:<serverId>" }, { network })`, then a long-lived stdio process inside the container with the server's env (vault values resolved at spawn, passed by name, never in argv) and a `PipeTransport` over its stdin / stdout. The sandbox needs one additive method (`openStdio(sandboxId, argv, { cwd, env })` → raw pipes, counted as busy like a PTY): requested from S21 by issue because another session is editing `packages/sandbox`. Requested as #143. Until it lands the launcher is typed against the narrow `SandboxStdioHost` interface and tested with a fake; `tests/integration/mcp-sandbox/` holds the real-container acceptance test.

## Interfaces used

`Connector` framework (own), `CredentialBroker`, `PermissionBroker` (receipts), `BrowserDriver`, `SandboxRunner` + the requested `openStdio`, `LibrarySink`, `Clock`. Fakes from `@psyche/testing`.

## Risks

- IMAP servers differ (no MOVE, no SPECIAL-USE, no UTF-8 SEARCH): the client falls back (COPY + \Deleted + EXPUNGE; name heuristics; ASCII-only search). Live tests behind `PSYCHE_LIVE_TESTS=1`.
- A real browser DOM is richer than the fake driver's text + elements: the offer parser works on snapshot text and refs only (`name … $price` lines, `Add to cart` buttons), so it holds on both.
- `financial` approvals are device-only with presence verification; the hand-off tool records a receipt and stops, so the scenario ends at the card.
