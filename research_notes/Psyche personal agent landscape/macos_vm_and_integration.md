## Key Question 1: macOS VMs on Apple Silicon — Virtualization.framework capabilities/limits, tooling (UTM, Tart, Lume/c-ua, VirtualBuddy, Anka), how c/ua runs agents in guests, and the "sandboxed Mac inside the app" UX

### Takeaway
Virtualization.framework gives a first-party, entitlement-gated path to install macOS from an IPSW and run it in-app, but it is hard-capped at two concurrent macOS guests (framework-enforced, licence-derived), has no nested virtualization for macOS guests, and only recently (macOS 27) gained first-boot user provisioning, USB passthrough and overlay/snapshot disk images; iCloud sign-in works only for VMs created fresh on macOS 15+ hosts from macOS 15+ IPSWs and still excludes the App Store. Lume/c-ua is the most agent-oriented stack (unattended IPSW install, OCI image distribution, in-guest daemon on port 3211, pre-granted Accessibility/Screen Recording in published images), while Tart, UTM and VirtualBuddy cover CI, general-purpose and developer-testing use respectively.

### Cited Findings

**Framework basics, entitlements, and version matrix**
- The Virtualization framework (macOS 11+) "provides high-level APIs for creating and managing virtual machines (VM) on Apple silicon and Intel-based Mac computers", supports VIRTIO devices (network, socket, serial, storage, entropy, memory balloon), and its topic list includes Shared directories, Sockets, Consoles, Clipboard sharing, USB Devices, Graphics, Audio, Memory (balloon), Network, and the required `com.apple.security.virtualization` entitlement — [Apple Virtualization framework](https://developer.apple.com/documentation/virtualization)
- macOS guests in UTM require "Apple Silicon hosts running macOS 12 or higher"; UTM's feature matrix for macOS guests: shared directories via VirtioFS need macOS 13+ on host and guest (mount in guest with `mount_virtiofs share [mount point]`), dynamic display resolution needs macOS 14, save states need macOS 14, clipboard sharing needs macOS 15+ on host and guest (install UTM "Guest Tools" = `spice-vdagent`/`spice-vdagentd`), USB sharing is "not available before macOS 27", and "Snapshots and disposable mode: not available before macOS 27" — [UTM macOS guest docs](https://docs.getutm.app/guest-support/macos/)
- Apple: "Shared directories in macOS VMs are only available in macOS 13 and later"; configure `VZVirtioFileSystemDeviceConfiguration` with a `tag`, use `VZSingleDirectoryShare` or `VZMultipleDirectoryShare`, and `VZVirtioFileSystemDevice` can change shares while the VM runs — [Apple Shared directories](https://developer.apple.com/documentation/virtualization/shared-directories)
- `VZSpiceAgentPortAttachment` (macOS 13+) is "an attachment point that enables the Spice clipboard sharing capability" with `sharesClipboard` and `spiceAgentPortName` — [Apple VZSpiceAgentPortAttachment](https://developer.apple.com/documentation/virtualization/vzspiceagentportattachment)
- `saveMachineStateTo(url:completionHandler:)` is macOS 14+; it "fails if the VM isn't in a paused state"; the sample calls `validateSaveRestoreSupport()` on the configuration, saves to `SaveFile.vzvmsave`, and the framework deletes the save file after a restore because "the VM disk no longer matches the state in the file" — [Apple saveMachineStateTo](https://developer.apple.com/documentation/virtualization/vzvirtualmachine/savemachinestateto(url:completionhandler:)); [Apple sample](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)
- Nested virtualization: `VZGenericPlatformConfiguration.isNestedVirtualizationSupported` is macOS 15+ and "available for Mac with the M3 chip, and later" — it is a property of the *generic (Linux) platform configuration*, not the Mac platform — [Apple isNestedVirtualizationSupported](https://developer.apple.com/documentation/virtualization/vzgenericplatformconfiguration/isnestedvirtualizationsupported); Tart: nested virtualization is "supported only on M3 or M4 chips running macOS 15 or later, and only for Linux VMs", enabled with `tart run --nested` — [Tart FAQ](https://tart.run/faq/); running a macOS guest inside a macOS VM "doesn't work" — [Eclectic Light, 2022](https://eclecticlight.co/2022/08/04/virtualisation-on-apple-silicon-macs-8-how-apple-limits-vms/)
- Bridged networking: the `com.apple.vm.networking` entitlement (needed for vmnet APIs without root) "is restricted to developers of virtualization software. To request this entitlement, contact your Apple representative" — [Apple com.apple.vm.networking](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.vm.networking)
- macOS 26 added the Apple Sparse Image Format (ASIF), creatable with `diskutil image` or Disk Utility and usable as VM backing storage via `VZDiskImageStorageDeviceAttachment`; macOS 26 also fixed "Virtual machine networking fails if you start a bridge mode VM while a shared or host mode VM is running" — [Apple macOS 26 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-26-release-notes)
- macOS 27 adds the DiskImageKit framework (macOS 27+): ASIF and RAW images, "stacked disk images" with a read-only base layer, one cache layer, and overlay layers that "store modifications to the base image (enables copy-on-write snapshots)", passed to Virtualization via `VZDiskImageStorageDeviceAttachment(diskImage:)` — [Apple DiskImageKit](https://developer.apple.com/documentation/diskimagekit); macOS 27 release notes: "The vmnet port forwarding APIs now support port forwarding when communicating over loopback", plus fixes for saving VM state with USB devices passed through and for restore crashes after USB mass-storage hot-plug, and "The Accessory Access framework is not supported within a macOS virtual machine" (listed as fixed) — [Apple macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)
- Apple's macOS-27 sample uses `VZUSBPassthroughDeviceConfiguration`/`VZUSBPassthroughDevice` with `AAUSBAccessoryManager` (AccessoryAccess framework) to hot-attach USB devices, `VZVirtualMachineView.automaticallyReconfiguresDisplay = true` for dynamic resolution, `capturesSystemKeys`, and a new `VZVirtualMachineViewAdaptor`; the `InstallationTool` writes a `VM.bundle` containing `Disk.img`, `AuxiliaryStorage`, `MachineIdentifier`, `HardwareModel`, and `RestoreImage.ipsw` — [Apple sample](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)

**First-boot automation / provisioning (new in macOS 27)**
- `VZMacGuestProvisioningOptions` (macOS 27+) provides `fullName`, `username`, `password`, `logsInAutomatically`, `enablesRemoteLogin` (SSH); "macOS only evaluates these options on the first boot after restore", changes after start have no effect, and "This configuration requires guest macOS 27 or later to function properly. Earlier versions of macOS don't support the automated guest configuration protocol and ignore these settings." It is applied via `VZMacOSVirtualMachineStartOptions.setGuestProvisioning(_:)` — [Apple VZMacGuestProvisioningOptions](https://developer.apple.com/documentation/virtualization/vzmacguestprovisioningoptions); [Apple sample](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)
- Lume's pre-macOS-27 approach to unattended setup: install macOS from the IPSW, boot once so macOS writes first-boot state, stop, "mount the Data volume on the host and write the settings as plain files" (a `lume` user, SSH, autologin, no-sleep), then boot again until SSH responds; this "avoids depending on display timing or Setup Assistant layouts" — [Lume: how it works](https://cua.ai/docs/lume/concepts/how-lume-works.md); `lume create macos-tahoe --ipsw <path> --unattended tahoe` (presets `tahoe` verified end-to-end; `sequoia` may still show the Accessibility step of Setup Assistant, issue #2155); default SSH credentials `lume`/`lume` — [Lume README](https://github.com/trycua/cua/blob/main/libs/lume/README.md)
- SIP cannot be toggled by file edits because it is a Secure-Enclave-signed LocalPolicy; `lume sip on|off` performs three boots and drives `csrutil` in Recovery through a temporary VNC session with OCR (requires `vncdotool`) — [Lume: how it works](https://cua.ai/docs/lume/concepts/how-lume-works.md); [Lume manage VMs](https://cua.ai/docs/lume/guides/manage-vms.md)

**Licensing and the 2-VM cap**
- Apple's macOS licence section 2B(iii) permits the user "to install, use and run up to two (2) additional copies or instances of the Apple Software" in virtual environments, for software development, testing during development, macOS Server, or "personal, non-commercial use"; the framework enforces it: a third macOS guest fails with `VZErrorDomain Code 6: "The maximum supported number of active virtual machines has been reached."` — [Eclectic Light, 2022](https://eclecticlight.co/2022/08/04/virtualisation-on-apple-silicon-macs-8-how-apple-limits-vms/)
- The licence also forbids using virtualized copies "in connection with service bureau, time-sharing, terminal sharing or other similar types of services" and, per a secondary reading, excludes non-Apple hardware — [Eclectic Light, 2022](https://eclecticlight.co/2022/08/04/virtualisation-on-apple-silicon-macs-8-how-apple-limits-vms/); [Broadcom community thread](https://community.broadcom.com/vmware-cloud-foundation/discussion/macos-on-esxi-how-many-vms-am-i-allowed-to-run)
- Cirrus Labs: "Apple's EULA only allows 2 additional VMs per host" and this "cannot be solved easily without Apple's involvement" — [Cirrus Labs blog](https://cirrus-ci.org/blog/2022/07/07/isolating-network-between-tarts-macos-virtual-machines); Lume docs: "up to two macOS guests at a time, which is Apple's limit" — [Lume overview](https://cua.ai/docs/lume); Crow CI: "Apple's macOS licence and Virtualization.framework both cap a host at two running guests" — [Crow CI docs](https://crowci.dev/dev/configuration/env-vars/backend-tart/)
- Apple's framework also detects clones: starting a second copy of the same VM files while one is running makes the framework "automatically construct a new identity for the second clone", forcing iCloud re-authentication — [Apple: Using iCloud with macOS VMs](https://developer.apple.com/documentation/virtualization/using-icloud-with-macos-virtual-machines)

**iCloud / Apple Account in guests**
- Apple: "In macOS 15 and later, Virtualization supports access to iCloud accounts and resources when running macOS in a virtual machine (VM) on Apple silicon. When you create a VM in macOS 15 from a macOS 15 software image (an .ipsw file) using a VZMacHardwareModel that you obtain from a VZMacOSRestoreImage, Virtualization configures an identity for the VM that it derives from security information in the host's Secure Enclave." Moving the VM to another Mac creates a new identity and requires re-authentication; "Using a macOS 15 installer to upgrade an older VM doesn't provide support for iCloud." — [Apple: Using iCloud with macOS VMs](https://developer.apple.com/documentation/virtualization/using-icloud-with-macos-virtual-machines)
- Apple engineer: this "requires macOS 15 as both the guest and the host" — [Apple Developer Forums thread 707682](https://developer.apple.com/forums/thread/707682?page=6)
- What works in a Sequoia-or-later VM: iCloud Drive, Keychain in iCloud (incl. Passwords.app and passkeys), shared iCloud databases (calendars/contacts), Shared iCloud Photos, CloudKit; what does not: App Store — "apps obtained from the App Store that check the current user is entitled to run them will fail to open" — [Eclectic Light, 2024](https://eclecticlight.co/2024/07/12/sequoia-virtualisation-and-apple-id/); Parallels confirms "signing into the Mac App Store from within the virtual machine is still not supported" and that Sonoma/earlier cannot sign in at all — [Parallels KB 131160](https://kb.parallels.com/en/131160)

**Display, GPU, headless operation**
- `VZVirtualMachineView` "automatically resizes the virtual machine display when the window size changes, and captures system keys such as the Globe key" — [Apple sample](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)
- Headless hosts (macOS 15+): "Virtualization.Framework needs an unlocked login.keychain when a VM runs"; otherwise VMs fail with errors like "Failed to generate keypair" — workarounds are auto-login via Screen Sharing or `security unlock-keychain` — [Tart FAQ](https://tart.run/faq/)
- Lume supports `--display none`/`--no-display` (headless), `--display vnc` (Screen Sharing instead of native viewer), `--vnc disabled`, `--vnc-port`, `--vnc-password`, `--detach` (logs in `~/Library/Logs/lume/`), and `lume attach` to reopen a viewer — [Lume manage VMs](https://cua.ai/docs/lume/guides/manage-vms.md)
- Lume documents a "GPU passthrough" guide ("Unlock a tested Metal capability profile for one workload inside a Lume macOS VM") — [cua docs index](https://cua.ai/docs/llms.txt)
- Linux guests "lose out on GPU and display support" compared with macOS guests (author reply) — [Eclectic Light, 2022](https://eclecticlight.co/2022/08/04/virtualisation-on-apple-silicon-macs-8-how-apple-limits-vms/)

**Networking in guests**
- Tart: default NAT lets a guest reach host services bound to 0.0.0.0 via the router IP; `--net-softnet` adds stricter isolation (VMs cannot reach the host); `--net-bridged` requires `tart ip --resolver=arp`; NAT subnet changeable via `Shared_Net_Address`/`Shared_Net_Mask` defaults; the macOS "Local Network" pop-up is triggered by host tools (e.g., Packer), not Tart — [Tart FAQ](https://tart.run/faq/)
- Cirrus Labs (2022): "Virtualization.Framework's NAT networking lacks proper isolation" — the reason they built softnet — [Cirrus Labs blog](https://cirrus-ci.org/blog/2022/07/07/isolating-network-between-tarts-macos-virtual-machines)

**Tooling: UTM**
- UTM downloads the latest compatible macOS IPSW automatically if none is selected and warns against third-party IPSW sites; guest tools for clipboard are Spice `spice-vdagent` — [UTM macOS guest docs](https://docs.getutm.app/guest-support/macos/)
- UTM 4.6.0 beta enabled nested virtualization by default for Linux VMs on macOS 15 with M3+ (secondary report) — [libkrun issue 375](https://upd.dev/containers/libkrun/issues/375)

**Tooling: Tart**
- Tart stores VM images in OCI registries; `tart clone ghcr.io/cirruslabs/macos-tahoe-base:latest tahoe-base`, `tart run`, `tart ip`, `ssh admin@$(tart ip ...)` (default credentials `admin`/`admin`), `tart create --from-ipsw=latest`, `tart push`/`tart pull`/`tart login` (credentials in Keychain), defaults 2 CPUs / 4 GB / 1024x768, `--dir=name:~/path[:ro]` with macOS guests seeing shares at `/Volumes/My Shared Files/<name>` (host and guest macOS 13+) — [Tart quick start](https://tart.run/quick-start/)
- VMs live in `~/.tart/vms/`, pulled OCI images in `~/.tart/cache/OCIs/`; automatic pruning of least-recently-used images; Tart "uses the same underlying technology as Anka 3.0"; Orchard is the cluster controller — [Tart FAQ](https://tart.run/faq/)
- Tart claims 25,000+ installations and offers Packer, GitLab Runner, Buildkite and GitHub Actions integrations — [tart.run](https://tart.run/)

**Tooling: Lume / c-ua**
- Lume requirements: Apple silicon, macOS 13+, 8 GB free RAM (16 GB for an 8 GB guest), ~50 GB disk per macOS guest; it exposes "one VM store through the lume CLI, a local HTTP API, and an MCP server"; the cua SDK "installs and drives Lume for local macOS sandboxes" — [Lume overview](https://cua.ai/docs/lume)
- Images: `lume pull macos-tahoe-vanilla:latest` defaults to registry `ghcr.io`, organization `trycua`; images are OCI-compliant with the disk split into 512 MB chunks (`--chunk-size-mb`, `--single-layer`, `--legacy` LZ4 format); `lume ipsw` prints the latest supported restore-image URL; `lume images`, `lume prune` — [Lume images CLI](https://cua.ai/docs/lume/reference/cli/images.md)
- VM operations: `--shared-dir ~/Projects[:ro]` mounts at `/Volumes/My Shared Files`; `lume clone` copies `disk.img` and `nvram.bin` together ("Never copy one without the other"); `lume set --disk-size` grows only, transactional with rollback, refuses FileVault guests; store at `~/.lume`; `lume shutdown`/`restart` are graceful over SSH — [Lume manage VMs](https://cua.ai/docs/lume/guides/manage-vms.md); [Lume: how it works](https://cua.ai/docs/lume/concepts/how-lume-works.md)
- HTTP API: the installer runs `lume serve` at login on port 7777 (localhost only; `GET http://localhost:7777/lume/vms`); `lume serve --mcp` exposes an MCP server over stdio whose tools can list/create/run/stop/clone/resize VMs and run SSH commands — [Lume serve API](https://cua.ai/docs/how-to-guides/lume/serve-api)
- Lume telemetry is on by default (pseudonymous, PostHog EU), excludes VM names/paths/commands, controllable with `lume config telemetry` or `LUME_TELEMETRY_ENABLED` — [Lume: how it works](https://cua.ai/docs/lume/concepts/how-lume-works.md)

**How c/ua runs computer-use agents inside macOS VMs**
- Current flow: host needs Apple silicon + macOS 14+, ~40 GB disk, 8 GB free RAM; `cua sb create macos --name mac` maps to `ghcr.io/trycua/macos:26` (Tahoe; `macos:sequoia` → `:15`); first create pulls a 23 GB image (~8 min), later creates clone it in ~25 s; `cua sb exec`, `cua sb screenshot`, `cua sb view` (HTML5 viewer via short-lived ticket) — [cua: create a local macOS sandbox](https://cua.ai/docs/start-here/create-a-local-macos-sandbox.md)
- Guest side: "On Tahoe, cua-spacesd starts at login and handles exec, screenshots, and the viewer" (viewer URL uses port 3211); on Sequoia images spacesd is absent and `exec` runs over `lume ssh`, screenshots over VNC, `view` via `lume attach`; "On Tahoe, the image comes with screen and accessibility permissions already granted" — [cua: create a local macOS sandbox](https://cua.ai/docs/start-here/create-a-local-macos-sandbox.md); `cua-spacesd` is "an in-sandbox daemon on port 3211 that provides processes, files, screenshots, and input over gRPC" — [trycua/cua README](https://github.com/trycua/cua)
- The older components `cua-computer`, `cua-computer-server`, `cua-agent`, `cua-som` are listed as deprecated/no longer maintained; the legacy Computer Server exposed `ws://localhost:8000/ws` with JSON `{command, params}` messages (cloud containers used port 8443 with auth) — [trycua/cua README](https://github.com/trycua/cua); [cua Computer Server WebSocket API](https://cua.ai/libraries/computer-server/WebSocket-API); earlier quickstarts used `lume run macos-sequoia-cua:latest` — [cua quickstart](https://cua.ai/docs/get-started/quickstart)
- The Cua Driver automates macOS apps "in the background" using AppKit, Accessibility, Quartz/HID and ScreenCaptureKit: windows on other Spaces are addressed by exact `CGWindowID` so "the user's current Space, frontmost app, and keyboard focus don't change"; element recovery checks only the first 2,000 accessibility element IDs; it "Needs Accessibility and Screen Recording"; Electron, Tauri, AppKit, SwiftUI and WKWebView are listed as covered; Chrome keeps trusted pointer input in the background while Safari/Firefox return a clean refusal; the ScreenCaptureKit filter that hides the agent cursor needs macOS 14+ — [Cua Driver platform support](https://cua.ai/docs/cua-driver/concepts/platform-support.md)
- Licensing: most of the cua repo (SDK, Driver, Lume) is MIT; Cua Spaces and Driver Bench are FSL-1.1-MIT; `cua-som` is AGPL-3.0; the `cua-perception` extension carries AGPL-3.0 obligations — [trycua/cua README](https://github.com/trycua/cua)

**Tooling: VirtualBuddy**
- Free, open-source GUI for Apple silicon; host macOS 13+; built-in wizard downloads restore images from Apple (or local/custom IPSW URL); Linux from ISO; supports Recovery mode (e.g., disable SIP), networking/file sharing, clipboard sharing, save/restore state for macOS VMs; `VirtualBuddyGuest` app auto-mounts as a disk image and (latest version, macOS 14+) provides clipboard sharing and automatic mounting of shared folders (macOS 13 legacy guest app: shared folders only); APFS cloning duplicates VMs with almost no extra disk; running a macOS 27 ("Golden Gate") beta guest on a macOS 26 host requires VirtualBuddy 2.2 beta 2+ and Apple's device support files — [VirtualBuddy](https://github.com/insidegui/VirtualBuddy)

**Tooling: Anka (Veertu)**
- Anka is "macOS virtualization and Build Cloud tools for DevOps and CI/CD teams", built on Apple's native hypervisor stack, with a Virtualization CLI (`anka create`, `anka run`, `anka cp`, start/stop/clone/suspend), a Build Cloud Controller and a Registry for templates/tags; "On Apple Silicon, suspended VMs cannot move between hosts" — [Anka docs](https://docs.veertu.com/anka/what-is-anka/); Tart says it uses the same underlying technology as Anka 3.0 — [Tart FAQ](https://tart.run/faq/)

### Inferences
- A Swift app can implement "a Mac inside the app" end-to-end with public API: `VZMacOSRestoreImage.fetchLatestSupported` → `VZMacOSInstaller` into an ASIF/RAW `Disk.img` plus `VZMacAuxiliaryStorage`, persist `VZMacHardwareModel` and `VZMacMachineIdentifier`, then on macOS 27 hosts with a macOS 27 IPSW pass `VZMacGuestProvisioningOptions` (admin user, auto-login, SSH) at first start, use a VirtioFS share to drop the agent binary in, and finish provisioning over SSH/vsock. For macOS 26-or-older guests, the Lume technique (mount the guest's Data volume on the host between boots and write plist/user records) is the proven no-GUI alternative; GUI-driving Setup Assistant via VNC/OCR is the fallback (which Lume still needs only for SIP changes).
- The two-guest cap means an agent product should budget exactly one "sandbox Mac" per user (leaving headroom for the user's own VM tooling), and should never fan out per task; per-task isolation inside the guest should come from DiskImageKit overlay layers (macOS 27) or APFS clones, not extra VMs.
- Because iCloud works only in VMs created from macOS 15+ IPSWs on macOS 15+ hosts and the App Store never works, a sandbox Mac can access the user's iCloud Drive/Keychain/Contacts/Calendars after an in-guest sign-in, but cannot run paid App Store apps; plan on copying first-party apps and installing third-party apps from direct downloads.
- Distributing a pre-provisioned guest as an OCI image (Lume/Tart style, ~20+ GB, ~8 minutes to pull) is the fastest path to a "ready sandbox" UX; building from IPSW on first run is slower but avoids shipping macOS images (licensing-sensitive).
- Headless operation in a background agent (LaunchAgent) must run in a logged-in session with an unlocked login keychain, otherwise the framework fails to start VMs.
- The `com.apple.vm.networking` restriction means a third-party app should design around NAT (plus vsock or VirtioFS for host↔guest control), not bridged networking.

## Key Question 2: Linux sandboxes on macOS for code execution (Apple `container`/Containerization, Docker Desktop, OrbStack, Lima/Colima, Podman) — startup, file sharing, networking, egress control, per-task ephemerality, rootless

### Takeaway
Apple's `container`/Containerization (macOS 26+ only, one lightweight VM per container, vminitd over vsock, "sub-second" starts) is the most isolation-friendly option for per-task sandboxes but is young and macOS-26-gated; Docker Desktop/OrbStack/Colima/Podman are mature shared-VM designs where per-task isolation is a container, not a VM. None of them ships an application-level egress allowlist; Anthropic's `sandbox-runtime` (Seatbelt + local proxies with domain allowlists) is the only tool found that provides egress control natively on macOS, and it is not a VM boundary.

### Cited Findings

**Apple Containerization / `container`**
- Containerization is "a Swift package for running Linux containers on macOS" on Apple silicon; "Each container runs in its own lightweight VM"; `vminitd` "is the initial process in the VM" exposing "a gRPC API over vsock" for runtime configuration, process launch, I/O, signals and events; "Containers achieve sub-second start times using an optimized Linux kernel configuration"; functionality tested from kernel 6.14.9; supports linux/amd64 via Rosetta 2; requirements macOS 26, Xcode 26, Apple silicon ("Older versions of macOS are not supported"); Apache-2.0 — [apple/containerization](https://github.com/apple/containerization)
- The `container` CLI is "Supported only on macOS 26. We do not support older versions of macOS"; consumes/produces OCI images; release versions are product versions, not semver; `container-apiserver` XPC API preserves compatibility within a major; experimental `k8s` subcommand — [apple/container README](https://github.com/apple/container/blob/main/README.md)
- Architecture: `container-apiserver` launch agent (`container system start`), `container-core-images` (content store), `container-network-vmnet` (virtual network), `container-runtime-linux` per container; integrates Virtualization framework, vmnet, XPC, launchd, Keychain (registry credentials), unified logging; on macOS 15 the default CIDR was 192.168.64.1/24 with no container-to-container communication and no `container network` commands; memory: "the Virtualization framework's partial ballooning means freed guest memory is not returned to the host" — [apple/container technical overview](https://github.com/apple/container/blob/main/docs/technical-overview.md)
- The how-to index (for main / release 0.4.1) covers CPU/memory limits and overcommit, `container stats`, bind mounts, named volumes, tmpfs, DNS-based container names, container-to-container connectivity, port forwarding, custom MAC addresses, isolated networks, SSH-agent forwarding, reaching Mac-hosted services, ulimits, Linux capabilities, masked/read-only paths, nested virtualization, custom init, multiplatform builds, "container machines" (persistent Linux environments with your home directory mounted), and local Kubernetes clusters — [apple/container how-to](https://github.com/apple/container/blob/main/docs/how-to.md)
- Third-party summaries describe vminitd handling IP assignment, filesystem mounting (EXT4 block devices) and process supervision, and static Linux binaries built with Swift's Static Linux SDK/musl; one blog's "under 350 ms" boot figure is uncited — [InfoQ](https://www.infoq.com/news/2025/06/apple-container-linux); [pyshine blog](https://pyshine.com/Apple-Container-Lightweight-VMs-Linux-Containers-macOS/)

**Docker Desktop**
- Supports the current macOS major and the two previous majors; needs 4 GB RAM; Rosetta 2 recommended on Apple silicon (`softwareupdate --install-rosetta`); the `--backend=docker-vmm` flag selects the Docker VMM engine, "the only supported value on Mac"; free for personal use, education, non-commercial open source and businesses under 250 employees and under $10M revenue, paid otherwise and for government — [Docker Desktop Mac install](https://docs.docker.com/desktop/setup/install/mac-install/)
- OrbStack's comparison (January 2025, Docker Desktop 4.37.2) marks Docker Desktop as lacking fast startup, dynamic memory ("Can't release memory"), two-way file sharing, container domain names and IPv6; both support bind mounts, Rosetta, localhost forwarding, VPN compatibility and proxies — [OrbStack vs Docker Desktop](https://docs.orbstack.dev/compare/docker-desktop)

**OrbStack**
- Vendor claims: native macOS app, "Fast startup", "Memory on demand"/"Dynamic memory", two-way file sharing, volume and image file access, container domain names with automatic HTTPS, IPv6, Kubernetes ClusterIP/LoadBalancer access — [OrbStack vs Docker Desktop](https://docs.orbstack.dev/compare/docker-desktop); its benchmarks page (late August 2023, M1 Max, OrbStack 0.17.0 vs Docker Desktop 4.22.0) presents build-time and battery results only as images, with power estimated from the kernel's per-process-group energy counter — [OrbStack benchmarks](https://docs.orbstack.dev/benchmarks)
- Blog claims of "2-second startup" and "up to 10x faster" are vendor/blog figures without independent methodology — [Setapp review](https://setapp.com/app-reviews/docker-desktop-alternatives-for-mac); [sliplane blog](https://frontend.sliplane.io/blog/orbstack-vs-docker)

**Lima / Colima**
- Lima: VZ (Virtualization.framework) "has been the default driver for macOS hosts since Lima v1.0" on macOS 13.5+ for new instances; vz requires Lima ≥ 0.14 and macOS ≥ 13.0; Virtualization.framework cannot run Intel guests on ARM (use QEMU for a full Intel VM; VZ+Rosetta for Intel userspace only); `legacyBIOS` unsupported — [Lima VM types](https://lima-vm.io/docs/config/vmtype/); [Lima vz driver](https://lima-vm.io/docs/config/vmtype/vz/)
- Colima: runtimes Docker (default), containerd (nerdctl), Incus; `--vm-type=vz --vz-rosetta` (Colima ≥ 0.5.3, macOS 13+, Apple silicon); `krunkit` for GPU-accelerated AI workloads (macOS 13+); defaults 2 CPUs / 2 GiB / 100 GiB; "Automatic Port Forwarding"; Incus VMs require M3+ — [Colima README](https://github.com/abiosoft/colima)

**Podman**
- `podman machine init` is "Rootless only" by default (`--rootful` opt-in); `--provider` overrides the default where multiple providers exist (example `applehv`); volume mounts use 9p and "on macOS the default security model is none so that symlinks work" (e.g., `-v "$HOME/git:$HOME/git:ro,security_model=none"`); default mount `$HOME:$HOME` from containers.conf; user-mode networking via gvproxy — [podman-machine-init man page](https://docs.podman.io/en/latest/markdown/podman-machine-init.1.html); Podman 5.0 removed the qemu provider on macOS "in favor of the more performant Apple hypervisor" — [Podman 5.0 blog](https://blog.podman.io/2024/03/podman-5-0-breaking-changes-in-detail/)

**Egress control / process sandboxing without a VM**
- Anthropic's `sandbox-runtime` (`srt`, beta research preview) enforces filesystem and network restrictions at the OS level: on macOS via `sandbox-exec` with dynamically generated Seatbelt profiles whose network rule allows connections only to a localhost proxy port; on Linux via bubblewrap + seccomp with the network namespace removed; traffic flows through an HTTP(S) proxy and a SOCKS5 proxy with `allowedDomains`/`deniedDomains` (wildcards, optional `:port`), DNS-rebinding guards against loopback/link-local/metadata addresses, Unix sockets blocked by default (`allowUnixSockets` on macOS), reads deny-then-allow, writes allow-only, `allowAppleEvents` and `enableWeakerNetworkIsolation` flagged as known escape paths; defaults with no settings file are no network, no writes outside default paths, unrestricted reads; usable as a library (`SandboxManager.wrapWithSandbox`) and to wrap MCP servers — [anthropic-experimental/sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)
- Lume VMs can also be used as Linux sandboxes (it "Runs Linux guests") and cua offers a gVisor container sandbox (`cua sb create ubuntu`) — [Lume overview](https://cua.ai/docs/lume); [trycua/cua README](https://github.com/trycua/cua)

### Inferences
- For per-task ephemeral sandboxes on macOS 26/27, Apple `container` is the best fit on isolation (VM per container, dedicated IP, OCI images, rootless-by-design launch agent) — but it is a macOS 26+ dependency, so an app that must support macOS 15 needs a fallback (Colima/Lima or Docker Desktop) or a bundled Lima-style VM of its own.
- Mature shared-VM tools are better for a long-lived "dev container" with the user's home mounted; their per-task isolation is only as strong as Linux namespaces. Rootless defaults: Podman machine (rootless), Apple `container` (launch agent, no root), Docker Desktop (root in VM, user-mode on host).
- No container tool found provides domain-level egress filtering; implement egress policy either outside the VM (e.g., a host-side proxy plus a NAT-only guest, modelled on `srt`'s proxy design) or inside the guest (iptables/nftables in the image), and treat Seatbelt-based `srt` as a complement for host-side tool processes, not as a substitute for VM isolation.
- Startup budgets: Apple's "sub-second" per-container claim is unbenchmarked publicly; design UX to tolerate seconds for the first container (image pull, VM boot) and reuse warm VMs/containers for interactive loops.

### Gaps
- No independent, reproducible startup-time or file-sharing-throughput benchmarks for Apple `container`, OrbStack, Colima or Podman were found; OrbStack's own numbers are images only.
- apple/container specifics (virtiofs vs block volumes, `--user`, exact DNS/port-forward syntax, macOS 26 vs 27 differences) were not retrievable beyond the how-to index.
- Podman's current default provider on macOS (applehv vs libkrun) and its virtiofs status could not be confirmed (man page is provider-agnostic; search budget exhausted).

## Key Question 3: Controlling macOS apps — Accessibility API, CGEvent input, ScreenCaptureKit, building an AX-tree snapshot for an LLM, AppleScript/JXA/Shortcuts/App Intents, macOS 26/27 changes, TCC permissions and how Electron/Swift apps request them, and UX pitfalls

### Takeaway
The proven agent stack is: AX tree walk (`AXUIElementCopyAttributeValue`/`AXUIElementCopyActionNames`/`AXUIElementPerformAction`, with `AXManualAccessibility` to wake Electron trees) for structure and actions, `CGEventPost` for input (needs Accessibility; listen-only taps need Input Monitoring), ScreenCaptureKit for screenshots (needs Screen & System Audio Recording and triggers macOS 15's monthly re-consent unless you use `SCContentSharingPicker` or the Apple-approved Persistent Content Capture entitlement), plus Apple Events (needs the hardened-runtime `com.apple.security.automation.apple-events` entitlement and `NSAppleEventsUsageDescription`) and `shortcuts run` for app-specific actions. TCC grants are keyed to code signature + bundle ID + path, so unsigned/ad-hoc Electron dev builds lose grants on every rebuild; macOS 27 additionally removes direct TCC-database access and denies cross-team container reads by default.

### Cited Findings

**Accessibility API (AXUIElement) and tree snapshots**
- A snapshot walker starts from the app element created from the PID and recurses through children reading `AXRole`, subrole, `AXTitle`, `AXValue`, `AXDescription`, `AXIdentifier`, `AXEnabled`, `AXFocused`, position (`AXPosition`) and size (`AXSize`), and action names from `AXUIElementCopyActionNames` (e.g., `AXPress`, `AXConfirm`, `AXCancel`, `AXRaise`, `AXShowMenu`); "Not all attributes exist on every element"; default `maxDepth` 5 (commands default to 5–8 levels) because deep trees are costly; access is checked with `AXIsProcessTrusted()` and prompted with `AXIsProcessTrustedWithOptions`, and without Accessibility permission "all commands will fail with accessDenied" — [agent-native: accessibility tree](https://mintlify.wiki/ericclemmons/agent-native/concepts/accessibility-tree)
- agent-native assigns `@n1`, `@n2`… refs to interactive elements, offers JSON output and screenshots as a fallback when the AX tree is sparse (inspired by Vercel's agent-browser) — [agent-native docs](https://www.mintlify.com/ericclemmons/agent-native); agent-desktop derives deterministic element references and uses "progressive skeleton traversal" (shallow overview, drill down) to cut tokens, macOS 13+ — [agent-desktop](https://www.sourcepulse.org/projects/29132745); CAM (OpenClaw plugin) returns roles, labels, coordinates and actions "with no screen recording needed, only the Accessibility permission" and notes partial Electron support — [Aziily/CAM](https://github.com/Aziily/CAM); axmcp exposes AX + OCR + pointer/keyboard over MCP — [tmc/axmcp](https://pkg.go.dev/github.com/tmc/axmcp@v0.2.0); axterminator uses a cached BFS over the AX tree with a vision fallback and "relies on an undocumented behavior of AXUIElementPerformAction" — [axterminator](https://docs.rs/crate/axterminator/0.10.2)
- Electron/Chromium apps enable their accessibility tree only when assistive tech is detected or `app.setAccessibilitySupportEnabled(true)` is called; third-party tools can force it on by setting the `AXManualAccessibility` attribute on the app's AXUIElement (created from its PID) with `AXUIElementSetAttributeValue` — [Electron accessibility tutorial](https://www.electronjs.org/docs/latest/tutorial/accessibility)
- Background automation details from a shipped agent driver: macOS omits windows on other Spaces from an app's AX window list, so the driver targets windows by exact `CGWindowID`; element lookup is capped at the first 2,000 AX element IDs; Electron "Typed mutation works while one native window maps to one page"; some background scroll/drag shapes refuse; minimized windows don't accept keyboard commits — [Cua Driver platform support](https://cua.ai/docs/cua-driver/concepts/platform-support.md)

**Input injection (CGEvent) and permissions**
- Apple DTS: posting and listening use different TCC services, each with CG "request" and "preflight" helpers (e.g., `CGPreflightListenEventAccess`); listen-only work doesn't need full Accessibility — [Apple Developer Forums 735204](https://developer.apple.com/forums/thread/735204); a default (active) `CGEventTap` triggers the Accessibility prompt while a listen-only tap triggers Input Monitoring — [Apple Developer Forums 122492](https://developer.apple.com/forums/thread/122492); DTS: Accessibility grants both posting and listening, Input Monitoring only listening — [Apple Developer Forums 828052](https://developer.apple.com/forums/thread/828052)
- Sandboxed (App Store) apps can use Input Monitoring via `CGEventTap`, but "general Accessibility APIs are not supported in sandboxed apps without temporary exception entitlements" — [Apple Developer Forums 780626](https://developer.apple.com/forums/thread/780626); revoking Accessibility while a default event tap is active can stop system-wide input — [Apple Developer Forums 844416](https://developer.apple.com/forums/thread/844416)

**Screenshots: ScreenCaptureKit and the recurring prompt**
- ScreenCaptureKit (macOS 12.3+) streams displays/apps/windows as `CMSampleBuffer`s; `SCContentSharingPicker` is "the recommended approach for letting people select content sources"; "Request screen recording permission from the person before capturing content… add a `NSScreenCaptureUsageDescription` key"; single frames via `SCScreenshotManager`; the framework page links the `com.apple.developer.persistent-content-capture` entitlement — [Apple ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit)
- Persistent Content Capture entitlement (macOS 14.4+) "indicates whether a Virtual Network Computing (VNC) app needs persistent access to screen capture"; you must submit Apple's request form before using it — [Apple Persistent Content Capture](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.persistent-content-capture); DTS calls it a managed capability you must be granted — [Apple Developer Forums 778616](https://developer.apple.com/forums/thread/778616)
- macOS 15: Apple moved from weekly to monthly re-approval in beta 6, dropped the per-reboot prompt, the dialog says the app wants "to bypass the system private window picker and access the screen and audio directly" with an "Allow For One Month" button; developers report ScreenCaptureKit apps are affected — [9to5Mac, Aug 2024](https://9to5mac.com/2024/08/14/macos-sequoia-screen-recording-prompt-monthly/); macOS 15.1 beta 6 notes: "Users will see fewer dialogs if they regularly use apps in which they have already acknowledged and accepted the risks" — [9to5Mac, Oct 2024](https://9to5mac.com/2024/10/07/macos-sequoia-screen-recording-popups/)
- macOS 26.1: plain (non-bundled) executables still get prompted and can capture after approval but "never show up in the UI list" under Screen & System Audio Recording — [Apple Developer Forums 807898](https://developer.apple.com/forums/thread/807898); a developer reports ScreenCaptureKit permissions "being reset after every build" until switching to a stable signing identity — [Apple Developer Forums 818415](https://origin-devforums.apple.com/forums/thread/818415); a macOS 27 beta report describes a separate "Remote Desktop" entry in System Settings distinct from Screen & System Audio Recording (unanswered thread) — [Apple Developer Forums 841530](https://developer.apple.com/forums/thread/841530)
- Electron: `desktopCapturer` requires Screen Recording consent on macOS 10.15+ (check with `systemPreferences.getMediaAccessStatus('screen')`); system-audio capture needs `NSAudioCaptureUsageDescription` (macOS 14.2+) and from Electron 39 uses Apple's CoreAudio Tap API by default with no fallback to the Screen & System Audio Recording permission (`disable-features=MacCatapLoopbackAudioForScreenShare` to opt out) — [Electron desktopCapturer](https://www.electronjs.org/docs/latest/api/desktop-capturer)

**Apple Events / AppleScript / JXA / Shortcuts / App Intents**
- The `com.apple.security.automation.apple-events` entitlement (macOS 10.7+) "indicates whether the app may prompt the user for permission to send Apple events to other apps"; not needed for same-team targets; enabled under Hardened Runtime → Resource Access → Apple Events — [Apple Events Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.automation.apple-events); DTS: notarized apps using Apple Events need both that entitlement and an `NSAppleEventsUsageDescription` Info.plist entry; sign nested code inside-out (avoid `--deep`) and use `notarytool` — [Apple Developer Forums 697470](https://developer.apple.com/forums/thread/697470)
- Apple's `shortcuts` CLI: `shortcuts run "Name"` (with `-i/--input-path`, `-o/--output-path`, `--output-type <UTI>`, pipe support, exit 0/1), `shortcuts list [-f Folder] [--folders]`, `shortcuts view`, `shortcuts sign`; shortcuts that prompt for input pause the CLI — [Apple Shortcuts CLI guide](https://support.apple.com/guide/shortcuts-mac/run-shortcuts-from-the-command-line-apd455c82f02/mac)
- WWDC25 App Intents: running actions directly from Spotlight on Mac is now supported; adopt `IndexedEntity` with `@Property(indexingKey:)` so Spotlight search filters intent parameters and Shortcuts auto-generates find actions; `SnippetIntent` for interactive snippets, `UndoableIntent`, `PredictableIntent`, `requestChoice(between:)`, `supportedModes` (background/foreground) — [WWDC25 session 275](https://developer.apple.com/videos/play/wwdc2025/275/)
- macOS 26 Tahoe adds Spotlight actions (hundreds of built-ins; developers surface more via App Intents), Shortcuts automations on Mac (time, folder changes, device connections, messages), and a "Use Model" action calling Apple Intelligence on-device/Private Cloud Compute/ChatGPT — [MacMost](https://macmost.com/how-to-use-spotlight-actions-in-macos-tahoe.html); [GSMArena](https://m.gsmarena.com/macos_tahoe_26_brings_overhauled_spotlight_shorcuts_and_live_activities_-news-68182.php)
- macOS 27 release notes: App Intents schema changes (`notes.createNote`/`updateNote` accept `AttributedString` names; `calendar.deleteEvents` renamed `calendar.deleteEvent`; AppEntity 10 MB cumulative size limit); Shortcuts "Use Model" on-device failures fixed; `SpotlightSearchTool` with Foundation Models needs a `.focused()` configuration for the on-device model's context window — [Apple macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)

**Platform changes affecting automation: macOS 26 and 27**
- macOS 26: Foundation Models framework (on-device LLM), Accessibility Nutrition Labels in the App Store, default minimum TLS raised to 1.2 for apps linked on macOS 26, `NSLog` dynamic strings redacted in unified logging, AGL removed — [Apple macOS 26 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-26-release-notes)
- macOS 27: "Apps can no longer access the local TCC database directly"; "Accessing files in other developer teams' app data containers and app group containers no longer prompts the user for authorization; such accesses are denied by default and can be managed by the user in Privacy & Security settings"; "XProtect may now restrict access to app data that is commonly targeted by malicious software"; in the Files & Folders pane "a process without a bundle ID cannot be granted access to specific app data containers" (workaround: Full Disk Access); `launchd` no longer loads plists carrying the quarantine xattr; background Neural Engine access needs `com.apple.developer.background-tasks.continued-processing.inference`; Rosetta is not auto-restored after upgrading and Intel apps stop running in macOS 28 — [Apple macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)

**TCC permission catalogue and how to request it (Swift vs Electron)**
- Accessibility: Swift `AXIsProcessTrustedWithOptions([kAXTrustedCheckOptionPrompt: true])` — [agent-native](https://mintlify.wiki/ericclemmons/agent-native/concepts/accessibility-tree); Electron `systemPreferences.isTrustedAccessibilityClient(prompt)` — [Electron systemPreferences](https://www.electronjs.org/docs/latest/api/system-preferences)
- Microphone/Camera: Electron `systemPreferences.askForMediaAccess('microphone'|'camera')` (resolves existing status without a new alert if already denied; app restart required after changing in System Settings) with `NSMicrophoneUsageDescription`/`NSCameraUsageDescription` in Info.plist; `getMediaAccessStatus('screen')` for Screen Recording — [Electron systemPreferences](https://www.electronjs.org/docs/latest/api/system-preferences)
- Speech Recognition: `SFSpeechRecognizer.requestAuthorization` / `authorizationStatus()` ("Asks the user to allow your app to perform speech recognition") — [Apple SFSpeechRecognizer](https://developer.apple.com/documentation/speech/sfspeechrecognizer)
- Calendars/Reminders: `requestFullAccessToEvents`, `requestWriteOnlyAccessToEvents`, `requestFullAccessToReminders` with `NSCalendarsFullAccessUsageDescription`/`NSCalendarsWriteOnlyAccessUsageDescription`/`NSRemindersFullAccessUsageDescription`; "all sandboxed macOS apps must include the `com.apple.security.personal-information.calendars` entitlement" — [Apple EventKit](https://developer.apple.com/documentation/eventkit/accessing-the-event-store); on macOS 14+ the request methods only show a dialog if the host bundle has the usage keys, otherwise bare Node calls resolve `false` silently — [eventkit-js README](https://cdn.jsdelivr.net/npm/eventkit-js@3.2.0/readme.md)
- Contacts: `CNContactStore.requestAccess(for: .contacts)`; "Your app crashes if you attempt to access contact data without a contacts usage description" (`NSContactsUsageDescription`); statuses include `.limited`; the contact `note` field needs the Apple-approved `com.apple.developer.contacts.notes` entitlement — [Apple Contacts](https://developer.apple.com/documentation/contacts/accessing-the-contact-store)
- Full Disk Access: "cannot be requested programmatically"; the user adds the app/terminal in System Settings → Privacy & Security — [imessage-query skill](https://playbooks.com/skills/terrylica/cc-skills/imessage-query); Desktop/Documents/Downloads access is separately gated for terminal/background processes ("If file reads or directory listings hang, grant access to the process that performs the file operations") — [OpenClaw mac permissions](https://cdn.jsdelivr.net/npm/openclaw@2026.7.1-2/docs/platforms/mac/permissions.md)
- Automation (Apple Events): triggered per target app on first send; needs entitlement + usage string (above) — [Apple Developer Forums 697470](https://developer.apple.com/forums/thread/697470); one Notes-automation integration notes macOS "requires explicit automation permission for one app to control another, and until you grant it in System Settings the server fails quietly" — [OpenClaw Apple Notes integration](https://rapidevelopers.com/openclaw-integrations/apple-notes)
- Notifications: `UNUserNotificationCenter.requestAuthorization(options:)` (see KQ5); Electron notifications require the app to be code-signed — [Electron Notification](https://www.electronjs.org/docs/latest/api/notification)
- Local Network: the macOS "Local Network" pop-up is triggered by host tools (e.g., Packer) and can be suppressed with `defaults write` entries for RFC 1918 ranges — [Tart FAQ](https://tart.run/faq/)

**UX pitfalls: grants reset, signing, notarization**
- "TCC ties a grant to the app's code signature, bundle identifier, and on-disk path"; ad-hoc signatures "generate a new identity every build", so macOS forgets grants and prompts can disappear until stale entries are cleared; fixes: sign with a real Apple Development/Developer ID certificate, keep bundle ID and install path fixed; recovery: remove the entry, relaunch from the same path, `sudo tccutil reset Accessibility <bundle id>`, `sudo tccutil reset ScreenCapture <bundle id>`, `sudo tccutil reset AppleEvents`, sometimes a reboot; grant Accessibility to a signed app/helper with its own bundle ID, never to a shared `node` binary ("Treat a node entry as broad permission for that entire Node runtime") — [OpenClaw mac permissions](https://cdn.jsdelivr.net/npm/openclaw@2026.7.1-2/docs/platforms/mac/permissions.md)
- Electron: macOS requires signing and notarization (10.15+); Electron Forge signs via `@electron/osx-sign` (`packagerConfig.osxSign` must exist even if empty; custom entitlements through `osxSign.optionsForFile` returning `{ entitlements: 'path.plist' }`) and notarizes via `@electron/notarize` with Apple ID + app-specific password + `teamId`, App Store Connect API key, or `notarytool store-credentials` keychain profile — [Electron Forge macOS signing](https://www.electronforge.io/guides/code-signing/code-signing-macos); `safeStorage`, `app.setLoginItemSettings()`, the `cookieEncryption` fuse and `autoUpdater` require a valid signature — [Electron code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)
- Hardened runtime: "add only the exceptions an app truly needs", entitlements belong on executables, not frameworks — [Apple hardened runtime](https://developer.apple.com/documentation/security/hardened-runtime.md)

### Inferences
- Snapshot format for the LLM: walk the focused window's subtree (depth ≤ 8, prune non-interactive containers), emit one line per element with a stable ref, role, title/value, enabled/focused flags, bounding box in screen points, and available actions; cache the ref→`AXUIElement` map per snapshot; fall back to a ScreenCaptureKit screenshot + coordinates only for sparse trees (WebViews, Electron without `AXManualAccessibility`, canvas apps). Prefer `AXUIElementPerformAction(AXPress)` and `AXUIElementSetAttributeValue(AXValue)` over synthetic clicks for reliability, with `CGEventPost` as the universal fallback.
- Permission ordering for onboarding: Accessibility first (unlocks AX + CGEvent posting + effectively Input Monitoring), then Screen & System Audio Recording (only when the vision fallback is needed, since it triggers monthly re-consent), then Automation per target app on first use, with Full Disk Access reserved for Messages/Mail database reads.
- Avoid the monthly screen-recording re-consent where possible by using `SCContentSharingPicker` for user-initiated captures or AX-only operation; the Persistent Content Capture entitlement is scoped to VNC apps and requires Apple's approval, so an AI agent is unlikely to qualify.
- For Electron, put the AX/CGEvent/ScreenCaptureKit/Apple-Events calls in a signed native helper or Swift XPC service with its own bundle ID so TCC grants are attributed to a stable identity rather than to Electron Helper processes or a shared Node runtime.
- For macOS 27, do not read `TCC.db` to display permission state; use the per-API preflight/status calls, and expect cross-team container reads (e.g., other apps' data) to be denied silently unless the user enables them.

### Gaps
- Apple's `AXUIElement.h` reference page could not be fetched (404 via the docs data endpoint); function names above are corroborated by third-party tools and Electron docs rather than Apple's symbol pages.
- The exact behavior of `CGPreflightPostEventAccess`/`CGRequestPostEventAccess` on current macOS was only found in forum reports.
- No Apple statement was found on macOS 26/27 changes to the Automation (Apple Events) prompt or to Accessibility TCC semantics; macOS 26 release notes contain no TCC items at all.
- Photos (PhotoKit) authorization and Local Network (`NSLocalNetworkUsageDescription`) on macOS 15+ were not researched (search budget exhausted).

## Key Question 4: Messages, Mail, Calendar, Reminders, Notes access from a third-party app

### Takeaway
Reading iMessage means opening `~/Library/Messages/chat.db` read-only with Full Disk Access and decoding `attributedBody` (an NSArchiver `typedstream` blob, mandatory since Ventura) — the Rust `imessage-exporter`/`crabstep` parser is the reference implementation, and heuristic regex decoders are fragile. Sending is AppleScript to Messages.app (reliable enough for text, worse for groups/new chats) or Shortcuts; richer features (reactions, typing, read receipts) require BlueBubbles-style code injection with SIP and Library Validation disabled, which is unsuitable for a consumer app. Calendar/Reminders and Contacts have first-party frameworks (EventKit with full-vs-write-only access, Contacts with limited access), while Mail and Notes are scriptable only through Apple Events.

### Cited Findings

**iMessage: reading chat.db**
- Since Ventura the `text` column is often empty and the body lives in `attributedBody`, "an Apple typedstream, the legacy NSArchiver format, which plistlib cannot read"; timestamps are nanoseconds since 2001-01-01 UTC; open connections read-only (`mode=ro`); the terminal/app needs Full Disk Access which "cannot be requested programmatically" — [imessage-query skill](https://playbooks.com/skills/terrylica/cc-skills/imessage-query); [imsg-mcp](https://pypi.org/project/imsg-mcp/)
- imessage-exporter parses message bodies and formatted ranges from `typedstream` with `crabstep`, handles edit history (edits before Ventura appear as normal messages), unsent messages, recovers recently deleted messages, groups handles by person using `person_centric_id` and Contacts, merges split chatrooms via `chat_lookup`, converts `CAF` and `AMR` audio messages to mp4, HEIC→JPEG, and embeds audio-message transcripts in HTML exports — [imessage-exporter features](https://github.com/ReagentX/imessage-exporter/blob/develop/docs/features.md); the `imessage-database` crate opens "a read-only connection" and probes the schema with `Capabilities::determine()` — [imessage-database README](https://github.com/ReagentX/imessage-exporter/blob/develop/imessage-database/README.md); the project supports "every iMessage feature as of macOS Golden Gate 27.0.1" and runs on macOS, Linux and Windows — [imessage-exporter](https://github.com/ReagentX/imessage-exporter)
- A widely used TypeScript MCP implementation queries `chat.db` with `sqlite3 -json`, selects `message.text` falling back to `hex(message.attributedBody)`, converts dates by dividing by 1e9 and adding the 1970→2001 offset, joins `attachment`/`message_attachment_join` for files, and decodes `attributedBody` with regexes ("heuristic parsing of an archive format, not a real deserializer, so it is fragile"), returning "[Message content not readable]" on failure; it checks DB access and prints Full Disk Access instructions but cannot request the permission — [apple-mcp message.ts](https://raw.githubusercontent.com/Dhravya/apple-mcp/main/utils/message.ts) (repo archived Jan 1, 2026 — [apple-mcp](https://github.com/Dhravya/apple-mcp))

**iMessage: sending**
- AppleScript send pattern: `tell application "Messages"`, pick the first service whose type is iMessage, `set targetBuddy to buddy <number>`, `send <text> to targetBuddy` — [apple-mcp message.ts](https://raw.githubusercontent.com/Dhravya/apple-mcp/main/utils/message.ts)
- BlueBubbles' server "uses AppleScript to perform simple functions like sending messages & attachments and creating chats" and "polls the chat.db database" for new messages; supports macOS Sierra+; Linux hosts run it only inside a macOS VM — [BlueBubbles server overview](https://docs.bluebubbles.app/server); "using Apple Script to send messages is much less reliable than using the Private API" — [BlueBubbles troubleshooting](https://docs.bluebubbles.app/server/troubleshooting-guides/cant-send-messages-from-bluebubbles)
- BlueBubbles Private API: Apple "doesn't let outside software access iMessage's internal code, such as for sending reactions, while SIP is enabled"; users must disable SIP and run `sudo defaults write /Library/Preferences/com.apple.security.libraryvalidation.plist DisableLibraryValidation -bool true`; the helper is injected into Messages.app; supports macOS 10.13+; on Apple silicon disabling SIP also disables running iOS apps; VM users should snapshot first — [BlueBubbles Private API installation](https://docs.bluebubbles.app/private-api/installation); the Rust toolkit imessage-rs likewise injects a dylib into Messages.app only with SIP disabled, while its AppleScript path needs no SIP change — [imessage-rs](https://docs.rs/imessage-rs)
- Shortcuts can be driven from scripts with `shortcuts run "Name" -i <input>` — [Apple Shortcuts CLI guide](https://support.apple.com/guide/shortcuts-mac/run-shortcuts-from-the-command-line-apd455c82f02/mac)

**Calendar and Reminders (EventKit)**
- "Your app can't request read-only access to either events or reminders. To read events or reminders from the event store, your app needs full access"; write-only access returns a single virtual calendar and no events; EventKitUI's chooser/editor runs out-of-process and "has full access to calendars on the device regardless of the access granted to your app" (iOS 17+); iOS 17+ denies requests if only the legacy `NSCalendarsUsageDescription` key is present; sandboxed macOS apps need `com.apple.security.personal-information.calendars` — [Apple EventKit](https://developer.apple.com/documentation/eventkit/accessing-the-event-store)
- A macOS 14.2.1 developer saw `requestFullAccessToReminders` return `false` with no prompt (not reproducible on iOS) — [Apple Developer Forums 745752](https://developer.apple.com/forums/thread/745752)

**Contacts**
- People can grant full or limited access; "Your app has automatic access to contacts it creates"; `.limited` status; `ContactAccessButton`/`contactAccessPicker` expand limited access without re-prompting; apps authorized in earlier OS versions keep full access — [Apple Contacts](https://developer.apple.com/documentation/contacts/accessing-the-contact-store)

**Mail.app scripting**
- A shipped integration controls Mail via AppleScript: `tell application "Mail" to return name` as an access probe (failure → user must enable Mail under Privacy & Security → Automation), iterates mailboxes checking `read status`, reads `subject`, `sender`, `date sent`, `content` (truncated to 300–500 chars), and sends with `make new outgoing message with properties {subject:…, content:…, visible:true}`, adding `to`/`cc`/`bcc` recipients then `send`; its search covers only `subject contains`, caps at 20 messages, and its unread/search functions actually return empty arrays (bugs) — [apple-mcp mail.ts](https://raw.githubusercontent.com/Dhravya/apple-mcp/main/utils/mail.ts)

**Notes scripting**
- Notes' AppleScript `body` property accepts HTML (`make new note with properties {name:…, body:"<h1>…"}`); JXA reads `body` back as HTML; requires Automation permission for the calling process — [macos-notes skill](https://skills.sh/vinitu/macos-notes-skill/macos-notes); [OpenClaw Apple Notes integration](https://rapidevelopers.com/openclaw-integrations/apple-notes)
- macOS 27 App Intents schemas for notes (`notes.createNote`, `notes.updateNote`, `notes.appendText`) and reminders exist for apps exposing their own notes/reminders to Siri, not for reading Apple Notes — [Apple macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)

### Inferences
- A consumer-grade agent should read Messages via a read-only SQLite connection plus a real typedstream decoder (port of `crabstep`/`pytypedstream` logic) and watch `chat.db` for changes (polling or FSEvents) — the BlueBubbles Private API path (SIP off, Library Validation off, dylib injection) is not shippable to normal users, and macOS 27's new restrictions on cross-team container access make such hacks riskier.
- Expect two separate TCC prompts for Messages: Full Disk Access (manual) for reading and Automation → Messages for sending. For Mail, Automation → Mail suffices for both read and send, but reading large mailboxes via Apple Events is slow (hence the 20-message caps in shipped code).
- Calendar/Reminders in an agent should request full access (read is impossible otherwise) and could optionally use EventKitUI's editor to avoid permissions for one-off event creation.
- Because Notes exposes HTML bodies via AppleScript, round-tripping rich notes is feasible; attachments and locked notes are not covered by any source here.

### Gaps
- No primary Apple documentation of the `chat.db` schema or of the `attributedBody` format exists; all details are from reverse-engineering projects.
- Whether macOS 26/27 changed Messages' database layout or Full Disk Access behavior was not found (imessage-exporter claims 27.0.1 support, implying continuity).
- Apple's Shortcuts "Send Message" action behavior from the CLI (confirmation prompts, group chats) was not verified (search budget exhausted).
- Mail.app scripting limits (performance, Automation prompt behavior on macOS 26/27) rest on one shipped integration's code, not Apple docs.

## Key Question 5: Notifications — UNUserNotificationCenter vs Electron Notification, actionable notifications, permissions, Focus modes, identity requirements

### Takeaway
Native `UNUserNotificationCenter` gives explicit/provisional authorization, categories with buttons and inline text replies, interruption levels (time-sensitive breaks through Focus on macOS 12+), and delegate callbacks; Electron wraps the same UNNotification API with `hasReply`, `actions`, `getHistory()` and events, but only for code-signed app bundles, and it exposes no explicit permission-request API. Critical alerts and (per Apple's session notes) communication-style Focus breakthrough need Apple-approved entitlements.

### Cited Findings
- `UNUserNotificationCenter.current().requestAuthorization(options: [.alert, .sound, .badge])` prompts once and records the response; adding `.provisional` grants quiet trial delivery (Notification Center history only, with Keep/Turn Off buttons) without a prompt, with status `.provisional` until the person decides; always check `notificationSettings()` before scheduling — [Apple: Asking permission to use notifications](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications)
- Actionable notifications: register `UNNotificationCategory` objects with `UNNotificationAction`s (unique identifiers, options such as destructive) via `setNotificationCategories`; use `UNTextInputNotificationAction` for inline typed replies; set `categoryIdentifier` on `UNMutableNotificationContent`; handle in `userNotificationCenter(_:didReceive:withCompletionHandler:)` by `response.actionIdentifier`, always calling the completion handler — [Apple: Declaring your actionable notification types](https://developer.apple.com/documentation/usernotifications/declaring-your-actionable-notification-types); typed text arrives in `UNTextInputNotificationResponse.userText` — [Apple UNTextInputNotificationResponse](https://developer.apple.com/tutorials/data/documentation/usernotifications/untextinputnotificationresponse.md)
- `UNNotificationInterruptionLevel.timeSensitive` (macOS 12+) "presents the notification immediately, lights up the screen, can play a sound, and breaks through system notification controls" such as Notification Summary and Focus; "The user can turn off the ability for time sensitive notification interruptions" — [Apple timeSensitive](https://developer.apple.com/documentation/usernotifications/unnotificationinterruptionlevel/timesensitive); WWDC21: Time Sensitive can break through Focus "if it has been allowed", while critical interruption "will continue to require an approved entitlement" — [WWDC21 10091 notes](https://www.wwdcnotes.com/notes/wwdc21/10091); HIG: "Never use the Time Sensitive interruption level to send a marketing notification" — [Apple HIG: Managing notifications](https://developer.apple.com/design/human-interface-guidelines/managing-notifications)
- Electron: "On MacOS, notifications use the UNNotification API"; "the app must be code-signed… Unsigned binaries will emit a failed event"; options `id` (→ UNNotificationRequest identifier), `groupId` (thread identifier), `subtitle`, `hasReply`/`replyPlaceholder`, `sound` (custom files in `Contents/Resources` or `~/Library/Sounds` etc.), `closeButtonText`, `actions`; events `show`, `reply` (`details.reply`), `action` (`details.actionIndex`), `failed`; `Notification.getHistory()` returns live objects for delivered notifications so handlers can be re-attached after restart (only `id`, `groupId`, `title`, `subtitle`, `body` populated; empty in unsigned dev builds); `remove(id)`, `removeAll()`, `removeGroup()`; `handleActivation()`, `toastXml`, `timeoutType`, `urgency` are not macOS — [Electron Notification](https://www.electronjs.org/docs/latest/api/notification)
- macOS 26 fixed washed-out Calendar notification icons; macOS 27 fixed "You might be unable to dismiss certain notifications" — [Apple macOS 26 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-26-release-notes); [Apple macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)

### Inferences
- A Swift (or Swift-helper) implementation is required for interruption levels, provisional authorization, categories registered at launch, and reliable delegate handling; Electron's wrapper covers buttons and inline reply but not interruption level or provisional/explicit authorization control.
- Notification identity is the app bundle's code signature/bundle ID: plain CLIs and unsigned dev builds cannot post UNNotifications; an Electron app must be signed even for local development testing of notifications.
- For an agent that needs to break through Focus (e.g., "task finished, needs approval"), use time-sensitive only when the user opts in, and consider communication notifications only if the Apple-approved entitlement and SiriKit intent donation are feasible.

### Gaps
- Apple's pages for the `com.apple.developer.usernotifications.time-sensitive` and `com.apple.developer.usernotifications.communication` entitlements returned 404 at the docs data endpoint, so whether time-sensitive needs only the Xcode capability (vs Apple approval) and the exact communication-notification requirements (INSendMessageIntent donation) are not confirmed here.
- Whether `UNUserNotificationCenter` works from an unbundled executable on macOS 26/27 was not verified (Electron's note implies a bundle + signature is required).
- No source covered macOS 26/27 changes to Focus filters or notification permission UX.

## Key Question 6: Dictation / on-device speech-to-text (SpeechAnalyzer, SFSpeechRecognizer, WhisperKit, Parakeet/FluidAudio/MLX, whisper.cpp, Moonshine) and text-to-speech for voice memos (AVSpeechSynthesizer/Personal Voice, Kokoro, Piper, ElevenLabs/OpenAI), including voice-note file formats

### Takeaway
On macOS 26+ Apple's `SpeechAnalyzer`/`SpeechTranscriber` is the default choice: fully on-device, system-managed models outside the app's memory, volatile+final results via async sequences, no one-minute limit, and reported ~2x faster than Whisper large-v3 on long files; `DictationTranscriber` covers older-model locales and custom vocabulary, and `SFSpeechRecognizer` (macOS 10.15+) remains the fallback with its one-minute/day-quota limits for server mode. For sub-second push-to-talk on any macOS 14+ Mac, FluidAudio's Core ML Parakeet (ANE, ~0.19 s on a short clip, 2.1–2.5% LibriSpeech WER) and WhisperKit (Core ML, macOS 14+) are the strongest open options. For TTS, `AVSpeechSynthesizer.write` produces PCM buffers (Personal Voice on macOS 14+ with authorization and non-commercial licence terms), Kokoro-82M (Apache-2.0, 24 kHz) runs on-device at ~23x real time via Core ML/MLX; voice notes must be encoded per channel — OGG/Opus for WhatsApp and Telegram, CAF for iMessage.

### Cited Findings

**Apple SpeechAnalyzer (macOS 26+)**
- `SpeechTranscriber` is available on iOS/iPadOS/macOS/tvOS/visionOS 26.0+ (`isAvailable`, `supportedLocales`, `installedLocales`, presets, `volatileResults`/`audioTimeRange` options, `results` async sequence) — [Apple SpeechTranscriber](https://developer.apple.com/documentation/speech/speechtranscriber); `DictationTranscriber` (26.0+) "uses the same speech-to-text machine learning models as system dictation features do, or as SFSpeechRecognizer does when it is configured for on-device operation", supports `AnalysisContext.contextualStrings` biasing, custom vocabulary via `SFSpeechLanguageModel`, and content hints such as `farField` — [Apple DictationTranscriber](https://developer.apple.com/documentation/speech/dictationtranscriber)
- WWDC25: transcription "runs entirely on device"; models are downloaded via `AssetInventory.assetInstallationRequest(supporting:)`, live in system storage, "don't increase app download size, storage, or runtime memory, and they run outside the app's memory space"; apps can hold a limited number of locales (`AssetInventory.allocatedLocales`/`deallocate`); results are timecoded on the audio timeline; volatile results are replaced by finalized ones; input is an `AsyncStream<AnalyzerInput>` fed from an `AVAudioEngine` tap converted to `SpeechAnalyzer.bestAvailableAudioFormat(compatibleWith:)`; designed for long-form/distant audio; the sample checks only microphone permission; no numeric latency given; not on watchOS — [WWDC25 session 277](https://developer.apple.com/videos/play/wwdc2025/277/); it powers Notes, Voice Memos and Journal and makes no network calls — [addpipe blog](https://blog.addpipe.com/apple-speechanalyzer-api/)

**SFSpeechRecognizer (macOS 10.15+)**

- Engine selection: macOS 26+ → `SpeechAnalyzer` + `SpeechTranscriber` (progressive live preset with `volatileResults` for push-to-talk UI; `DictationTranscriber` for custom vocabulary/older locales); macOS 14–15 → FluidAudio Parakeet (English/European, ANE, lowest latency) or WhisperKit (broad language coverage, Core ML); whisper.cpp/Moonshine remain cross-platform fallbacks. SFSpeechRecognizer should be the last resort because of its one-minute and quota limits and single-task-at-a-time on-device behavior.
- Push-to-talk UX: capture 16 kHz-ish mono via `AVAudioEngine`, feed buffers to the engine continuously (volatile partials), finalize on key-up; for Parakeet streaming use 320 ms chunks (FluidAudio's recommended operating point, ~5% WER vs ~8% at 160 ms).
- Voice memos: synthesize to PCM (`AVSpeechSynthesizer.write`, Kokoro, or cloud `pcm/wav`), then transcode with AVFoundation/ffmpeg per channel: OGG/Opus mono 48 kHz for WhatsApp/Telegram (`.ogg`, `audio/ogg`), CAF for iMessage; keep Telegram URL-sent voice notes under 1 MB. Avoid Personal Voice for anything that could be read as commercial use given the SLA language.
- Model residency: Apple's system-managed speech models cost the app nothing in RAM; Parakeet/Whisper models cost 0.3–4 GB of process memory and need ANE/Core ML warm-up (seconds on first launch), so pre-warm in the background.

## Key Question 7: Keychain — SecItem APIs, data-protection keychain, Touch ID access control, keychain-access-groups, Electron safeStorage internals, whether third-party apps can read Safari/Passwords.app credentials, and sanctioned alternatives

### Takeaway
Use the data-protection keychain (`kSecUseDataProtectionKeychain = true`, macOS 10.15+) for all agent secrets; gate high-value items with `SecAccessControlCreateWithFlags(.userPresence | .biometryCurrentSet)` plus `LAContext`, which on macOS requires a team-signed app with a keychain access group (otherwise `errSecMissingEntitlement -34018`). Electron's `safeStorage` is Chromium's OSCrypt: a random key in a login-keychain item named "<App> Safe Storage", so it is only as stable as the app's code signature. Third-party apps cannot read Safari/Passwords.app credentials — they live in Apple's data-protection keychain access groups and are brokered only through Credential Provider extensions (metadata without passwords; the system asks the extension to fill), passkeys via `ASAuthorizationPlatformPublicKeyCredentialProvider` (associated domains required), and, new in macOS 26, user-initiated Credential Exchange Protocol export/import (`ASCredentialExportManager`/`ASCredentialImportManager`).

### Cited Findings

**Core APIs and the data-protection keychain**
- `kSecUseDataProtectionKeychain` (macOS 10.15+): "indicates whether to treat macOS keychain items like iOS keychain items"; "It's highly recommended that you set the value of this key to true for all keychain operations… Use it unless you specifically need access to items previously stored in a legacy keychain in macOS"; `kSecAttrSynchronizable = true` items also behave like iOS items but sync via iCloud — [Apple kSecUseDataProtectionKeychain](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain)
- Access groups apply "to macOS keychain items when you query with the kSecUseDataProtectionKeychain key, set the item's kSecAttrSynchronizable attribute, or both"; an app's groups are `keychain-access-groups` entries, then the `application-identifier` (`com.apple.application-identifier` on macOS = team ID + bundle ID), then app groups; the first entry is the default group; items belong to exactly one group; using a group the app lacks fails with `errSecMissingEntitlement`; searching another group returns `errSecItemNotFound` — [Apple: Sharing access to keychain items](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)
- Accessibility classes (`kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` > `WhenUnlocked` (default) > `AfterFirstUnlock` > `Always`), `SecAccessControlCreateWithFlags(nil, kSecAttrAccessibleWhenUnlocked, .userPresence, &error)` to demand user presence, and `.applicationPassword` for an item-specific password — [Apple: Restricting keychain item accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility); `biometryCurrentSet` = Touch ID for currently enrolled fingers / Face ID for the enrolled user — [Apple SecAccessControlCreateFlags](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags.md)
- Touch ID recipe: create the access control with `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` + `.userPresence`, optionally pass an `LAContext` (`touchIDAuthenticationAllowableReuseDuration` up to 5 minutes) via `kSecUseAuthenticationContext`, add with `SecItemAdd`; on read, `SecItemCopyMatching` triggers the biometric prompt automatically (set `context.localizedReason`/`kSecUseOperationPrompt`), or pass `kSecUseAuthenticationUI = kSecUseAuthenticationUISkip` to skip protected items; the Secure Enclave returns only pass/fail; `NSFaceIDUsageDescription` is required for Face ID but "The system doesn't require a comparable usage description for Touch ID" — [Apple: Accessing Keychain Items with Face ID or Touch ID](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id)
- On macOS, `SecItemAdd` with `kSecAttrAccessControl` set to `.biometryCurrentSet` returned `-34018` (`errSecMissingEntitlement`) for an app whose `keychain-access-groups` was empty; the poster found that adding the Keychain Sharing capability made the error go away — [Apple Developer Forums 684453](https://developer.apple.com/forums/thread/684453); community notes: combining `.biometryCurrentSet` and `.devicePasscode` without a logical operator returns `errSecParam (-50)`, and setting both `kSecAttrAccessible` and `kSecAttrAccessControl` in one add query also yields `-50` — [swift-security keychain access control reference](https://tessl.io/registry/dpearson2699/swift-ios-skills/3.9.0/files/skills/swift-security/references/keychain-access-control.md)

**Electron safeStorage**
- On macOS keys are stored "in Keychain Access… in a way that prevents other applications from loading them without user override"; synchronous calls "can block the current thread to collect user input"; `isEncryptionAvailable()` is true when the Keychain is available; the async API (`encryptStringAsync`/`decryptStringAsync` returning `{ shouldReEncrypt, result }`) is non-blocking, supports key rotation and temporary unavailability, and the sync API "may be deprecated"; `setUsePlainTextEncryption()` is a no-op on macOS; without a valid, consistent signature macOS may not treat builds as the same app and the Keychain may "re-prompt the user for permission on every update" — [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)
- Chromium's OSCrypt stores a generated 128-bit random, Base64-encoded password in a keychain item whose service/account default to "Chromium Safe Storage"/"Chromium" (Chrome-branded builds use "Chrome"), returning an empty string if the user denies Keychain access — [Chromium keychain_password_mac.mm](https://chromium.googlesource.com/chromium/src/+/08fbce0a25be93e3ccef86182a5a7e8f08f4be2f/components/os_crypt/keychain_password_mac.mm); Electron sets the service to the app name plus " Safe Storage" and the account to the app name at startup — [Electron commit 324db14 (mirror)](https://ayakael.net/mirrors/electron/commit/324db14969c74461b849ba02c66af387c0d70d49); a third-party reader documents "Claude Safe Storage" with PBKDF2-HMAC-SHA1, salt `saltysalt`, 1003 rounds, `v10` prefix (secondary source) — [ai-usagebar safe_storage.rs](https://docs.rs/crate/ai-usagebar/0.21.0/source/src/safe_storage.rs)

**Safari / Passwords.app credentials and sanctioned alternatives**
- The Passwords app shows the Data Protection keychain (iCloud Keychain, or "Local Items"); its local copy is `~/Library/Keychains/[UUID]/keychain-2.db`; passkeys appear only there ("Keychain Access omits them"); the file-based login keychain is separate and is what Keychain Access manages; items can be protected by the Secure Enclave and biometrics — [Eclectic Light: Inside Sequoia's new Passwords app](https://eclecticlight.co/2024/09/26/inside-sequioas-new-passwords-app/)
- Apple Platform Security: users pick a third-party app as a credential provider (macOS 13+ in Extensions settings); the extension may share metadata that "includes the website of the credential and the associated user name, but not its password"; the OS "communicate[s] with the extension to get the password when the user chooses to fill a credential into an app or a website in Safari"; metadata lives in the provider's container — [Apple Platform Security guide](https://support.apple.com/guide/security/sec6319ac7b9/web)
- `ASCredentialProviderViewController` (macOS 11+): add a Credential Provider Extension target and the `com.apple.developer.authentication-services.autofill-credential-provider` entitlement to both extension and container app; `prepareCredentialList(for:)`, `provideCredentialWithoutUserInteraction(for:)`, `prepareInterfaceForExtensionConfiguration()`, passkey registration/assertion, one-time codes, `ASCredentialIdentityStore` for suggestions, `ASCredentialUpdater` "report" callbacks; "This class ignores calls from Mac apps built with Mac Catalyst" — [Apple ASCredentialProviderViewController](https://developer.apple.com/documentation/authenticationservices/ascredentialproviderviewcontroller)
- Passkeys: "You need to have an associated domain with the webcredentials service type when making a registration or assertion request; otherwise, the request returns an error"; use `ASAuthorizationPlatformPublicKeyCredentialProvider(relyingPartyIdentifier:)` with `ASAuthorizationController`; "Your app can't use passkeys to authenticate for services that you haven't configured as the app's associated domains"; WKWebView passkey checks need iOS 16.4+/macOS 13.3+ — [Apple: Supporting passkeys](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys); macOS 26: `preferImmediatelyAvailableCredentials` now works for passkey registration — [Apple macOS 26 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-26-release-notes)
- Credential Exchange (macOS 26+): `ASCredentialExportManager` "allows your app to exchange authentication credentials like passwords and passkeys with other apps"; requires `SupportsCredentialExchange = YES` and `SupportedCredentialExchangeVersions` (`1.0`) in the credential provider extension's Info.plist; `requestExport(for:)` shows out-of-process system UI, the OS "acts as an intermediary… this process doesn't write any data to the file system", launches the importer with `ASCredentialExchangeActivity`, and the importer calls `ASCredentialImportManager.importCredentials(token:)` — [Apple ASCredentialExportManager](https://developer.apple.com/documentation/authenticationservices/ascredentialexportmanager); the Passwords app's File → "Export … to App" existed in macOS 26 but at the time of writing "no major password manager has shipped an app using ASCredentialImportManager for macOS yet" — [Dan Fabulich](https://danfabulich.medium.com/you-can-export-import-passkeys-now-but-only-on-ios-3b90cddf5fe6); Dashlane says Credential Exchange is available on iOS 26/macOS 26 (Wi-Fi items unsupported; passkeys need internet) — [Dashlane support](https://support.dashlane.com/hc/articles/32907864739474); a Bitwarden community thread reports it still could not register as a macOS password/passkey provider as of macOS 26.2 (user report) — [Bitwarden community](https://community.bitwarden.com/t/register-as-macos-password-and-passkey-provider/93723)

### Inferences
- Confirming the brief's premise: nothing in Apple's APIs lets a third-party app enumerate or read Safari/Passwords credentials. Mechanically, those items sit in Apple's own data-protection keychain access groups, and the access-group model (`errSecItemNotFound` for groups you don't belong to) plus Secure-Enclave/biometric gating make them unreachable; the only sanctioned flows are user-driven (AutoFill via a credential-provider extension, passkey assertions for your own associated domains, or CXP export where the user explicitly picks your importer app).
- An agent that wants to "log in on the user's behalf" should therefore ask the user to fill credentials in the agent's own browser/webview through system AutoFill, or run as a registered credential provider importing via CXP — never scrape the keychain or `keychain-2.db`.
- For the agent's own secrets (API keys, OAuth tokens): Swift/native helper → `SecItemAdd` with `kSecUseDataProtectionKeychain`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (or `AfterFirstUnlock` for background agents), optional `.userPresence` for a "vault" tier; requires Developer ID signing with a team-prefixed keychain access group (enable Keychain Sharing even if not sharing). Electron → `safeStorage` async API for low-friction encryption at rest, accepting that it is tied to the login keychain and the app's signature (re-prompts if signing changes).
- Expect a Touch ID prompt only when reading `.userPresence`-protected items; the default data-protection keychain does not prompt the user at all, unlike legacy file-based keychain ACL dialogs.

### Gaps
- No Apple document explicitly states "third-party apps cannot read Safari/Passwords items"; the conclusion is inferred from the access-group model, the Platform Security guide's broker design, and Eclectic Light's analysis.
- The precise entitlement/provisioning-profile requirements for data-protection-keychain + biometric ACLs on macOS (beyond the forum finding that Keychain Sharing fixes `-34018`) were not documented by an Apple page I could fetch.
- Current (late 2026) status of major password managers shipping macOS CXP import and credential-provider registration remains unverified (search budget exhausted).
- Electron's exact OSCrypt key-derivation parameters come from a secondary source and should be verified against Chromium's `os_crypt_mac.mm` before relying on them.
