Evidence basis. Two kinds of sources are cited below:

1. **Local inspection** of the installed app on this Mac on 2026-10-18: `/Applications/Claude.app` version **2.42304.0** (Electron **44.7.2**, bundle id `com.anthropic.claudefordesktop`), its `~/Library/Application Support/Claude/` data directory, `~/.claude/` (Claude Code 2.1.286 CLI / 2.1.299 embedded), the Chrome native-messaging manifests, `~/.codex/` (Codex CLI 0.162.0), and the tool manifest and operating instructions the app exposes to an agent session. ## Q1. Information architecture: sidebar sections, panes, modes, and how panes relate to a chat

### Takeaway
As of October 2026 the desktop app is a single Electron shell with three top-level surfaces: **Home** (Chat and Cowork merged since v1.26832.0 on 2026-08-06; "Unified Claude" on 3P), **Code** (Claude Code with a multi-pane workspace per session), and the sidebar sections Dispatch, Scheduled/Routines, Projects and Customize. The Chat/Cowork surface is the claude.ai web front end loaded from Anthropic's CDN inside the app; the Code surface is a native-feeling pane layout (chat, diff, browser, terminal, file, plan, tasks, subagent, iOS Simulator) where every pane belongs to exactly one session and the agent can open, close and pop out panes through app-provided MCP tools.

### Cited Findings

**Top-level surfaces and the sidebar**
- The desktop app has three tabs: **Chat** (conversations), **Cowork** ("Dispatch and longer agentic work"), and **Code** (software development); each Code session "has its own chat history and project folder, and the sidebar lists sessions for parallel work" — [Claude Code Desktop docs](https://code.claude.com/docs/en/desktop.md)
- v1.26832.0 (2026-08-06) "merged Chat and Cowork Home as the default, with the sidebar showing Home alongside Code" — [Claude Desktop changelog](https://claude.com/docs/cowork/changelog.md)
- On 3P deployments, when `chatTabEnabled` is true "Claude Desktop presents Chat and Cowork together as **Home** in its sidebar, next to **Code**. From Home, the user chooses **Chat** or **Cowork** in the message box, and the sidebar lists chats and tasks together"; this layout applies to Claude Desktop 1.26832.0 and later, earlier versions showed Chat, Cowork and Code as separate tabs — [Chat in Claude Desktop on 3P](https://claude.com/docs/third-party/claude-desktop/chat.md)
- "Unified Claude" (3P, beta, enforced for all Desktop 3P deployments on November 10) removes the Chat/Cowork choice: "each message sent from the home screen starts a Cowork session" on a VM-capable device and a Chat conversation otherwise; it is controlled by the `desktopHome` key (`standard`/`off`); Code stays separate — [Unified Claude in Claude Desktop on 3P](https://claude.com/docs/third-party/claude-desktop/unified-claude.md)
- Cowork sidebar entries named in official docs: **Dispatch** ("appears as **Dispatch** in the left sidebar", a single conversation whose child tasks appear "under the Dispatch group in the sidebar with its own status") — [Dispatch guide](https://claude.com/docs/cowork/guide/dispatch.md); **Scheduled** ("click 'Scheduled' in the left sidebar", or type `/schedule` in a task) and the **Tasks list** with a trash icon and a "⋮" menu next to each task — [Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); **Customize** ("manage connectors, skills, and plugins from **Customize** in the sidebar") — [Cowork overview](https://claude.com/docs/cowork/overview.md)
- Dispatch child-task states shown in the sidebar: Running, Awaiting input, Awaiting answer, Completed, Error, Archived — [Dispatch guide](https://claude.com/docs/cowork/guide/dispatch.md)
- Code-tab sidebar controls: "filter by status, project, or environment; group by project"; **+ New session** (Cmd+N); split view by Cmd-clicking a session; rename by clicking the title in the toolbar; archive icon on hover ("removes the worktree"); **Auto-archive after PR merge or close** in Settings > Claude Code; **Routines** in the sidebar or its **More** menu; a **Scheduled** section for sessions started by local scheduled tasks; Dispatch-spawned sessions carry a **Dispatch** badge; **Projects** in the sidebar coordinate cloud sessions — [Claude Code Desktop docs](https://code.claude.com/docs/en/desktop.md); [Desktop scheduled tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks.md)
- v2.42304.0 (2026-10-15) added **nested sessions** ("a task in a separate session that appears under the original in the sidebar and reports back", local and SSH only), **side chat** (`/btw`, a pane beside the session), saved **Environments** (folder, SSH host, cloud environment or Remote Control machine), and a **Session rail and Context card** ("side panel showing environment, context, connectors, outputs, changes, and background tasks"); v2.37337.1 (2026-10-13) added **Open in new window** for chats; Cmd+B toggles the sidebar (Cmd+. removed 2026-09-24) — [Claude Desktop changelog](https://claude.com/docs/cowork/changelog.md)
- The app exposes sidebar/session-management MCP tools to the agent itself: `ccd_sidebar` (create/rename/delete sections and groups, move sessions, pin, mark unread/completed, set view), `ccd_session_mgmt` (archive/unarchive, `set_session_title`, `export_transcript`, `search_session_transcripts`, set permission mode/model/effort/fast mode/output style, `set_remote_control`, `send_message`, `list_events`), `ccd_view` (`show_pane`, `close_pane`, `set_transcript_view`), `ccd_window` (`open_session_in`, `close_split`, `set_sidebar_collapsed`), `ccd_session` (`start_session`, `hand_off_to_session` which forks the conversation into a new session with a remaining plan, `move_to_cloud`, `mark_chapter` which inserts a transcript divider and a floating table of contents), `ccd_turn` (`update_plan`, a task list pinned under the latest message; `wrap_up`, a recap plus one question with 1–2 reply buttons or app actions such as commit/create_pr/merge/fix_ci/verify), `ccd_host` (`open_in_editor`, `reveal_path`, `request_keep_awake`, `clean_up_worktrees`, `sync_with_base_branch`, `get_storage_usage`), `ccd_directory` (`request_directory`, `change_directory`), `ccd_pr` (`bind_pr`, `set_auto_merge`, `set_monitor`), `terminal` (`run_in_terminal`, `read_terminal`), `visualize.show_widget` (inline HTML/SVG widgets rendered in the transcript) — [tool manifest observed in a Claude Code Desktop session, 2026-10-18](file:///Applications/Claude.app/Contents/Resources/app.asar)

### Inferences
- The "Chat" surface is literally the claude.ai SPA (the bundled `ion-dist` shell plus CDN-loaded code), which is why chat features (branching, sharing, Projects UI) track the web app; the Code tab is where the desktop-specific React UI (pane layout, session rail) lives. An imitation should therefore separate a "web-view chat host" from a "native agent workspace" and give the agent an RPC surface (the `ccd_*` tools) to manipulate the workspace.
- The `ccd_turn.update_plan`/`wrap_up` tools show that the plan panel and the end-of-turn "next step" box are rendered by the host from structured tool calls rather than parsed from prose — a reusable pattern.
- The `buddy_window`, `quickWindow` and `designWindow` entry points indicate additional floating windows (a companion/"buddy" window, a global quick-entry window, and a design canvas window) beyond the main window; only quick entry and the design canvas are corroborated by other sources.

### Gaps
- No official source was retrieved describing claude.ai chat conversation controls (edit-and-branch, retry, star/pin, archive, search, export, incognito, reply-to-message) in the desktop app; the relevant support articles could not be fetched after the search budget ran out.
- The exact sidebar section order for consumer (non-3P) builds is not documented in one place; the above is assembled from several docs.

## Q2. The built-in browser pane and Claude in Chrome: embedding, persistence, isolation, who controls it

### Takeaway
The built-in browser is an Electron-hosted pane with its own storage partition (observed `Partitions/launch-preview-*` and `cowork-file-preview`), driven by a Playwright-style tool set (`read_page` accessibility tree, `find`, `get_page_text`, `computer` screenshots/clicks, `form_input`, `javascript_tool`, console/network readers) and gated per site by Allow once / Always allow / Deny cards plus an Anthropic site-safety check; sign-ins stay in the app's profile (Cowork keeps them until "Clear browsing data", Code clears them on quit unless **Keep cookies** is set). Claude in Chrome is a separate extension that acts in the user's real Chrome profile over native messaging, with 1Password filling credentials so passwords never enter Claude's context.

### Cited Findings

**Built-in browser: capabilities and embedding**
- "When the built-in browser is on, Cowork and Code sessions show a **Browser** pane where users can open and sign in to any site. In the pane, Claude can open pages, read them, click, type, fill in forms, take screenshots, and run JavaScript on a page." — [Built-in browser and Claude in Chrome (3P)](https://claude.com/docs/third-party/claude-desktop/browser.md)
- Open with **Cmd+Shift+B** (macOS) / Ctrl+Shift+B, or the **Browser** title-bar button; a **Dev servers** menu starts/stops servers; the ⋮ menu has **Keep cookies**, **Clear browsing data**, **Auto-verify changes**, **Open links in built-in browser**; a **Browser tools** toggle in Settings > Claude Code turns the Browser off; "Claude uses the pane to verify its own changes (screenshots, DOM, clicks, forms)"; "The Browser uses a clean profile. For logged-in browsing, use the Claude in Chrome extension"; opening HTML, PDF, image or video paths from chat launches them in this pane — [Claude Code Desktop docs](https://code.claude.com/docs/en/desktop.md)
- Dev-server preview is configured in `.claude/launch.json` (`name`, `runtimeExecutable`, `runtimeArgs`, `port` default 3000, `cwd`, `env`, `autoPort`, `program`, `args`, `url`, `autoVerify`); a localhost `url` "must be the origin only, with a matching port" — [Claude Code Desktop docs](https://code.claude.com/docs/en/desktop.md)
- The tool surface exposed to the agent: `preview_start` (by `name` from launch.json or by `url`), `navigate`, `computer` (screenshot, click, type, scroll, key, drag, zoom, `scroll_to`, hover; coordinates in the last screenshot's frame), `find` (accessibility-tree substring search returning `ref_N` handles), `read_page` (YAML accessibility tree, `filter: interactive`), `get_page_text`, `form_input`, `javascript_tool` ("for DEBUGGING and INSPECTION only"), `read_console_messages`, `read_network_requests` (auth values redacted), `resize_window` (mobile/tablet/desktop presets, `colorScheme`), `tabs_context/create/select/close`, `preview_logs/list/stop`, and `browser_batch` for sequencing — [tool manifest observed in a Claude Code Desktop session, 2026-10-18](file:///Applications/Claude.app/Contents/Resources/app.asar)
- The app bundle depends on `playwright-core` 1.57.0 and a workspace package `@ant/browser-tool-schemas` — [app package.json inside app.asar](file:///Applications/Claude.app/Contents/Resources/app.asar)
- Separate Chromium storage partitions exist on disk for the pane: `Partitions/launch-preview-cowork-shared`, `Partitions/launch-preview-static`, `Partitions/cowork-file-preview` (each with Cookies, IndexedDB, Service Worker, Cache, etc.) — [App Support/Claude/Partitions](file:///Users/devmello/Library/Application%20Support/Claude/Partitions/)
- A `$BROWSER` shim (`claude-browser-shim.js`, a sh/JS polyglot) is injected into Code sessions: when a tool such as `gh`, Vite or Python's `webbrowser` opens a URL, the shim "asks the app over the unix socket in `CLAUDE_BROWSER_BRIDGE` ({socket, key}) to show the URL in the session's Browser pane, and opens the OS browser itself on any answer but 'pane'"; only absolute http(s) URLs without userinfo are relayed; the key is a 64-hex string; reply timeout 3 s — [claude-browser-shim.js](file:///Applications/Claude.app/Contents/Resources/claude-browser-shim.js)
- Timeline: browser-style address bar in preview (v1.21459.0, 2026-07-14); Browser pane screenshot capture and annotation (v1.25927.0, 2026-08-04); unattended sessions can no longer start dev servers in the Browser preview (v1.28929.0, 2026-08-11); 3P `builtinBrowserEnabled` with domain allow/block controls (v2.2553.0, 2026-09-17) — [Claude Desktop changelog](https://claude.com/docs/cowork/changelog.md); a third-party report dates the Code-tab browser launch to the week of 2026-07-06 (Claude Code v2.1.202–2.1.206) — [Digital Applied](https://www.digitalapplied.com/blog/claude-code-desktop-sandboxed-browser-agents-2026)
- In Cowork the built-in browser "opens in the side panel next to your task" and requires Claude Desktop to be open and online; it is the default on desktop (rolling out), switchable to Claude in Chrome under **Settings > Cowork** — [Use the built-in browser in Claude Cowork](https://support.claude.com/en/articles/16607400-use-the-built-in-browser-in-claude-cowork); [Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)

**Built-in browser: persistence, isolation, approvals, policy**
- "Sign-ins and cookies from the pane stay in the app's own browser storage on the device, separate from the user's other browsers. Cowork sessions keep them until the user clicks **Clear browsing data** in the pane's menu. Code sessions clear them when the app quits, unless the user sets **Keep cookies** in the pane's menu to **Shared** or **Per session**." — [Built-in browser and Claude in Chrome (3P)](https://claude.com/docs/third-party/claude-desktop/browser.md)
- "Before Claude acts on a site, Claude Desktop asks the user to approve it. **Allow once** covers that page, and **Always allow** saves the site on the device until the user revokes it in **Settings**. After a user approves a site, Claude can read and interact with its pages as the user sees them, including pages behind the user's sign-in" — [Built-in browser and Claude in Chrome (3P)](https://claude.com/docs/third-party/claude-desktop/browser.md); in the Code tab external sites get a per-site card **Allow once / Always allow / Deny**, and "write actions go through safety classifiers in every mode" — [Claude Code Desktop docs](https://code.claude.com/docs/en/desktop.md)
- Both the built-in browser and Claude in Chrome check public addresses against Anthropic's **site safety list** via `releases.claude.com`; if the check cannot complete "users can keep browsing the site, but Claude can't read or act on it"; logs retain account ID, IP, timestamp and OS/Chrome version but "No URL, page content, prompt content" — [Built-in browser and Claude in Chrome (3P)](https://claude.com/docs/third-party/claude-desktop/browser.md)
- Policy keys: `builtinBrowserEnabled` (default false), `builtinBrowserDefaultDomainPolicy` (`allow` | `block`), `builtinBrowserAllowedDomains`, `builtinBrowserBlockedDomains`; hostname entries cover `www.` but not other subdomains, `*.` wildcards cover subdomains but not the bare domain; "The site policy restricts Claude, not the user" (a blocked page shows the banner "This site is blocked by your organization's policy" and Claude's tools stay off); `coworkEgressAllowedHosts` further restricts which sites the pane can open — [Built-in browser and Claude in Chrome (3P)](https://claude.com/docs/third-party/claude-desktop/browser.md); Code-tab admin keys `browserExternalPageTools: "disabled"` and `disableBrowserExternalNavigation: true` — [Claude Code Desktop docs](https://code.claude.com/docs/en/desktop.md)
- Cowork "network egress permissions don't cover web fetch, web search, MCPs, or Claude in Chrome" — [Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)

**Claude in Chrome (extension) and its bridge**

- Native messaging manifests on this machine: `com.anthropic.claude_browser_extension` → `/Applications/Claude.app/Contents/Helpers/chrome-native-host` (stdio) allowing extension IDs `dihbgbndebgnbjfmelmegjepbnkhlgni`, `fcoeoabgfenejglbffodgkkbkcdhcgfn`, `dngcpimnedloihjnnfngkgjoidhnaolf`; and `com.anthropic.claude_code_browser_extension` → `~/.claude/chrome/chrome-native-host` allowing `fcoeoabgfenejglbffodgkkbkcdhcgfn` (the CLI's own bridge) — [NativeMessagingHosts manifests](file:///Users/devmello/Library/Application%20Support/Google/Chrome/NativeMessagingHosts/com.anthropic.claude_browser_extension.json)

- Credentials: "When a task requires login, Claude can request credentials from 1Password… You approve each request with biometrics, and 1Password fills the credential directly, so Claude never sees the password or one-time code" (beta on macOS) — [Get started with Claude in Chrome](https://support.claude.com/en/articles/12012173-get-started-with-claude-in-chrome); "your passwords and one-time codes never enter Claude's context" — [Use Claude in Chrome safely](https://support.claude.com/en/articles/12902428)

- Enterprise: Claude in Chrome on 3P is available only to Enterprise-Admin-Console-managed orgs and needs **Allow user-added MCP servers** on; site allow/block lists are shared between the extension and the built-in browser — [Built-in browser and Claude in Chrome (3P)](https://claude.com/docs/third-party/claude-desktop/browser.md)

### Inferences
- The pane is most plausibly an Electron `WebContentsView`/`BrowserView` with a named `partition`, automated through the in-process Playwright/CDP layer that `playwright-core` provides; `read_page`'s YAML accessibility tree and `find`'s `ref_N` handles match Playwright's aria-snapshot style. Nothing in the sources states the exact Electron API.
- "Take control" is implicit rather than modal: the user can type an address and interact with the pane at any time (the docs stress that site policy "restricts Claude, not the user"), and Esc stops the agent; no dedicated "full screen / take over" control for the pane was documented.
- A file named `chrome-import-sites.json` sits in the app's data directory — [App Support/Claude](file:///Users/devmello/Library/Application%20Support/Claude/) — which suggests a feature for importing sign-ins/sites from Chrome into the built-in browser; its purpose is not documented in any retrieved source.

### Gaps
- No source states whether the pane runs in the main renderer process or a separate Electron window, nor the CDP/automation mechanism (Playwright is only a listed dependency).
- The claude.com blog post "Claude gets its own browser in Cowork" could not be fetched for its date.

## Q3. Computer use on macOS: helper processes, permissions, tiers, and refusals

### Takeaway
Computer use runs on the real desktop (not the VM) through a Swift N-API addon (`computer_use.node`) plus helper executables, needs macOS **Accessibility** and **Screen Recording**, and layers three controls on top: fixed **app tiers** (browsers and trading platforms view-only, terminals/IDEs click-only, everything else full), **per-app session approvals** ("Allow for this session"/Deny; 30 minutes for Dispatch-spawned sessions), and an action/prompt-injection review; it hides other apps while working, excludes the terminal from screenshots, downscales screenshots to ~1372×887, and is aborted by a global Esc. Refusals cover credentials/secure fields, financial transfers and trades, CAPTCHAs, system settings and permanent deletion.

### Cited Findings

- Since v2.19675.0 (2026-10-01) computer use requires macOS 14 or later; fixes stopped it saving into hidden/protected folders and typing into unresponsive apps (v2.31226.0, v2.42304.0) — [Claude Desktop changelog](https://claude.com/docs/cowork/changelog.md); Claude's research preview began 2026-03-23 — [codex.danielvaughan.com, 2026-04-17](https://codex.danielvaughan.com/2026/04/17/codex-app-computer-use-macos-background-gui-automation/)

- The iOS Simulator pane is a separate, non-computer-use path: "drives the simulator directly, so it doesn't need computer use and never takes over your screen"; consent is once per device; screenshots go to Anthropic; up to 4 devices per session; `disableMobileSimulatorTools` and `requireCoworkFullVmSandbox` turn it off — [Test iOS apps in the simulator](https://code.claude.com/docs/en/desktop-ios-simulator.md); its helper `Claude iOS Sim.app` hosts Meta's FBSimulatorControl, runs "out-of-process and TCC-disclaimed (via the `disclaimer` wrapper)" under a deny-by-default Seatbelt profile that removes network and $HOME reads — [claude-ios-sim.sb](file:///Applications/Claude.app/Contents/Resources/claude-ios-sim.sb)

### Inferences
- The `secureField` reason code indicates the AX layer refuses to type into macOS secure text fields (password fields) at the dispatch level, i.e. the password refusal is enforced below the model, not only by prompt.
- `disclaimer` (a TCC "responsibility disclaimer" wrapper) is how Anthropic keeps helper processes from inheriting the main app's Screen Recording/Accessibility grants; the Seatbelt comments explicitly rely on it. - No official document describes the exact event-injection API (CGEvent vs. AX actions) or how the "teach" recordings are stored/replayed.
- The 30-minute Dispatch grant and the per-tier rules are documented, but the full default blocklist of app categories is not published ("Some apps are off-limits by default").

## Q4. Cowork's sandbox on macOS: VM technology, folder mounting, network, and known limitations

### Takeaway
Local Cowork runs Claude Code inside an Ubuntu 22.04 Linux VM created with Apple's Virtualization.framework (entitlement `com.apple.security.virtualization`), booted from a ~10 GiB `rootfs.img` with a Go root daemon (`coworkd`/`sdk-daemon`) reached over vsock JSON-RPC; selected host folders are shared read-write into `/sessions/<name>/mnt/<Folder>`; all egress goes through gVisor networking and a host MITM/allowlist proxy. Known problems: a July 2026 kernel-plus-shared-mount escape ("SharedRoot"), world-readable logs, host-side MCP servers outside the VM, and a no-network boot bug; since 2026-10-06 new Pro/Max Cowork sessions default to Anthropic's cloud instead.

### Cited Findings

**VM construction and artifacts**
- The app is entitled `com.apple.security.virtualization` (also `automation.apple-events`, `cs.allow-jit`, audio/camera/bluetooth/usb/location/photos, keychain groups incl. `com.anthropic.claude.webauthn`/`hwkey` and Microsoft identity groups) — [codesign entitlements of Claude.app](file:///Applications/Claude.app/Contents/MacOS/Claude)
- On-disk VM bundle `~/Library/Application Support/Claude/vm_bundles/claudevm.bundle/` contains `rootfs.img` (10,737,418,240 bytes; GPT disk), `vmlinuz` (ARM64 Linux kernel image), `initrd` (zstd), `initrd-micro` (SVR4 cpio with busybox, blkid, `virtio-rng.ko`, `nvme*.ko`), `sessiondata.img` (~425 MB), `efivars.fd`, `gvisorMacAddress`, `vmIP` (172.16.10.3 observed), `machineIdentifier`, `.cowork-adopted`, `.*.origin` markers; a sibling `vm_bundles/warm/` directory; `vm-support-probe.json` records `virtSupport: "supported"` keyed by app version|OS|arch; the VM-side Claude Code binary lives in `claude-code-vm/2.1.299/claude` (252 MB, with `.sdk-version`), separate from the host binary in `claude-code/2.1.299/<hash>/claude.app` — [App Support/Claude](file:///Users/devmello/Library/Application%20Support/Claude/)
- "Hypervisor: Apple Virtualization framework. The guest is a Linux VM"; root disk fetched from `downloads.claude.ai/vms/linux/arm64/<revision>/rootfs.img.zst` (1.23 GB compressed, 10 GiB logical, 99 MiB EFI + ext4 root); guest is "Ubuntu 22.04.5 LTS, kernel 6.8.0-136-generic" with Node 22.23.2, Python 3.10.12, uv, and document tools (pdfplumber, camelot, pytesseract, unoserver, markitdown, magika, an `extract-text` dispatcher); `srt-settings.json` ("Sandbox RunTime") inside a `smol-bin` image sets the network allowlist, the MITM proxy socket `/var/run/mitm-proxy.sock` and filesystem rules; host side `CoworkVMManager` tracks "the socket device, shared directories (as a path map), network mode, memory, and CPU count" with `StartVMArgs`; `initrd-micro` is "a fast-boot initramfs" — [Telkins teardown](https://www.telkins.com/blog/a-teardown-of-the-claude-desktop-app)
- Guest daemon `/usr/local/bin/sdk-daemon` ("a stripped Go 1.25.12 arm64 binary") run by `coworkd.service` as root, exposing a vsock RPC bridge for process management; host Swift `CoworkVMRPCClient` sends JSON over vsock; `SpawnProcessArgs` carries command, working directory, environment, extra mounts and allowed domains; `KillProcessArgs`, `WriteStdinArgs`; events `vmStartupStep`, `guestConnectionChanged`, `vmStopped`; the app ships its own `smol-bin` daemon copy that `coworkd`'s updater installs at boot; `MountConfig` has path, mode, optional flag and `hideJson` — [Telkins teardown](https://www.telkins.com/blog/a-teardown-of-the-claude-desktop-app)
- Pluto's March 2026 snapshot: 4 vCPUs, 4 GB RAM; "Network virtualization: gVisor. It blocks `socket()`, so `dig` and `curl` fail inside the VM"; each session gets a random Unix account (e.g. `awesome-wizardly-volta`); the session disk is reformatted ext4 on every boot; `/etc/systemd/system/coworkd.service` sets `User=root`, `NoNewPrivileges=no`, `ProtectSystem=false`, `ProtectHome=false`; nftables has empty ACCEPT chains; no AppArmor profiles for `coworkd`, `sandbox-helper` or the Claude Code binary; `sandbox-helper` (2.1 MB) is replaced each boot — [Pluto Security](https://pluto.security/blog/inside-claude-cowork-how-anthropics-autonomous-agent-actually-works/)

**Folder access and mounting**
- Users attach **workspace folders**; "the agent can then read, create, and modify files anywhere inside those folders, and run code against them inside the sandbox VM"; admins can set `allowedWorkspaceFolders` (entries with `path`, `mode: rw|ro`, `isDefaultSelected`; `~` and `%OneDrive%`/`%USERNAME%` tokens; `[]` means no folders); "The check is enforced against the resolved path, so symlinks and `..` traversal can't be used to escape"; read-only applies to Claude's file tools in Code sessions but "shell commands don't enforce it"; on macOS "network mounts under `/Volumes/` are currently treated as local folders"; on Windows network drives are mounted only if mapped at sandbox start and "The sandbox can stay running between sessions" — [Desktop and filesystem access (3P)](https://claude.com/docs/third-party/claude-desktop/local-access)
- Approval flow from logs: a `request_cowork_directory` MCP tool "triggers a per-directory permission dialog"; `main.log` shows "permission request emitted, then forwarded as `control_request`, then the bridge resolves it (`behavior=allow`), then the folder is added to the session and mounted"; `/Users/username/Desktop` maps to `/sessions/<session-name>/mnt/Desktop` — [Pluto Security](https://pluto.security/blog/inside-claude-cowork-how-anthropics-autonomous-agent-actually-works/)
- v1.46388.3 (2026-09-04) let users attach "home folder, Documents, AppData, Library, or whole drives, with protected locations excluded" — [Claude Desktop changelog](https://claude.com/docs/cowork/changelog.md)
- Cowork session records on disk (`local-agent-mode-sessions/<account>/<org>/local_<uuid>.json`) carry `userSelectedFolders`, `cwd`, `permissionMode`, `model`, `vmProcessName`, `hostLoopMode`, `enabledMcpTools` (`"<connector-id>:<tool>": bool`), `slashCommands`, `isArchived`; each session directory holds `audit.jsonl`, `outputs/`, `uploads/`; sibling files `scheduled-tasks.json`, `remote-session-spaces.json` (sessionId → folders), `cowork-policy-limits-cache.json` (`restrictions.enforce_web_search_mcp_isolation`, `defaults.remote_control_at_startup`) — [local-agent-mode-sessions](file:///Users/devmello/Library/Application%20Support/Claude/local-agent-mode-sessions/)

**Network egress**
- Three layers: (1) gVisor blocks `socket()`; (2) a host MITM proxy (engine `elazarl/goproxy`) with a fresh ephemeral CA per boot installed into the VM trust store, re-signing only `api.anthropic.com` (issuer `O=Coworkd MITM Proxy; CN=Coworkd MITM CA (Ephemeral)`) and CONNECT-tunnelling `github.com`, `pypi.org`, `files.pythonhosted.org`, `registry.npmjs.org` with SNI-based allowlisting; in-VM env `http(s)_proxy=http://localhost:3128`, `ALL_PROXY=socks5h://localhost:1080` forwarding to host ports `CLAUDE_CODE_HOST_HTTP_PROXY_PORT`/`CLAUDE_CODE_HOST_SOCKS_PROXY_PORT`; DNS resolved proxy-side ("Proxy-unaware clients fail with `getaddrinfo EAI_AGAIN`"); (3) a host egress proxy applying a domain allowlist to `WebFetch` (blocked → `EGRESS_BLOCKED`), while `WebSearch` goes through Anthropic — [Pluto Security](https://pluto.security/blog/inside-claude-cowork-how-anthropics-autonomous-agent-actually-works/)
- `srt-settings.json` allowlists package registries and Anthropic/Claude domains with `allowLocalBinding` and `allowAllUnixSockets` both `true`; Anthropic "added a proxy in the VM that checks the provisioned session token" after an exfiltration finding where a malicious file caused uploads through an allowed domain; host-side networking uses `VZGvisorNetworking` ("similar to the gvisor-tap-vsock project") — [Telkins teardown](https://www.telkins.com/blog/a-teardown-of-the-claude-desktop-app)

**Platform coverage, cloud default, policy keys**
- Windows: "Cowork's sandbox runs on the operating system's built-in virtualization… there is no installation path inside WSL" — [Desktop and filesystem access (3P)](https://claude.com/docs/third-party/claude-desktop/local-access); Linux desktop app shipped v1.17377.1 (2026-06-30) — [Claude Desktop changelog](https://claude.com/docs/cowork/changelog.md); community projects run Cowork natively on Linux by stubbing the macOS-native pieces — [rmorison/claude-cowork-linux](https://github.com/rmorison/claude-cowork-linux)

### Inferences
- The `hostLoopMode` and `vmProcessName` fields in session records, together with the deprecated `requireCoworkFullVmSandbox` key, imply two execution topologies: the agent loop (Claude Code) running on the host with only tool execution in the VM, versus everything in the VM. The "full VM sandbox" mode is the stricter one and disables host-only features (iOS Simulator).
- Because sharing is a path map handed to `SpawnProcessArgs.extraMounts`, folder grants are per-process rather than per-VM; the escape shows that a kernel bug in the guest plus any rw share is sufficient to reach host files, so an imitation should prefer read-only shares plus an explicit write-back channel.
- The "warm" bundle directory and `initrd-micro` indicate a pre-booted/fast-boot VM to hide multi-second cold starts.

### Gaps
- The exact sharing transport (virtiofs vs. 9p vs. a daemon-mediated copy) is not stated by any source ("The article does not name the sharing mechanism").
- Anthropic's own engineering write-up of the Cowork sandbox (referenced by Telkins) was not located.
- The contents of `sessiondata.img` and the `git-shadow/` directory (46 hash-named entries next to `git-worktrees.json`) are undocumented; `git-shadow` is plausibly a shadow-repository store for snapshots/rewind but this is unconfirmed.

## Q5. Approvals, permission modes, plans, long-running work, and "ask the user a question"

### Takeaway
Every surface shares one permission pipeline (hooks → deny rules → ask rules → mode → allow rules → `canUseTool`), surfaced as approval cards with "Allow once / Always allow / Deny" (Cowork labels them Manual/Auto/Skip; Code labels them Manual/Accept edits/Plan/Auto/Bypass). Clarifying questions are a tool (`AskUserQuestion`: 1–4 questions, 2–4 options each, optional multi-select, "Other" free text, optional HTML/markdown previews) rendered as selectable cards; plans are a mode plus an `ExitPlanMode` approval; long-running work is handled by Desktop scheduled tasks (local, 1-minute minimum), cloud Routines (1-hour minimum, API/GitHub triggers), `/loop`, Dispatch (phone → desktop, child sessions, 10-minute approval timeout), Remote Control, channels, and a background daemon.

### Cited Findings

**Permission modes and approval UI**
- Code tab modes and settings keys: **Manual** (`default`), **Accept edits** (`acceptEdits`, also auto-approves `mkdir`, `touch`, `mv`), **Plan** (`plan`), **Auto** (`auto`, "a background classifier checks actions first"; needs Opus 4.6+/Sonnet 4.6+/Haiku 5.5/Fable on the Anthropic API; admins disable with `disableAutoMode`), **Bypass permissions** (`bypassPermissions`; Pro/Max enable via "Allow bypass permissions mode" in Settings → Claude Code); a mode picked in the selector "is remembered per folder, except Plan"; cloud sessions offer Accept edits, Plan and Auto only — [Claude Code Desktop docs](https://code.claude.com/docs/en/desktop.md)
- Cowork modes in the chat-box selector: **Manual** ("Manually approve", formerly "Ask before acting"; Allow/Deny per action), **Auto** ("Automatically approve"; "reviews each action for safety, such as data exfiltration or prompt injection"; "uses more of your usage limit"), **Skip** ("Skip all approvals", formerly "Act without asking"); "Claude requires explicit permission before permanently deleting any files"; Team/Enterprise admins can remove Auto and "require per-task approval for write-capable connector tools" — [Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)
- Evaluation order in the harness/SDK: hooks → deny rules → ask rules → permission mode → allow rules → `canUseTool` callback; `AskUserQuestion`, MCP tools with `_meta["anthropic/requiresUserInteraction"]`, org-`ask` connector tools and `rm`/`rmdir` on critical paths are never auto-approved; `plan` mode routes every file-edit/shell-write to the callback; `dontAsk` denies instead of prompting; `bypassPermissions` refuses to start as root outside a recognised sandbox — [Agent SDK: Configure permissions](https://code.claude.com/docs/en/agent-sdk/permissions.md)
- Callback contract: `canUseTool(toolName, input, { signal, suggestions, … })` returns `{ behavior: "allow", updatedInput, updatedPermissions? }` or `{ behavior: "deny", message }`; "Approve and remember" echoes a suggested `PermissionUpdate` with destination `localSettings`, which "writes the rule to `.claude/settings.local.json`"; `suppressAlwaysAllowRule: true` hides the always-allow choice; the callback "can stay pending indefinitely"; a `PreToolUse` hook can return `defer` so the process can exit and resume later; a `PermissionRequest` hook can fan out notifications (Slack, email, push) — [Agent SDK: Handle approvals and user input](https://code.claude.com/docs/en/agent-sdk/user-input.md)
- The permission request travels as `control_request` over the bridge and resolves with `behavior=allow` (observed in Cowork `main.log`) — [Pluto Security](https://pluto.security/blog/inside-claude-cowork-how-anthropics-autonomous-agent-actually-works/)
- Connector tool approvals: **Allow once** / **Always allow** at call time, and per-tool **Always allow / Needs approval / Blocked** under Customize > Connectors → Tool permissions — [Get started with connectors](https://claude.com/docs/connectors/overview.md); on 3P a `toolPolicy` of `allow`/`blocked`/`ask`, and `mcpScheduledTaskApprovalLifetimeDays` limits reuse of MCP approvals in scheduled tasks — [Chat in Claude Desktop on 3P](https://claude.com/docs/third-party/claude-desktop/chat.md); [Claude Desktop changelog](https://claude.com/docs/cowork/changelog.md)
- Artifacts have their own asks: publish without prompting on a typed prompt, but ask in plan mode, when declaring runtime capabilities (connectors, downloads), when republishing a public artifact, or in a scheduled-task turn — [Share session output as artifacts](https://code.claude.com/docs/en/artifacts.md)

**Clarifying questions**

Questions stay open until you answer them by default"; answer "by picking an option, or type your own text through the `Other` row or the notes field"; `askUserQuestionTimeout` (`60s`/`5m`/`10m`, the **Question auto-continue timeout** row in `/config`) closes an idle dialog, submits any selected options and tells Claude the user may be away; the timer never runs in background sessions, screen-reader mode, or Remote Control; "permission prompts, including plan approval, never auto-resolve on idle" — [Tools reference](https://code.claude.com/docs/en/tools-reference.md)

### Inferences
- The host renders four distinct card types from tool traffic: permission cards (from `control_request`), question cards (from `AskUserQuestion` input), plan-approval cards (from `ExitPlanMode`), and the desktop-only plan list / next-step box (from `update_plan`/`wrap_up`). An open-source clone can get identical UX by intercepting those four tool names in an Agent SDK `canUseTool`/message stream.
- The `jobs/` directory and daemon logs point to Claude Code's own background-session supervisor (spare workers, leases) being what keeps Desktop scheduled tasks and nested sessions alive without a terminal.

### Gaps
- No public document describes the Dispatch wire protocol beyond Pluto's log observations (SSE from Anthropic to the desktop `sessions-bridge`).
- The plan pane's rendering (markdown of `~/.claude/plans/*.md`) is inferred from file presence; no doc describes it.

## Q6. Memory, Skills, connectors/MCP: files, consolidation, controls, installation

### Takeaway
Memory is three-layered: Claude Code **auto memory** on disk (`~/.claude/projects/<slug>/memory/MEMORY.md` index + topic files, first 200 lines/25 KB loaded, per repository across worktrees), **claude.ai memory** that follows the account into Cowork cloud sessions (toggle in the "+" menu before a task; Settings > Memory; sensitive categories excluded), and **project memory** shared between Chat and Cowork inside a project. Skills are `SKILL.md` bundles synced from claude.ai into `~/.claude/skills/synced/<org>_<account>/`, bundled in the app as `.skill` files, and installed via Customize > Skills; connectors are remote MCP servers (OAuth, tool-level permissions) or local MCPB desktop extensions (`.mcpb` zip with `manifest.json`, installed under `~/Library/Application Support/Claude/Claude Extensions/`).
