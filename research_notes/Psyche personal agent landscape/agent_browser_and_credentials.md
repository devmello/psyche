# Agent-controlled browser inside a desktop app, and safe credential handling (as of 2026-10-18)

Scope note: five key questions below. Primary docs were fetched wherever possible (Electron, Playwright, Anthropic, 1Password, Bitwarden, Cloudflare, Brave, Google, OpenAI's Operator system card PDF). OpenAI's help-center and openai.com pages returned HTTP 403 to the fetcher, so Atlas/ChatGPT-agent behaviour is sourced from OpenAI's CISO post as quoted by Simon Willison, the Operator system card PDF, and Zenity Labs' research. The web-search budget was exhausted near the end, so a few items (Steel live-view docs, CEF wiki, Genspark, 2026 Atlas updates) are recorded as gaps rather than guessed.

## KQ1. Embedding a browser the agent owns (Electron WebContentsView / sessions / CDP, Playwright connectOverCDP, extensions, CEF, Tauri, persistence, popups, downloads, recording)

### Takeaway
Electron (current stable 44.9.0, Chromium 152, released 2026-10-16) gives everything needed in-process: `WebContentsView` per tab on a `BaseWindow`, `persist:`-prefixed session partitions for on-disk profiles, `webContents.debugger` for raw Chrome DevTools Protocol, `setWindowOpenHandler` for OAuth popups, `will-download` for downloads, and `safeStorage` for OS-keychain-wrapped secrets. Playwright 1.64 can attach to that same Chromium via `connectOverCDP` (Chromium-only, lower fidelity than `connect()`), while `--remote-debugging-port` remains a documented Electron switch (no breaking-change entry removes it). Electron's Chrome-extension support is deliberately partial (no `chrome.action`, `chrome.identity`, `chrome.windows`, `chrome.storage.sync`), so loading a commercial password-manager extension into an embedded Electron browser should not be assumed to work; Tauri's macOS/Linux WebKit webviews expose no CDP at all.

### Cited Findings

**Electron versions and view model**
- Current stable Electron is 44.9.0 (Chromium 152.0.7977.167, Node 24.22.0, released 2026-10-16); prerelease 45.0.0-beta.5 ships Chromium 156.0.8078.36; supported stables are 44.9.0, 43.8.0, 42.11.15 — [Electron Releases](https://releases.electronjs.org/)
- `new WebContentsView([options])` accepts `webPreferences` and an existing `webContents`; "A WebContents can be presented in only one WebContentsView at a time"; views are attached with `win.contentView.addChildView(view)` on a `BaseWindow` and positioned with `setBounds()`; main-process only; the sidebar marks `BrowserView` as Deprecated — [Electron WebContentsView docs](https://www.electronjs.org/docs/latest/api/web-contents-view)
- Breaking changes: Electron 30 deprecated `BrowserView` in favour of `WebContentsView` (BrowserView became a wrapper around it); Electron 36 deprecated `session.loadExtension/removeExtension/getExtension/getAllExtensions` in favour of the `session.extensions` class; the page's newest section is 44.0 and contains no entry removing `--remote-debugging-port` — [Electron breaking changes](https://www.electronjs.org/docs/latest/breaking-changes)

**Sessions, persistence, downloads, permissions**
- `session.fromPartition`: a `persist:` prefix gives "a persistent session available to all pages in the app with the same partition"; without the prefix the session is in-memory; an empty partition returns the default session; a Session with custom `options` must be created before the partition is first used — [Electron session docs](https://www.electronjs.org/docs/latest/api/session)
- `ses.storagePath` returns the absolute on-disk path where the session's data is persisted (null for in-memory sessions); the `will-download` event supplies a `DownloadItem` and `event.preventDefault()` cancels the download; `setPermissionRequestHandler` / `setPermissionCheckHandler` gate `clipboard-read`, `geolocation`, `media`, `notifications`, `hid`, `serial`, `usb` (both handlers are needed for complete handling); `setDisplayMediaRequestHandler` gates screen capture; `ses.cookies`, `clearStorageData`, `setProxy` (+ `closeAllConnections`) are available — [Electron session docs](https://www.electronjs.org/docs/latest/api/session)
- Fuse `EnableCookieEncryption` "encrypts the on-disk cookie store with OS-level keys"; fuse `EnableNodeCliInspectArguments` controls `--inspect`/`--inspect-brk` and SIGUSR1; no fuse controls `--remote-debugging-port` — [Electron Fuses](https://www.electronjs.org/docs/latest/tutorial/fuses)
- `--remote-debugging-port=port` is documented as "Enables remote debugging over HTTP on the specified port"; `--inspect` defaults to 127.0.0.1:9229; switches must be appended with `app.commandLine.appendSwitch` before the app `ready` event — [Electron command-line switches](https://www.electronjs.org/docs/latest/api/command-line-switches)
- A third-party skill doc claims Electron 34+ "removed support for the `--remote-debugging-port` CLI flag"; this is contradicted by the current command-line-switches page, which still documents it, and by the breaking-changes page, which has no such entry — claim: [claudskills.com](https://claudskills.com/skills/electron-e2e-cdp-testing/SKILL.md); contradicted by [Electron command-line switches](https://www.electronjs.org/docs/latest/api/command-line-switches) and [Electron breaking changes](https://www.electronjs.org/docs/latest/breaking-changes)

**CDP from inside Electron (`webContents.debugger`)**
- `win.webContents.debugger` (main process) exposes `attach([protocolVersion])`, `isAttached()`, `detach()`, `sendCommand(method[, commandParams, sessionId]) -> Promise<any>`; events `'message' (event, method, params, sessionId)` and `'detach' (event, reason)`; the session is detached when the webContents closes or when DevTools is opened for it; a `sendCommand` issued before the target navigates may not resolve until navigation; commands with no result resolve to `{}` — [Electron Debugger docs](https://www.electronjs.org/docs/latest/api/debugger)
- `webContents.setWindowOpenHandler` runs before `window.open()`/`target=_blank` windows are created; returning `{action:'deny'}` cancels, `allow` may supply `createWindow`; `did-create-window` fires with `url, frameName, options, referrer, disposition`; `executeJavaScriptInIsolatedWorld` (world 999 is the contextIsolation world); `capturePage()` returns a NativeImage; `sendInputEvent` injects mouse/wheel/keyboard events but "the containing BrowserWindow must be focused"; `will-navigate` (main-frame, user/page-initiated, cancellable), `will-redirect`, `did-navigate`, `did-navigate-in-page`; the `login` event handles HTTP basic auth; `setUserAgent` overrides the UA — [Electron webContents docs](https://www.electronjs.org/docs/latest/api/web-contents)

**Playwright / Puppeteer attaching over CDP**
- `browserType.connectOverCDP(endpointURL, options?)` accepts an HTTP URL like `http://localhost:9222/` or a `ws://.../devtools/browser/...` URL; options `headers`, `timeout` (30000 default), `slowMo`, `artifactsDir`, `isLocal`, `noDefaults` (skip Playwright's default overrides on the existing default context); the existing profile is `browser.contexts()[0]`; Chromium-only; "fidelity is significantly lower than `browserType.connect()`"; a browser launched outside Playwright must use args matching Playwright's curated list or "some functionality may break" — [Playwright BrowserType](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)
- `launchPersistentContext(userDataDir)` keeps cookies/localStorage on disk, returns a single context, allows one browser instance per directory, and explicitly does not support automating Chrome's default "User Data" profile; `channel: 'chrome' | 'msedge'` uses branded browsers — [Playwright BrowserType](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)
- Playwright's Electron support is "experimental": `_electron.launch({ args: ['main.js'] })`, Electron v21+, `electronApp.evaluate()` runs in the main process, native dialogs must be stubbed, and if launch times out "make sure the `nodeCliInspect` fuse (`FuseV1Options.EnableNodeCliInspectArguments`) is not set to `false`"; only launching (not attaching to a running app) is documented — [Playwright Electron class](https://playwright.dev/docs/api/class-electron)
- Latest Playwright is 1.64 (bundled Chromium 156.0.8078.4); 1.59 added `browser.bind()` so `playwright-cli`/`@playwright/mcp` can connect to a launched browser; 1.62 bundled the MCP server and `playwright-cli`; 1.60 added `noDefaults` on `connectOverCDP` and a `boxes` option on aria snapshots described as "useful for AI consumption"; 1.63 added `ariaSnapshotJSON()`; 1.64 added `page.getByRef()` and `page.webmcp` — [Playwright release notes](https://playwright.dev/docs/release-notes)
- Puppeteer `page.accessibility.snapshot()` reflects Chrome's accessibility tree and by default drops nodes screen readers don't use unless `interestingOnly:false` — [Puppeteer Accessibility.snapshot](https://pptr.dev/api/puppeteer.accessibility.snapshot)
- Puppeteer `page.screencast()` records WebM (VP9, 30 FPS), needs ffmpeg, is marked obsolete in favour of `Page.record()` (Chrome 153+) — [Puppeteer page.screencast](https://pptr.dev/api/puppeteer.page.screencast)

**Extensions inside Electron (can a password manager load?)**
- Electron "does not support arbitrary Chrome Store extensions"; it is "a non-goal of the Electron project to be perfectly compatible with Chrome's implementation of Extensions"; only unpacked extensions load, only into persistent sessions, per session, and must be re-loaded on every app boot; APIs not listed as supported are "provisional and may be removed" — [Electron Chrome Extension Support](https://www.electronjs.org/docs/latest/api/extensions)
- Supported API surface: `chrome.devtools.*` (all), `chrome.extension` (`lastError`, `getURL`, `getBackgroundPage`), `chrome.management` (subset), `chrome.runtime` (subset incl. `connect`, `sendMessage`, `onMessage`), `chrome.scripting` (all), `chrome.storage.local` only (no `sync`/`managed`), `chrome.tabs` (`sendMessage`, `reload`, `executeScript`; partial `query`/`update`; no "current tab" `-1`), `chrome.webRequest` (all, with Electron's own `webRequest` taking precedence); supported manifest keys include `host_permissions` (MV3) and `background` (MV2); `chrome.action`, `chrome.identity`, `chrome.windows`, popups, options pages and service workers are not mentioned — [Electron Chrome Extension Support](https://www.electronjs.org/docs/latest/api/extensions)
- `session.extensions.loadExtension(path[, options])` throws for in-memory sessions, cannot be called before `ready`, defaults `allowFileAccess` to false, and logs a console warning when an extension requests an unsupported API — [Electron Extensions API](https://www.electronjs.org/docs/latest/api/extensions-api)

**Secrets and biometrics in Electron**
- `safeStorage` encrypts strings with OS crypto: macOS Keychain (other apps blocked without user override), Windows DPAPI ("protected from other users on the same machine but not from other apps in the same user session"), Linux via `gnome_libsecret`/`kwallet*`; `getSelectedStorageBackend()` returning `basic_text` means items are "protected only by a hardcoded plaintext password"; async variants (`encryptStringAsync`, `decryptStringAsync` with `shouldReEncrypt`) are recommended; sign macOS builds or Keychain re-prompts on every update — [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)
- `systemPreferences.promptTouchID(reason)` / `canPromptTouchID()` are macOS-only and "This API itself will not protect your user data"; real protection requires keychain items with access-control flags such as `kSecAccessControlUserPresence`, e.g. storing an encryption key via `node-keytar` and reading it only after the prompt resolves — [Electron systemPreferences](https://www.electronjs.org/docs/latest/api/system-preferences)

**Tauri and CEF alternatives**
- Tauri uses WebView2 (Chromium) on Windows, WKWebView (WebKit, updated only with the OS) on macOS, WebKitGTK on Linux, and the system WebView on Android — [Tauri Webview Versions](https://v2.tauri.app/reference/webview-versions/)
- Automating Tauri apps uses Microsoft Edge WebDriver for WebView2 on Windows (driver version must match), WebKitWebDriver on Linux (Xvfb for headless), and an embedded WebDriver provider on macOS that requires `tauri-plugin-wdio-webdriver` in debug builds — [WebdriverIO Tauri platform support](https://webdriver.io/docs/desktop-testing/tauri/platform-support)
- A team's internal notes report that WKWebView "exposes no Chrome DevTools Protocol port", so CDP-style automation does not work on macOS Tauri; they drove the UI via a Tauri event bus instead (anecdotal, single source) — [adom wiki hd-ui-mac skill](https://wiki.adom.inc/api/pages/adom/hd-mac-bootstrap/files/skills/hd-ui-mac/SKILL.md)

### Inferences
- A practical "agent-owned browser" in Electron is: one `BaseWindow` hosting a `WebContentsView` per tab, all created with `webPreferences.partition = 'persist:agent'`, with `webContents.debugger.attach('1.3')` per tab for CDP (`Accessibility.getFullAXTree`, `Input.dispatch*`, `Page.startScreencast`, `Network.*`), plus `setWindowOpenHandler` to route OAuth popups into a new agent tab and `session.on('will-download')` to quarantine downloads. Persistence across restarts is free because the partition data lives at `ses.storagePath`; enable the `EnableCookieEncryption` fuse so the cookie jar is OS-key encrypted.
- "Take control" (user and agent sharing the browser) is natural in-process: the user interacts with the `WebContentsView` directly while the agent drives it through CDP; both touch the same renderer. The main design cost is arbitration (pause agent input while the user is active). Highlighting agent actions can be done by injecting an overlay with `executeJavaScriptInIsolatedWorld` (as browser-use's `buildDomTree.js` does) or by drawing a transparent sibling `View`; recording can use CDP `Page.startScreencast` (what Puppeteer's screencast/record wraps) rather than OS screen capture.
- Running a separate headful Chromium/Chrome (`--remote-debugging-port` + dedicated `--user-data-dir`) and attaching with `connectOverCDP` buys full Chrome extension support and branded-Chrome fingerprinting, at the cost of a second process, a window that is not embeddable inside your pane, and Playwright's own warning about lower fidelity and arg-mismatch breakage. The in-app `WebContentsView` route keeps the pane embedded but forfeits store extensions (password managers in particular, which depend on `chrome.action` popups, MV3 service workers, and `chrome.identity`/native messaging that Electron does not list as supported).
- Tauri is not a viable host for a CDP-driven agent browser on macOS/Linux (WebKit, WebDriver-only); it is viable only on Windows via WebView2.
- Do not expose `--remote-debugging-port` in production builds: the protocol has no authentication, so gate it behind an env var or use `webContents.debugger` in-process (no network listener at all).

### Gaps
- CEF: both fetches of the CEF GeneralUsage wiki returned 404, so remote-debugging settings, `CefRequestContext` persistence, Chrome-vs-Alloy runtime status and extension support in CEF are not cited here.
- The official Chrome DevTools Protocol viewer is JavaScript-rendered and returned no text, so exact `Accessibility.getFullAXTree`, `Page.startScreencast`, `Input.dispatchMouseEvent` parameter lists are not cited (Puppeteer/Playwright docs above confirm the capabilities exist).
- No source was found that tests a real password-manager extension (1Password/Bitwarden) inside Electron; the conclusion that they will not work is an inference from Electron's supported-API list.
- Electron's exact on-disk location for partitions (commonly `userData/Partitions/<name>`) was not visible in the fetched page; use `ses.storagePath` at runtime.

## KQ2. How products do it (Claude desktop browser pane, Claude in Chrome, ChatGPT Atlas/Operator, Comet, Dia, Opera Neon, Edge, Manus, cloud browsers) and user takeover

### Takeaway
The market has converged on two browser identities: a clean, agent-owned profile (Claude Cowork/Claude Code browser pane, Atlas "logged-out" mode, Manus Cloud Browser, Browserbase/Kernel/Anchor sessions) versus the user's real browser with real sign-ins (Claude in Chrome, Manus Browser Operator, Opera Neon's MCP connector, Edge "Browse with Copilot"). Every serious product adds a human takeover path (watch mode, "Take Over" on CAPTCHA/MFA, live-view iframes, per-site Allow once/Always/Deny) and an action classifier or critic that checks each write action against the user's request.

### Cited Findings

**OpenAI: Operator (Jan 2025), ChatGPT agent, Atlas (Oct 2025)**
- Operator system card (2025-01-23): confirmations "before finalizing actions that affect the state of the world (e.g., before completing a purchase or sending an email)" with 92% recall on 607 tasks across 20 risk categories, cutting model-mistake risk "by approximately 90%"; proactive refusals of "banking transactions and making high-stakes decisions" (94% recall) and a full restriction on "selling or purchasing stocks"; Watch Mode on higher-impact sites such as email "automatically pausing execution when the user becomes inactive or navigates away from the page"; the card never uses the word "takeover" — [Operator System Card (PDF)](https://cdn.openai.com/operator_system_card.pdf)
- Willison's launch notes: Operator "frequently asked users for confirmation", and OpenAI's demo team used a "take control" option to enter credit-card details and complete the purchase; he recommends a fresh session per task and wiping the session after entering payment details — [Simon Willison on Operator](https://simonwillison.net/2025/Jan/23/introducing-operator/)
- Atlas (quoting OpenAI CISO Dane Stuckey): "prompt injection remains a frontier, unsolved security problem"; logged-out mode is recommended "when you don't need to take action within your accounts"; Watch Mode on sensitive sites "requires you have the tab active to watch the agent do its work"; Willison tested GitHub and a bank and saw no Watch Mode trigger; he calls 99% "a failing grade" for application security — [Simon Willison: OpenAI CISO on Atlas](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/)
- Atlas agent mode is off by default and opt-in; logged-in mode uses existing sessions (e.g. can read and send Gmail), logged-out mode has no credentials; "the first mode selected becomes the default for later agent sessions"; memories from regular ChatGPT chats affect Atlas (memory-poisoning route via connected services, uploaded files, visited sites); the browser can send requests to any domain so "data should be presumed exposed if the agent is compromised" (2025-10-23) — [Zenity Labs on Atlas](https://labs.zenity.io/post/exploring-the-risks-of-chatgpt-s-atlas-browser)
- Atlas agent "Cannot run code in the browser, access your file system or other apps, download files, or install extensions"; it "pauses for approval on sensitive surfaces"; Browser Memories are optional and deletable; page visibility is per site; agent mode is a preview on Plus/Pro/Business, unavailable on Free/Go (article updated 2025-10-24) — [allthings.how Atlas agent mode guide](https://allthings.how/chatgpt-atlas-agent-mode-macos-setup-controls-workflows/)
- OpenAI's own help article on Atlas agent mode exists but returned HTTP 403 to the fetcher — [OpenAI Help: Ask ChatGPT sidebar and ChatGPT Agent on Atlas](https://help.openai.com/en/articles/12628199-using-ask-chatgpt-sidebar-and-chatgpt-agent-on-atlas)

**Cloud browser infrastructure (Browserbase, Kernel, Anchor, Steel)**
- Browserbase Session Live View: `bb.sessions.debug(session.id)` returns `debuggerFullscreenUrl`/`debuggerUrl`; embed in an iframe (read-only by adding `pointer-events: none`; read/write otherwise; `&navbar=false` hides the navbar); documented uses include "taking control or giving input" and "delegating credentials to an end user"; each tab has its own URL via `pages[i].debuggerFullscreenUrl`; the iframe posts `browserbase-disconnected` when the session ends — [Browserbase Session Live View](https://docs.browserbase.com/features/session-live-view)
- Browserbase Contexts persist cookies, localStorage, IndexedDB, sessionStorage, Service Workers, autofill and preferences (not the HTTP cache) when `persist: true`; encrypted at rest; recommended one Context per site per login; do not run concurrent sessions on one Context; sites may still invalidate sessions — [Browserbase Contexts](https://docs.browserbase.com/features/contexts)
- Browserbase's 1Password integration page describes a Service Account + 1Password SDK retrieval flow for scripted logins (distinct from 1Password's approval-gated Secure Agentic Autofill) — [Browserbase 1Password integration](https://docs.browserbase.com/integrations/1password)
- Kernel: "Watch or take over a running session"; sessions can be recorded as MP4; Profiles persist "cookies, storage, logins, history, open tabs"; stealth fingerprints by default; a managed CAPTCHA solver is included; idle browsers enter standby five seconds after the last client disconnects and keep state; CDP and WebDriver BiDi are exposed — [Kernel features](https://www.kernel.sh/docs/overview/features); [Kernel docs](https://www.kernel.sh/docs/)
- Anchor Browser advertises live view, "human-in-the-loop workflows", managed identities with MFA, persistent profiles, residential proxies/sticky IPs, CAPTCHA solving and "extra-stealth fingerprinting" — [Anchor Browser docs](https://docs.anchorbrowser.io/)

**Google Chrome (Gemini agent)**

### Inferences
- For a personal desktop agent, the Anthropic desktop pattern is the closest template: an embedded, persistent, clean profile (not the user's Chrome), per-site Allow once/Always/Deny, write-action classifiers independent of permission mode, a hard "never" list (purchases, account creation, CAPTCHA bypass, sensitive data entry), and a visible pane the user can take over at any moment. Pair it with an optional "use my real browser" path (extension or MCP connector) only for tasks that genuinely need existing sign-ins.
- Takeover UX has three recurring triggers across products: verification challenges (CAPTCHA/MFA/SMS → Manus "Take Over", Browserbase "delegating credentials to an end user"), sensitive sites (Operator/Atlas Watch Mode pausing when the tab is inactive), and classifier blocks (Claude Auto mode falling back to per-step approval). Implement all three as explicit states in the pane.
- Atlas's "first mode becomes the default" finding (Zenity) is a UX anti-pattern to avoid: make logged-in vs logged-out an explicit per-task choice with a persistent visual indicator.

## KQ3. Browser-agent frameworks and page representation (browser-use, Stagehand, Magnitude, Skyvern, Anthropic computer use, Playwright MCP/aria snapshots) and the CAPTCHA / bot-detection stance

### Takeaway
Frameworks split into DOM/accessibility-tree agents that hand the model indexed element references (browser-use's `buildDomTree.js` index map, Playwright MCP's aria snapshot refs, Anthropic's `read_page`/`find`) and vision-first agents that need coordinate-grounded models (Magnitude, Anthropic's `computer_toolset_20260801`). All mature frameworks ship a placeholder/variable mechanism so secrets never reach the model. On bots, the legitimate path is Cloudflare's Web Bot Auth (RFC 9421 Ed25519 signatures, still an individual IETF draft), while Anthropic explicitly prohibits CAPTCHA bypass; cloud infra vendors (Kernel, Anchor) sell CAPTCHA solving, which is the opposite stance.

### Cited Findings

**browser-use (Python)**
- `sensitive_data` maps placeholder names (e.g. `x_user`, `x_pass`) to real values, either globally or per domain pattern (`'https://*.example-staging.com'`, `'http*://test.example.com'`, `'https://google.com': {...}`); "The LLM only sees placeholders... we filter your sensitive data from the input text" and "Real values are injected directly into form fields after the LLM call"; recommended companions are `Browser(allowed_domains=[...])`, `use_vision=False` "to prevent LLM seeing sensitive data in screenshots", and `storage_state='./auth.json'` to reuse login cookies instead of passwords — [browser-use sensitive data docs](https://docs.browser-use.com/open-source/examples/templates/sensitive-data.md)
- Pydantic AI's browser-use harness requires a non-empty `allowed_domains` allowlist with explicit hostnames whenever flat (non-scoped) `sensitive_data` is supplied — [Pydantic AI browser-use harness](https://pydantic.dev/docs/ai/harness/browser-use/)
- Browser Use Cloud secrets support `allowed_domains` wildcards such as `*.example.com` and advise adding SSO/OAuth redirect domains to the allowlist — [Browser Use Cloud secrets guide](https://docs.browser-use.com/cloud/guides/secrets)
- CVE-2025-47241: before 0.1.45 a decoy domain in the URL userinfo portion bypassed `allowed_domains` — [Debian tracker CVE-2025-47241](https://security-tracker.debian.org/tracker/CVE-2025-47241)

- A 2026-10-07 third-party audit notes browser-use's default tools include `write_file`, `read_file`, `evaluate` (JS) and `Bash`, that the Bash integration "is not an operating-system sandbox", and recommends a container for untrusted tasks — [Agent Trust Hub audit of browser-use](https://www.skills.sh/gregpr07/browser-use/open-source/security/agent-trust-hub)

**Stagehand (Browserbase)**
- `act()` takes `variables` that fill `%name%` placeholders (`action: "enter %password% in the password field", variables: { password: process.env.USER_PASSWORD }`); variables "will not be shared with LLM providers"; set `verbose: 0` to keep secrets out of logs; Python needs `use_api: true`; prefer atomic single-step actions; `observe()` returns candidate actions (selector, method, args) that can be passed to `act()` and cached to skip LLM calls — [Stagehand act docs](https://docs.stagehand.dev/v2/basics/act); [Stagehand observe docs](https://docs.stagehand.dev/v2/basics/observe)

**Magnitude**
- Vision-first: requires a model "good at following instructions and planning" that can also "locate precise coordinates in an image"; recommends Claude Sonnet, with Qwen 2.5 VL 72B as the open alternative — [Magnitude LLM configuration](https://docs.magnitude.run/customizing/llm-configuration); agent options use `provider: 'anthropic'` with a Claude Sonnet model string — [Magnitude agent options](https://docs.magnitude.run/core-concepts/agent-options)

**Skyvern**
- The driving model "receives placeholders instead of real values"; Skyvern substitutes the real value "only at the moment it types into a field"; a Mask Secrets setting hides typed values in later screenshots/page text; stored secrets are never returned by the API; vault integrations: 1Password (Service Account Token), Bitwarden (email + master password), Azure Key Vault, custom HTTP credential service; TOTP via authenticator key, email/SMS forwarding, verification URL, or magic link, polled every 10 s for up to 15 min; passkeys are Enterprise-only — [Skyvern credentials docs](https://www.skyvern.com/docs/credentials/introduction)

**Anthropic computer use and Chrome tools**
- Current tool is `computer_toolset_20260801` (GA on Claude API and Google Cloud; no beta header) with 17 members (`screenshot`, `zoom`, `left_click`, `type`, `key`, `scroll`, `left_click_drag`, `hold_key`, `wait`, etc.); supported models include claude-fable-5-1, claude-mythos-5-1, claude-opus-5-5, claude-sonnet-5-5, claude-haiku-5-5; older `computer_20251124`/`computer_20250124` error on Claude 5.5+; precautions: dedicated VM/container, "Avoid giving the model sensitive data, such as account login information", allowlist internet access, and human confirmation for consequential decisions "and any task requiring affirmative consent, such as accepting cookies, completing financial transactions, or agreeing to terms of service"; Anthropic adds classifiers that scan tool returns (including screenshots) for injections and steer the model to verify the instruction came from the user; a `<robot_credentials>` XML pattern is mentioned for logins with an explicit warning that it raises injection risk — [Claude computer use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)

**Playwright aria snapshots and Playwright MCP**
- Aria snapshots are YAML renderings of the accessibility tree (`- role "name" [attribute=value]`, nested by indentation; attributes `checked`, `disabled`, `expanded`, `level`, `pressed`, `selected`; link URLs as `/url`), obtained via `page.ariaSnapshot()` / `locator.ariaSnapshot()` — [Playwright aria snapshots](https://playwright.dev/docs/aria-snapshots)

**Bot detection, Web Bot Auth, CAPTCHAs**

- "Signed agents" (2025-08-28) extend verified bots to user-directed agents whose infrastructure signs requests; Enterprise customers can act on them as a group in security rules — [Cloudflare: signed agents](https://blog.cloudflare.com/signed-agents/)
- IETF status: `draft-meunier-web-bot-auth-architecture-05` (2026-03-02) is an individual Internet-Draft "not endorsed by the IETF", expired, and replaced by `draft-meunier-webbotauth-httpsig-protocol`; not adopted by a working group — [IETF Datatracker](https://datatracker.ietf.org/doc/draft-meunier-web-bot-auth-architecture/)
- Third-party summaries report Cloudflare, Anthropic and OpenAI moved Web Bot Auth to production together with Claude, ChatGPT, Perplexity and Common Crawl as supported operators, and that Amazon Bedrock AgentCore Browser adopted it; sources conflict on whether an IETF WG was chartered in 2026 — [Crawlbase on Web Bot Auth](https://crawlbase.com/blog/web-bot-auth-signed-agents/); [noqta on agent traffic 2026](https://noqta.tn/en/blog/agent-traffic-engineering-web-bot-auth-2026); contradicted on WG status by [IETF Datatracker](https://datatracker.ietf.org/doc/draft-meunier-web-bot-auth-architecture/)
- Anthropic: Claude in Chrome "is prohibited from bypassing CAPTCHAs" — [Using Claude in Chrome safely](https://support.claude.com/en/articles/12902428-using-claude-in-chrome-safely); Claude Code's browser "won't ... bypass CAPTCHAs on an approved site without your input" — [Claude Code desktop docs](https://code.claude.com/docs/en/desktop)
- Manus pauses and asks the user to Take Over on CAPTCHA — [Manus Cloud Browser docs](https://manus.im/docs/features/cloud-browser); Kernel includes "a managed CAPTCHA solver" — [Kernel features](https://www.kernel.sh/docs/overview/features); Anchor offers CAPTCHA solving and extra-stealth fingerprinting — [Anchor Browser docs](https://docs.anchorbrowser.io/)

### Inferences
- The most robust page representation for a desktop agent is the accessibility tree with stable element refs (Playwright `getByRef`/aria refs, Anthropic `find`→`ref_N`, browser-use indices), with screenshots reserved for layout questions. This also reduces secret leakage because `use_vision=False`-style modes exist precisely to keep typed secrets out of the model's images.
- Variable/placeholder substitution is table stakes: every framework reviewed (browser-use, Stagehand, Skyvern) implements "model sees `%password%`/`x_pass`, automation layer types the real value", and each pairs it with a domain allowlist because a prompt-injected model can still be steered to type the placeholder on the wrong site.
- A personal agent should sign its requests with Web Bot Auth and present an honest UA rather than buying stealth/CAPTCHA-solving; the latter conflicts with Anthropic's usage rules and with the "verified agent" direction Cloudflare, OpenAI and Anthropic are standardizing on.

- Official browser-use documentation of its current DOM serializer (index format, screenshot overlay) was not reachable; only mirrors and a code analysis were found.
- Playwright's docs page on aria snapshots does not itself discuss AI usage; the "useful for AI consumption" wording is in the release notes only.
- Whether an IETF working group has adopted Web Bot Auth in 2026 is unresolved between sources.

## KQ4. Credential handling: password-manager agent features, placeholder substitution, approval flows, OAuth vs passwords, session reuse, vendor prohibitions, local vault storage

### Takeaway
The leading pattern in 2026 is "the model never sees the secret": 1Password's Agentic Mode / 1Password for Claude (GA for Mac 2026-07-16) fills credentials from the extension after a per-request biometric approval and scopes access to the task; Bitwarden's Agent Access SDK (2026-03-24, alpha) pairs an agent with the client and requires per-credential CLI approval, injecting secrets as child-process environment variables; Dashlane refuses autonomous agent vault access; Keeper exposes secrets via a gated MCP; Apple Passwords offers only user-initiated credential-provider autofill. Frameworks (browser-use, Stagehand, Skyvern) implement placeholder substitution plus domain scoping, and vendors (Anthropic, OpenAI) prohibit agents from entering passwords/payment data, bypassing CAPTCHAs, or executing financial transfers. For a local vault, wrap keys with the OS keychain (`safeStorage`), gate on biometrics, and store ciphertext in SQLCipher/age with strict log and screenshot redaction.

### Inferences
- Recommended architecture for a personal desktop agent: (1) a credential broker process separate from the model loop that holds the vault key wrapped by `safeStorage` and unlocked by biometrics; (2) the model only ever sees stable placeholders (`{{cred:github}}`), and the broker types values directly into the embedded webContents (CDP `Input.insertText`) only when the current origin matches the credential's bound origin; (3) every fill is a discrete approval with a visible card (item, site, agent, task) offering approve / switch / deny, defaulting to one-time grants with explicit opt-in for per-site standing grants; (4) after fill, clear fields on failure and scrub typed values from screenshots/text the model sees (Skyvern "Mask Secrets", browser-use `use_vision=False`); (5) prefer OAuth/connector tokens or reused session cookies over typing passwords, and never store cards/IDs at all (1Password and Anthropic both exclude them today).
- If the agent runs inside Electron, the 1Password/Bitwarden extension route is not available (Electron extension API gap in KQ1), so either (a) run the agent browser as a separate real Chrome with the 1Password extension and Agentic Mode, or (b) build the broker yourself using the 1Password SDK/service accounts or Bitwarden's Agent Access CLI as the backing store; (b) loses 1Password's own approval UX unless re-implemented.
- Observed but not publicly documented: Anthropic's desktop-app agent system rules (seen in this session) carve out a narrow exception allowing test credentials to be typed only on `localhost`, `127.0.0.1`, `[::1]`, `*.localhost`, `*.test` hosts for the user's own application, using values from the project's seed/fixture files, never live keys or real identifiers. Treat this as a design pattern to copy, not a cited fact.

### Gaps
- No public URL documents Anthropic's localhost test-credential exception; it was observed only in the live system prompt.
- 1Password has not published protocol details beyond "Noise Framework" (key management, session lifetime, denial/timeout behaviour, audit logs, revocation).
- Bitwarden's SDK repo README (github.com/bitwarden/agent-access) could not be fetched directly; supported languages are unconfirmed.
- Whether 1Password Agentic Mode works with Atlas, Comet or Browserbase after the Claude launch is not stated in 1Password's 2026 posts (Browserbase was the 2025 early-access partner).
- No Windows Hello equivalent for Electron's Touch ID prompt is documented on the fetched page.

## KQ5. Prompt-injection defenses for a browsing/email agent (Anthropic numbers, OpenAI, Google, CaMeL/dual-LLM, lethal trifecta, OWASP 2026, practical rules)

### Takeaway
Measured attack-success rates have fallen sharply but not to zero: Anthropic reports 23.6% → 11.2% in 2025 and, with model training + probes + an action classifier, 0% for Sonnet 5/Opus 5/Mythos 5 and 0.3% for Fable 5 on a harder 2026 eval; OpenAI's Operator went 62% → 23% with a 99%-recall monitor; Google's Chrome agent adds a page-isolated "User Alignment Critic" and origin sets. The consensus architecture is layered: treat page content as data, keep a privileged planner isolated from quarantined content (dual-LLM/CaMeL), bound reachable origins, and require confirmation for state-changing actions, because "99% is a failing grade" and the lethal trifecta (private data + untrusted content + exfiltration channel) cannot be filtered away.

### Cited Findings

**Anthropic**
- 2025 pilot: 123 test cases across 29 attack scenarios; autonomous-mode attack success fell from 23.6% to 11.2% with safeguards; on a browser-specific set of four attack types (hidden DOM fields, URL/tab-title injections) it fell from 35.7% to 0% — [Piloting Claude for Chrome](https://claude.com/blog/claude-for-chrome)
- 2026 GA: three layers (model training on a growing attack library; "probes" that scan tool results and warn Claude to be suspicious; action classifiers using "the same mechanism as Claude Code's auto mode" that block actions not matching the request); on the current harder eval, pre-safeguard rates were 17.6% (Opus 4.5) and 3.8% (Opus 5); with probes 16.7% (Opus 4.5, Nov-2025 safeguards); with probes + classifier 0% for Sonnet 5, Opus 5, Mythos 5 and 0.3% for Fable 5; successful breaks were "manually verified as low-severity"; "prompt injection is a moving target" — [Claude in Chrome is generally available](https://claude.com/resources/articles/claude-in-chrome-generally-available)
- API-side: classifiers scan tool returns (incl. screenshots) and steer Claude to check whether an instruction really came from the user; opt-out is possible via support — [Claude computer use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- ShadowPrompt: a zero-click injection chain in the Claude Chrome extension reported by Koi research (published 2026-03-26), fixed in extension 1.0.41 with an underlying XSS fixed 2026-02-19 (secondary report) — [SOCRadar on ShadowPrompt](https://socradar.io/blog/shadowprompt-zero-click-anthropics-claude/)

**OpenAI**
- Operator: on 31 injection scenarios susceptibility was 62% unmitigated, 47% with prompting only, 23% final; a separate prompt-injection monitor pauses execution with 99% recall / 90% precision on 77 red-team attempts and flagged 46 of 13,704 benign screens; confirmations, watch mode and refusals "continue to apply, serving as speed bumps for potential attackers"; OpenAI "expect[s] that adversaries will craft novel prompt injection attacks" — [Operator System Card (PDF)](https://cdn.openai.com/operator_system_card.pdf)
- Atlas: CISO calls injection "a frontier, unsolved security problem"; mitigations are red-teaming, training to ignore malicious instructions, "overlapping guardrails", rapid response; Willison: "in application security 99% is a failing grade" and logged-in mode shifts the security decision onto users — [Simon Willison: OpenAI CISO on Atlas](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/)

**Google Chrome (2025-12-08)**
- Spotlighting (prioritize user/system instructions over page text) plus training against known attacks; a User Alignment Critic, "a separate model built with Gemini", isolated from page content and seeing only action metadata, approves/rejects each planned action, with repeated rejections returning control to the user; Agent Origin Sets split read-only vs read-writable origins and hide unrelated iframes; model-generated URLs must pass a deterministic check; a real-time injection classifier runs in parallel with planning; design cites the dual-LLM pattern and CaMeL — [Google: Architecting security for agentic capabilities in Chrome](https://blog.google/security/architecting-security-for-agentic/)

**Brave's research on Comet, Fellou, Opera Neon**
- Comet (reported 2025-07-25, disclosed 2025-08-20): instructions hidden behind a Reddit spoiler executed on "Summarize the current webpage", exfiltrating email and a Gmail OTP; initial fix 07-27 was incomplete; recommendations: separate user instructions from page content and treat model output as untrusted, independently check each action against the user's request, require explicit approval for security-sensitive actions such as sending email, never auto-click through TLS interstitials, isolate agentic browsing with minimum permissions — [Brave: Comet prompt injection](https://brave.com/blog/comet-prompt-injection/)
- "Unseeable" injections (2025-10-21): near-invisible text in screenshots is OCR'd into Comet's prompt; Fellou sends visible page text to the LLM on mere navigation; a withheld third issue was later disclosed as Opera Neon; recommendations: isolate agentic from regular browsing, require explicit user invocation for agentic actions, "treat agentic browsing as dangerous" until categorical improvements — [Brave: Unseeable prompt injections](https://brave.com/blog/unseeable-prompt-injections/)

**Architectural patterns**
- Lethal trifecta (2025-06-16): private-data access + exposure to untrusted content + external communication; guardrails claiming 95% "is a failing grade"; the fix is to remove one leg; once untrusted input is ingested it "must be unable to trigger consequential actions"; incidents cited include Microsoft 365 Copilot, GitHub MCP server, GitLab Duo, ChatGPT Operator — [Simon Willison: The lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Dual LLM: a privileged LLM with tools sees only the user's request; a quarantined LLM without tools processes untrusted text into symbolic references (`$email-summary-1`) so "at no point is content handled by the quarantined LLM exposed to the privileged LLM"; CaMeL extends it by having the P-LLM emit a restricted-Python program whose interpreter tracks capabilities per variable and enforces policies at tool calls (e.g., send email only to trusted recipients, else ask); limitations: policies are hard to write, approval "user fatigue" — [Simon Willison on CaMeL](https://simonwillison.net/2025/Apr/11/camel/)
- CaMeL paper (arXiv 2503.18813, v2 2025-06-24; Debenedetti, Shumailov, Carlini, Tramèr et al.): extracts control and data flows from the trusted query so untrusted data "cannot alter the program flow"; solves 77% of AgentDojo tasks with provable security vs 84% undefended — [arXiv: Defeating Prompt Injections by Design](https://arxiv.org/abs/2503.18813)

**OWASP Top 10 for LLM Applications 2026**
- Published 2026-08-03 (v1.0): 1 Prompt Injection, 2 Sensitive Information Disclosure, 3 Excessive Agency (up from 6), 4 Supply Chain, 5 Data and Model Poisoning, 6 Unbounded Consumption (up from 10), 7 Misinformation, 8 Hidden Context Exposure (renamed from System Prompt Leakage), 9 Vector and Embedding Weaknesses, 10 Improper Output Handling (down from 5); methodology blended a 7,714-incident corpus (6,639 classifiable) at ~25% with practitioner voting at ~75%; no categories added or removed — [CSA research note on OWASP LLM Top 10 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-owasp-llm-top10-2026-incident-weighted-202/)
- Hidden Context Exposure broadens scope to tool/function schemas, retrieved policy text, developer instructions and anything assembled into the context the user cannot see; guidance is to assume hidden context can be discovered and not treat it as a security control — [Invicti on OWASP LLM Top 10 2026](https://www.invicti.com/blog/owasp-llm-top-10-2026-whats-new)
- The OWASP project page fetched still listed the 2025 edition (LLM01:2025 Prompt Injection … LLM10:2025 Unbounded Consumption), so the 2026 ordering above rests on the CSA/Invicti secondary notes — [OWASP GenAI LLM Top 10](https://genai.owasp.org/llm-top-10/)

**Product-level controls that operationalize these rules**
- Anthropic desktop pane: write-action classifiers in every mode plus domain-allowlist checks before new sites — [Claude Code desktop docs](https://code.claude.com/docs/en/desktop); "following instructions found in emails or web content" is on the never-do list — [Claude in Chrome permissions guide](https://support.claude.com/en/articles/12902446-claude-in-chrome-permissions-guide)
- Playwright MCP origin allow/block lists are explicitly "not a security boundary" and ignore redirects — [microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp); browser-use's allowlist had a userinfo bypass (CVE-2025-47241) — [Debian tracker](https://security-tracker.debian.org/tracker/CVE-2025-47241)
- Zenity on Atlas: memories poisoned in one product propagate to the browser agent; any-domain egress makes exfiltration allowlisting infeasible — [Zenity Labs on Atlas](https://labs.zenity.io/post/exploring-the-risks-of-chatgpt-s-atlas-browser)

### Inferences
- Practical rule set for a personal browsing/email agent, each traceable to a cited control: (1) page/email content is data, never instructions, and tool results carry a provenance tag the planner cannot override (Brave, Google spotlighting, Anthropic never-list); (2) a separate action checker (classifier or small critic model) that sees only the user's request and the proposed action metadata, not page content (Google critic, Anthropic action classifier, CaMeL policies); (3) origin sets: read-only vs read-writable origins per task, deterministic URL checks, confirm on any new origin (Google; Claude Code allowlist check); (4) confirmations for every state-changing or egress action (send, post, purchase, delete, grant), with pause-when-unwatched on sensitive sites (Operator/Atlas watch mode); (5) credentials and payment data never enter the model (KQ4) and the agent never completes CAPTCHAs; (6) assume any domain is an exfiltration channel, so remove the "private data" leg where possible (logged-out/clean profile by default) and log every action for replay; (7) make allowlists enforce on redirects and canonicalized hosts (Playwright MCP and browser-use caveats).
- Because evaluated attack-success rates vary by an order of magnitude across model generations (17.6% vs 3.8% pre-safeguards for Opus 4.5 vs Opus 5), model choice is itself a security control; pin the newest model with published eval numbers for autonomous browsing.

### Gaps
- OWASP's own 2026 publication page was not reachable; the ranking is from reputable secondary notes.
- Anthropic's 2026 GA article does not describe the eval corpus size or attack taxonomy, so the 0–0.3% figures cannot be compared like-for-like with the 2025 123-case set.
- Microsoft's Edge blog says nothing about prompt-injection defenses for "Browse with Copilot"; no Edge-specific defense documentation was found.
- No independent (non-vendor) replication of Anthropic's, OpenAI's or Google's attack-success numbers was found.
